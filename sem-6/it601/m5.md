### 1. Foundations of Network Security

#### 1.1 Introduction to the Concept of Security

**Why Network Security Matters**

Every time data travels across a network — whether across a LAN, the public Internet, or a wireless link — it passes through infrastructure owned and operated by parties other than the communicating hosts. Any of those intermediate points is a potential vantage point for an attacker. Network security is the discipline of ensuring that despite this hostile environment, communication remains confidential, accurate, and available to legitimate parties.

Security is not a single feature that can be bolted on; it is a property of an entire system that must be designed in from the start. A single weak link — an unencrypted protocol, an unauthenticated endpoint, a misconfigured firewall — can invalidate every other safeguard.

***

**The CIA Triad — Three Foundational Security Goals**

Every security requirement can be traced back to one or more of three fundamental properties, collectively known as the **CIA Triad**:

```
          Confidentiality
               /\
              /  \
             /    \
            /      \
           /________\
     Integrity    Availability
```

**1. Confidentiality**

Information must be accessible only to those who are authorised to see it. An eavesdropper who intercepts data in transit must not be able to read it.

* Achieved by: **Encryption** (symmetric and asymmetric).
* Violated by: Eavesdropping, wiretapping, packet sniffing, traffic analysis.

**2. Integrity**

Information must not be altered — intentionally or accidentally — during storage or transit, and any unauthorised modification must be detectable.

* Achieved by: **Cryptographic hash functions**, **Message Authentication Codes (MACs)**, **Digital Signatures**.
* Violated by: Man-in-the-middle attacks that modify data, bit-flipping attacks, replay attacks.

**3. Availability**

Systems and data must be accessible to authorised users when needed. An attacker who cannot read or modify data can still cause harm by making it inaccessible.

* Achieved by: **Redundancy**, **rate limiting**, **firewalls**, **DDoS mitigation**.
* Violated by: Denial of Service (DoS) and Distributed Denial of Service (DDoS) attacks, ransomware.

***

**Extended Security Properties**

Beyond the CIA Triad, several additional properties appear in formal security models:

| Property            | Definition                                                          | Mechanism                                                                 |
| ------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **Authentication**  | Verifying that a party is who it claims to be                       | Passwords, certificates, public key cryptography, biometrics              |
| **Non-repudiation** | A party cannot deny having sent a message or performed an action    | Digital signatures (only the holder of the private key could have signed) |
| **Authorisation**   | A verified identity has only the permissions it is supposed to have | Access control lists, role-based access control, capability systems       |
| **Accountability**  | Actions can be traced back to the responsible party                 | Audit logs, digital signatures, timestamps                                |
| **Freshness**       | A message is recent and not a replay of an old message              | Nonces (random numbers used once), timestamps, sequence numbers           |

***

**Classes of Attackers and Threat Models**

Security is always designed against a **threat model** — a description of the assumed attacker's capabilities and goals. Common attacker classes:

| Attacker Class           | Capabilities                                                                  | Examples                                                                      |
| ------------------------ | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **Passive eavesdropper** | Can observe traffic but not modify it                                         | Wiretapper on a shared medium, packet sniffer on an unencrypted Wi-Fi network |
| **Active attacker**      | Can intercept, inject, modify, delete, and replay packets                     | Man-in-the-Middle (MitM) on an ARP-poisoned LAN                               |
| **Insider threat**       | Legitimate access; abuses privileges                                          | Disgruntled employee exfiltrating data                                        |
| **Nation-state / APT**   | Large resources; long time horizon; can compromise hardware and supply chains | Advanced Persistent Threat actors                                             |
| **Script kiddie**        | Limited skill; uses pre-built tools                                           | Automated vulnerability scanners, DDoS-for-hire services                      |

The **Dolev-Yao model** is the standard formal attacker model in cryptographic protocol analysis: the adversary has complete control of the network — it can read, intercept, modify, delay, replay, and inject any message — but cannot break computationally hard cryptographic primitives.

***

**Types of Security Attacks**

Attacks are classified along two axes:

**By impact on data flow:**

| Attack Type        | Description                                                      | Examples                                                                                           |
| ------------------ | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **Passive Attack** | Observing or monitoring transmissions without altering them      | Eavesdropping, traffic analysis (inferring information from patterns even without reading content) |
| **Active Attack**  | Altering data streams, injecting messages, or disrupting service | Masquerade, replay, modification, denial of service                                                |

**Specific active attack categories:**

| Attack                         | Description                                                                                                                        |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Masquerade (Spoofing)**      | Attacker impersonates a legitimate entity (IP spoofing, email spoofing, ARP spoofing)                                              |
| **Replay Attack**              | Attacker captures a valid transmission and retransmits it later (e.g., replaying an authentication credential)                     |
| **Modification Attack**        | Attacker alters the content of a message in transit (man-in-the-middle data tampering)                                             |
| **Denial of Service (DoS)**    | Attacker overwhelms a resource to prevent legitimate access (SYN flood, ICMP flood)                                                |
| **Distributed DoS (DDoS)**     | DoS launched from thousands of compromised machines (a botnet) simultaneously                                                      |
| **Man-in-the-Middle (MitM)**   | Attacker secretly intercepts and potentially relays communications between two parties who believe they are communicating directly |
| **SQL Injection**              | Attacker injects malicious SQL into an input field, causing a database to execute unintended commands                              |
| **Cross-Site Scripting (XSS)** | Attacker injects malicious scripts into web pages viewed by other users                                                            |
| **Phishing**                   | Social engineering attack to trick users into revealing credentials                                                                |
| **Brute Force**                | Exhaustively trying all possible keys or passwords                                                                                 |
| **Dictionary Attack**          | Trying likely passwords from a precomputed list                                                                                    |
| **Rainbow Table Attack**       | Using precomputed hash → plaintext tables to reverse a password hash                                                               |

***

**Security Services vs. Security Mechanisms**

**Security Services** (what is provided) vs. **Security Mechanisms** (how it is implemented):

| Security Service    | Mechanism(s) Used                                            |
| ------------------- | ------------------------------------------------------------ |
| **Confidentiality** | Symmetric encryption (AES), asymmetric encryption (RSA), TLS |
| **Data integrity**  | Hash functions (SHA-256), HMAC, digital signatures           |
| **Authentication**  | Digital certificates, challenge-response, Kerberos, PKI      |
| **Non-repudiation** | Digital signatures with public key cryptography              |
| **Access control**  | Firewalls, ACLs, VPNs, capability lists                      |
| **Availability**    | Redundancy, rate limiting, CDN, DDoS mitigation services     |

***

**The Concept of Trust and the Security Perimeter**

Traditional network security assumed a clear boundary between a trusted internal network and an untrusted external network (the Internet). A **firewall** enforced this boundary — anything inside was trusted, anything outside was not.

This **perimeter model** has been largely undermined by:

* Mobile devices and remote work (endpoints outside the perimeter).
* Cloud computing (servers outside the perimeter).
* Insider threats (attackers already inside).
* Lateral movement — an attacker who breaches the perimeter can move freely within the trusted zone.

The modern response is the **Zero Trust Architecture** (ZTA): **"never trust, always verify."** Every access request — regardless of origin, inside or outside the traditional perimeter — must be authenticated and authorised based on identity, device health, and context. Access is granted with least privilege.

***

**Kerckhoffs's Principle**

A foundational principle of cryptographic system design (formulated by Auguste Kerckhoffs in 1883):

> **A cryptosystem should be secure even if everything about the system, except the key, is public knowledge.**

This means security must not depend on keeping the algorithm secret ("security through obscurity"). The algorithm should be able to withstand public scrutiny — which is why open, peer-reviewed algorithms (AES, RSA, SHA-256) are trusted, while proprietary secret algorithms are not.

The corollary: **the key must be the only secret**, and key management (generation, distribution, storage, rotation, revocation) is therefore one of the hardest problems in practical security.

#### 1.2 Network Security Design Paradigm

**What is a Security Design Paradigm?**

A **security design paradigm** is the overarching framework of principles, strategies, and architectural decisions that guide how security is built into a network system. Rather than being a single rule, it is a mindset and a structured methodology that determines how every component of a system handles threats.

***

**Core Design Principles**

**1. Defence in Depth (Layered Security)**

No single security measure is sufficient. An attacker who defeats one layer should still face additional barriers. Security controls are stacked at every layer of the system:

```
Physical security (locked server rooms)
         |
Network security (firewalls, IDS/IPS)
         |
Host security (OS hardening, endpoint protection)
         |
Application security (input validation, WAF)
         |
Data security (encryption at rest and in transit)
         |
User / Identity security (MFA, least privilege)
```

Each layer assumes the outer layers may be compromised. This is the principle of **defence in depth** — borrowed from military strategy.

**2. Principle of Least Privilege**

Every user, process, and system component should be granted the **minimum access rights necessary** to perform its function, and no more. A compromised component with minimal privileges can do limited damage.

* A web server process should not have write access to the entire file system.
* A database account for a read-only reporting tool should not have INSERT or DELETE permissions.
* A user should not have administrator rights unless performing administrative tasks.

**3. Fail-Safe Defaults**

The default state of a system should be **secure** — access should be denied unless explicitly permitted. The burden of granting access is preferred over the burden of denying it.

* A firewall that blocks all traffic by default and only opens specific ports is safer than one that allows all traffic and tries to block known threats.
* An application that throws an error on unexpected input is safer than one that silently continues.

**4. Open Design (Kerckhoffs's Principle Applied)**

Security should not rely on the secrecy of the design. Algorithms and protocols should be publicly known and peer-reviewed. Only keys should be secret. This enables public scrutiny and detection of weaknesses before deployment.

**5. Separation of Privilege**

Critical operations should require multiple independent conditions to be satisfied. No single person or component should have unconstrained power.

* Two-person integrity rules for nuclear launch codes.
* Multi-signature cryptocurrency wallets requiring $k$ of $n$ keys.
* Dual-control for large financial transactions.

**6. Economy of Mechanism (Simplicity)**

Security mechanisms should be as simple as possible. Complexity introduces unanticipated interactions and hidden vulnerabilities. Every line of code in a security-critical path is a potential attack surface.

**7. Complete Mediation**

Every access to every resource must be checked against the access control policy. No cached or assumed permissions should be used without re-validation. This prevents attacks that exploit stale authorisation states.

**8. Psychological Acceptability**

Security mechanisms should not make the system unreasonably difficult to use. If users find security controls too burdensome, they will circumvent them. Good security design makes the secure path the easy path.

***

**The Security Architecture Components**

A complete network security architecture integrates several classes of control:

**Firewalls**

A **firewall** is a network device (hardware or software) that enforces an access control policy on network traffic. It inspects packets and permits or denies them based on rules.

| Firewall Type                                   | Description                                                                                                                                                       |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Packet-filtering firewall**                   | Inspects individual packets in isolation based on IP address, port, and protocol. Fast but stateless — cannot detect attacks spread across multiple packets       |
| **Stateful inspection firewall**                | Tracks the state of connections. Only allows packets that belong to an established, legitimate connection. Blocks packets that do not belong to any known session |
| **Application-layer firewall (proxy firewall)** | Understands application-layer protocols (HTTP, FTP, DNS). Can inspect content, enforce application-level policies, and detect protocol-specific attacks           |
| **Next-Generation Firewall (NGFW)**             | Combines stateful inspection with deep packet inspection, intrusion prevention, SSL decryption, and application identification                                    |

**Demilitarised Zone (DMZ)**

A **DMZ** is a network segment physically separated from both the internal network and the Internet, where publicly accessible services (web servers, mail servers, DNS servers) are hosted.

```
Internet --[Outer Firewall]--> [DMZ: Web/Mail/DNS Servers] --[Inner Firewall]--> Internal LAN
```

If an attacker compromises a DMZ server, the inner firewall limits damage to the internal network. The DMZ is exposed but isolated.

**Intrusion Detection and Prevention Systems (IDS/IPS)**

* **IDS (Intrusion Detection System)**: Monitors network traffic and generates alerts when suspicious patterns are detected. Passive — does not block traffic.
* **IPS (Intrusion Prevention System)**: Monitors and actively blocks suspicious traffic inline. Can drop packets or reset connections.

Detection approaches:

| Approach                    | Description                                                  | Strength                                             | Weakness                                             |
| --------------------------- | ------------------------------------------------------------ | ---------------------------------------------------- | ---------------------------------------------------- |
| **Signature-based**         | Matches traffic against a database of known attack patterns  | Very accurate for known attacks; low false positives | Cannot detect new (zero-day) attacks                 |
| **Anomaly-based**           | Establishes a baseline of normal behaviour; flags deviations | Can detect unknown attacks                           | Higher false positive rate; requires training period |
| **Heuristic / Behavioural** | Uses rules and ML models to identify suspicious behaviour    | Balanced                                             | May flag legitimate unusual activity                 |

**VPN — Virtual Private Network**

A **VPN** creates an encrypted tunnel over an untrusted network (the Internet), allowing remote endpoints to communicate as if they were on the same private network.

* **Site-to-site VPN**: Connects two entire networks (e.g., two office LANs) through a persistent encrypted tunnel.
* **Remote-access VPN**: Allows individual users (working from home, travelling) to connect to a corporate network over an encrypted tunnel.

Protocols: IPsec (IKEv2), SSL/TLS-based VPNs (OpenVPN, WireGuard).

**Network Access Control (NAC)**

NAC enforces a policy requiring devices to meet a minimum security posture (OS patched, antivirus running, disk encrypted) before being allowed to connect to the network. Non-compliant devices may be quarantined to a remediation VLAN.

***

**Security Policy Framework**

A **security policy** is a formal document that defines what is to be protected, from whom, and how. The policy drives all technical controls.

The policy framework typically has three levels:

| Level           | Document                         | Audience          | Content                                                                      |
| --------------- | -------------------------------- | ----------------- | ---------------------------------------------------------------------------- |
| **Strategic**   | Security Policy                  | Board / Executive | Organisational security goals, risk appetite, compliance obligations         |
| **Tactical**    | Security Standards and Baselines | IT Management     | Specific required configurations, approved algorithms, password requirements |
| **Operational** | Procedures and Guidelines        | IT Staff / Users  | Step-by-step instructions for security tasks, acceptable use                 |

***

**Risk Management**

Security decisions are fundamentally about **risk management** — the rational allocation of limited resources to address threats proportional to their likelihood and impact.

\$$\text{Risk} = \text{Threat} \times \text{Vulnerability} \times \text{Asset Value}\$$

**Risk treatment options:**

| Option       | Description                                      | Example                                                         |
| ------------ | ------------------------------------------------ | --------------------------------------------------------------- |
| **Avoid**    | Eliminate the risky activity                     | Do not collect sensitive data that is not necessary             |
| **Mitigate** | Reduce likelihood or impact with controls        | Encrypt data at rest to reduce impact of server theft           |
| **Transfer** | Shift risk to a third party                      | Cyber insurance; outsourcing to a compliant cloud provider      |
| **Accept**   | Acknowledge residual risk after other treatments | Accept that perfect security is impossible; monitor and respond |

***

**Security Models**

Formal security models provide mathematical frameworks for reasoning about access control policies:

| Model                          | Description                                             | Key Concept                                                                                                              |
| ------------------------------ | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Bell-LaPadula**              | Focuses on confidentiality; used in government/military | No read up (cannot read higher-classified data); No write down (cannot write to lower classification — prevents leakage) |
| **Biba**                       | Focuses on integrity; the dual of Bell-LaPadula         | No read down (cannot read lower-integrity data); No write up (cannot write to higher-integrity level)                    |
| **Clark-Wilson**               | Focuses on commercial integrity                         | Well-formed transactions; separation of duties                                                                           |
| **Brewer-Nash (Chinese Wall)** | Prevents conflicts of interest                          | Once a user accesses data from one competitor, they cannot access data from another in the same category                 |

***

**The Attack Surface and Attack Vector**

* **Attack surface**: The total set of points where an attacker could attempt to enter or extract data from a system. A large attack surface — many open ports, many running services, many user accounts, large codebase — means more potential vulnerabilities. Reducing attack surface (disabling unused services, closing unused ports, removing unused software) is a foundational hardening measure.
* **Attack vector**: The specific path or means by which an attacker reaches and exploits a vulnerability. Examples: a vulnerable web application, an unpatched OS, a phishing email, an open USB port, an insecure wireless network.

### 2. Cryptographic Techniques

#### 2.1 Symmetric Key Cryptographic Algorithms

**What is Cryptography?**

**Cryptography** is the science of securing communication in the presence of adversaries. It transforms readable data (**plaintext**) into an unreadable form (**ciphertext**) using a mathematical algorithm and a **key**, a process called **encryption**. The reverse — converting ciphertext back to plaintext — is **decryption**.

Formally, an encryption scheme consists of:

* A **key generation** algorithm: $k \leftarrow \text{KeyGen}(1^\lambda)$ where $\lambda$ is the security parameter.
* An **encryption** function: $c = E(k, m)$ where $m$ is the plaintext and $c$ is the ciphertext.
* A **decryption** function: $m = D(k, c)$.

Correctness requirement: $D(k, E(k, m)) = m$ for all valid keys $k$ and messages $m$.

***

**What is Symmetric Key Cryptography?**

In **symmetric key cryptography** (also called **secret key** or **private key** cryptography), the **same key** is used for both encryption and decryption. Both the sender and the receiver must possess this shared secret key, and the key must be kept confidential from all other parties.

```
Sender                                    Receiver
   |                                          |
   |  Plaintext (m)                           |
   |  + Secret Key (K)                        |
   |  --[Encryption Algorithm]--> Ciphertext  |
   |                                          |
   |       Ciphertext transmitted over        |
   |       insecure channel                   |
   |                                          |
   |                          Ciphertext      |
   |                          + Secret Key (K)|
   |                          --[Decryption]->|
   |                          Plaintext (m)   |
```

**Key properties:**

| Property                 | Value                                                                             |
| ------------------------ | --------------------------------------------------------------------------------- |
| Key count                | One shared key for both parties                                                   |
| Key distribution problem | Yes — the key must be securely shared before communication can begin              |
| Speed                    | Very fast — orders of magnitude faster than asymmetric                            |
| Scalability              | Poor — $n$ parties require $\binom{n}{2} = \frac{n(n-1)}{2}$ unique pairwise keys |
| Typical key size         | 128–256 bits                                                                      |

***

**Two Classes of Symmetric Ciphers**

**Stream Ciphers**

Encrypt one bit (or byte) at a time. A **keystream** is generated from the key and XORed with the plaintext. The keystream must be pseudo-random and must never be reused with the same key.

\$$c\_i = m\_i \oplus k\_i\$$

* Fast and suitable for real-time communication (voice, video).
* Examples: RC4 (deprecated), ChaCha20 (modern), A5/1 (GSM).
* Critical vulnerability: **reusing the keystream** allows plaintext recovery via XOR of two ciphertexts.

**Block Ciphers**

Encrypt fixed-size blocks of plaintext (e.g., 64 or 128 bits) at a time using a fixed transformation determined by the key. Longer messages are divided into blocks and processed according to a **mode of operation**.

Most modern symmetric algorithms are block ciphers.

***

**DES — Data Encryption Standard**

DES was adopted as the US federal standard in 1977 (FIPS 46). It was the dominant symmetric cipher for two decades.

**Parameters:**

* Block size: **64 bits**
* Key size: **56 bits** (technically 64 bits, but 8 are parity bits, leaving 56 effective bits)
* Structure: **Feistel network**, 16 rounds

**Feistel Network Structure:**

A Feistel cipher splits the block into two halves ($L$ and $R$) and applies a round function $F$ iteratively. The round function does not need to be invertible because the structure itself is self-inverting.

```
Round i:
  L_{i+1} = R_i
  R_{i+1} = L_i XOR F(R_i, K_i)

Decryption (same structure, keys applied in reverse order):
  R_i = L_{i+1}
  L_i = R_{i+1} XOR F(L_{i+1}, K_i)
```

**DES Round Function F:**

1. **Expansion (E)**: Expand right half from 32 to 48 bits.
2. **Key Mixing**: XOR with 48-bit round subkey.
3. **S-Boxes (Substitution)**: 8 S-boxes, each mapping 6-bit input to 4-bit output. S-boxes are the primary source of non-linearity and are designed to resist differential cryptanalysis.
4. **Permutation (P)**: A fixed bit permutation.

**DES Key Schedule:** The 56-bit key generates 16 subkeys of 48 bits each through shifts and permutations.

**Why DES is broken:**

The 56-bit key space contains $2^{56} \approx 7.2 \times 10^{16}$ possible keys. In 1998, the **EFF DES Cracker** ("Deep Crack") exhausted the entire key space in **56 hours** using specialised hardware. By 1999, combined with distributed computing, the record fell to **22 hours**. Today, DES can be broken in seconds with modern hardware. DES must **never** be used in new systems.

***

**Triple DES (3DES / TDEA)**

To extend DES's useful life without redesigning it, **Triple DES** applies DES three times with two or three independent keys.

**3DES-EDE (Encrypt-Decrypt-Encrypt) with two keys ($K\_1$, $K\_2$):**

\$$c = E\_{K\_1}\bigl(D\_{K\_2}\bigl(E\_{K\_1}(m)\bigr)\bigr)\$$

The Decrypt-in-the-middle ensures backward compatibility: if $K\_1 = K\_2$, the result is identical to single DES (since $E\_{K}(D\_{K}(x)) = x$).

**Three-key 3DES ($K\_1$, $K\_2$, $K\_3$, all different):**

\$$c = E\_{K\_3}\bigl(D\_{K\_2}\bigl(E\_{K\_1}(m)\bigr)\bigr)\$$

Effective key length: 112 bits (two-key) or 168 bits (three-key). Block size remains 64 bits.

**Problems with 3DES:**

* Three times slower than DES — still slow compared to AES.
* 64-bit block size makes it vulnerable to **birthday attacks** on the block size (SWEET32 attack, 2016): after approximately $2^{32}$ blocks (\~32 GB) are encrypted with the same key, block collisions leak information. NIST deprecated 3DES in 2019 and disallowed it for new applications from 2023.

***

**AES — Advanced Encryption Standard**

**AES** (FIPS 197, 2001) is the current global symmetric encryption standard, selected through an open international competition run by NIST from 1997 to 2001. The winning algorithm was **Rijndael**, designed by Joan Daemen and Vincent Rijmen.

**Parameters:**

| Variant | Key Size | Number of Rounds |
| ------- | -------- | ---------------- |
| AES-128 | 128 bits | 10               |
| AES-192 | 192 bits | 12               |
| AES-256 | 256 bits | 14               |

Block size is always **128 bits** (16 bytes) for all variants.

**AES is not a Feistel cipher** — it uses a **Substitution-Permutation Network (SPN)**.

***

**AES Internal Structure**

AES operates on a **4×4 matrix of bytes** called the **State**:

```
State (16 bytes = 128-bit block):
| s00  s01  s02  s03 |
| s10  s11  s12  s13 |
| s20  s21  s22  s23 |
| s30  s31  s32  s33 |
```

Each AES round (except the final) applies four transformations in sequence:

**1. SubBytes**

Each byte in the State is replaced by its corresponding value in the **AES S-Box** — a fixed 16×16 lookup table constructed from the multiplicative inverse in $GF(2^8)$ followed by an affine transformation. This provides **non-linearity** (the critical property for security — prevents linear attacks).

**2. ShiftRows**

The rows of the State are cyclically shifted left by different amounts:

* Row 0: shift by 0 (unchanged)
* Row 1: shift by 1 byte
* Row 2: shift by 2 bytes
* Row 3: shift by 3 bytes

This provides **diffusion** — moves bytes to different column positions, ensuring that each column after MixColumns depends on bytes from all columns of the previous round.

**3. MixColumns**

Each column of the State is treated as a polynomial over $GF(2^8)$ and multiplied by a fixed polynomial $a(x) = {03}x^3 + {01}x^2 + {01}x + {02}$. This provides **full diffusion** within a column — each output byte depends on all four input bytes of the column.

The final round **omits MixColumns** (this makes encryption and decryption structurally symmetric).

**4. AddRoundKey**

Each byte of the State is XORed with the corresponding byte of the round key derived from the key schedule. This is the only step that uses the key. All other steps provide confusion and diffusion but are key-independent.

**Key Expansion (Key Schedule):**

The original key is expanded into $N\_r + 1$ round keys (11 for AES-128), each 128 bits, using a recursive function involving SubBytes (S-Box on individual bytes), RotWord (cyclic shift), and XOR with a round constant.

**AES Round (summary):**

```
Initial: AddRoundKey (using original key)
For each round 1 to N_r - 1:
    SubBytes
    ShiftRows
    MixColumns
    AddRoundKey
Final round:
    SubBytes
    ShiftRows
    AddRoundKey  (no MixColumns)
```

**Why AES is secure:**

* **No known practical attack** faster than exhaustive key search against AES-128 (best known: biclique attack reduces search space by a tiny factor, negligible in practice).
* Strong theoretical grounding: AES provides excellent **confusion** (SubBytes via S-Box) and **diffusion** (ShiftRows + MixColumns). After just 2 rounds, every output bit depends on every input bit — the **avalanche effect**.
* Hardware acceleration: Most modern CPUs (Intel, AMD, ARM) implement AES in dedicated instructions (`AES-NI`) achieving throughputs of many GB/s.

***

**Modes of Operation for Block Ciphers**

A block cipher encrypts exactly one block at a time. **Modes of operation** define how to apply a block cipher to messages longer than one block. The mode chosen has enormous security implications.

**ECB — Electronic Code Book Mode**

\$$c\_i = E\_K(m\_i)\$$

Each block encrypted independently. **Deterministic**: identical plaintext blocks produce identical ciphertext blocks.

**Fatal flaw:** Patterns in the plaintext are preserved in the ciphertext. The canonical demonstration is the "ECB penguin" — encrypting a bitmap image in ECB mode produces a ciphertext that still shows the outline of the original image. **ECB must never be used.**

**CBC — Cipher Block Chaining Mode**

\$$c\_i = E\_K(m\_i \oplus c\_{i-1}), \quad c\_0 = \text{IV (Initialisation Vector)}\$$

Each plaintext block is XORed with the previous ciphertext block before encryption. The **IV** must be random and unpredictable (not secret, but fresh per message). Identical plaintext blocks produce different ciphertext blocks (provided the IV differs). Decryption can be parallelised; encryption cannot.

**Vulnerability:** A **padding oracle attack** (POODLE, BEAST) against CBC mode in TLS led to its deprecation in TLS 1.3.

**CTR — Counter Mode**

\$$c\_i = m\_i \oplus E\_K(\text{Nonce} | i)\$$

Generates a keystream by encrypting successive counter values (Nonce concatenated with block index). XOR with plaintext. Turns a block cipher into a stream cipher. Fully parallelisable for both encryption and decryption. Random access into the encrypted stream is possible. **The nonce must never be reused with the same key.**

**GCM — Galois/Counter Mode**

Combines CTR mode encryption with a Galois-field-based MAC (GHASH) to provide both **confidentiality and integrity** simultaneously — an **Authenticated Encryption with Associated Data (AEAD)** mode. GCM is the dominant mode in TLS 1.2 and TLS 1.3, IPsec, and SSH.

\$$\text{AES-256-GCM is the de facto standard for high-security symmetric encryption.}\$$

**Mode Comparison Table:**

| Mode | Parallelisable Enc | Parallelisable Dec | Integrity  | Nonce/IV Required | Security                      |
| ---- | ------------------ | ------------------ | ---------- | ----------------- | ----------------------------- |
| ECB  | Yes                | Yes                | No         | No                | Broken — never use            |
| CBC  | No                 | Yes                | No         | Yes (random)      | Vulnerable to padding oracles |
| CTR  | Yes                | Yes                | No         | Yes (unique)      | Secure if nonce not reused    |
| GCM  | Yes                | Yes                | Yes (AEAD) | Yes (unique)      | Current standard              |

***

**The Key Distribution Problem**

The fundamental limitation of symmetric cryptography is the **key distribution problem**: before two parties can communicate securely, they must already share a secret key — but how do they establish this key securely if they have never met and the network is untrusted?

**Solutions:**

* **Physical key exchange**: Out-of-band, e.g., a courier delivers the key. Impractical at Internet scale.
* **Key Distribution Centre (KDC)**: A trusted third party holds pairwise keys with every user (used in Kerberos). Single point of failure.
* **Asymmetric cryptography (Diffie-Hellman key exchange)**: Two parties establish a shared secret over a public channel without any prior secret (covered in Section 2.2). This is the practical solution used universally on the Internet.

#### 2.2 Asymmetric Key Cryptographic Algorithms

**What is Asymmetric Key Cryptography?**

**Asymmetric key cryptography** (also called **public key cryptography**) was a revolutionary development introduced by Whitfield Diffie and Martin Hellman in 1976. Instead of one shared secret key, each party holds a **mathematically linked key pair**:

* **Public key** ($K^+$ or $K\_{pub}$): Can be freely distributed to anyone. Used to encrypt messages or verify signatures.
* **Private key** ($K^-$ or $K\_{priv}$): Must be kept absolutely secret by its owner. Used to decrypt messages or create signatures.

The mathematical relationship between the keys is such that:

* What is encrypted with the public key can only be decrypted with the corresponding private key.
* What is signed with the private key can be verified by anyone with the corresponding public key.
* It is computationally infeasible to derive the private key from the public key (assuming the underlying hard problem holds).

```
Sender                                              Receiver (has K_pub, K_priv pair)
   |                                                       |
   |  Plaintext (m) + Receiver's Public Key (K_pub)        |
   |  --[Encryption]--> Ciphertext (c)                     |
   |                                                       |
   |           Ciphertext transmitted                      |
   |                                                       |
   |                         Ciphertext (c) + K_priv       |
   |                         --[Decryption]--> Plaintext   |
```

**Key properties:**

| Property         | Symmetric                     | Asymmetric                                       |
| ---------------- | ----------------------------- | ------------------------------------------------ |
| Keys             | One shared secret             | Key pair (public + private)                      |
| Key distribution | Hard (must share secret)      | Easy (publish public key)                        |
| Speed            | Very fast                     | 100–1000× slower                                 |
| Key management   | $O(n^2)$ keys for $n$ parties | $O(n)$ key pairs for $n$ parties                 |
| Use cases        | Bulk data encryption          | Key exchange, digital signatures, authentication |

In practice, asymmetric cryptography is used to **exchange or establish a symmetric session key** (key encapsulation), which then encrypts actual data. This **hybrid encryption** approach combines the security of asymmetric with the speed of symmetric.

***

**Mathematical Foundations**

Asymmetric cryptography relies on **trapdoor one-way functions** — functions that are easy to compute in one direction but computationally hard to invert without knowledge of a secret (the trapdoor, i.e., the private key).

Three hard problems underpin modern asymmetric cryptography:

| Hard Problem                                  | Used In              | Description                                                        |
| --------------------------------------------- | -------------------- | ------------------------------------------------------------------ |
| **Integer Factorisation**                     | RSA                  | Given $n = p \times q$ (product of large primes), find $p$ and $q$ |
| **Discrete Logarithm (DLP)**                  | Diffie-Hellman, DSA  | Given $g^x \mod p$, find $x$                                       |
| **Elliptic Curve Discrete Logarithm (ECDLP)** | ECDH, ECDSA, Ed25519 | Given point $Q = kP$ on an elliptic curve, find scalar $k$         |

***

**Diffie-Hellman Key Exchange (DHKE)**

Published in 1976, **Diffie-Hellman** solved the key distribution problem: two parties can establish a **shared secret** over a completely public channel without any prior secret. Neither party transmits the shared secret — they each compute it independently.

**Public parameters** (known to everyone, including attackers):

* A large prime $p$
* A generator $g$ (a primitive root modulo $p$, $1 < g < p$)

**Protocol:**

```
Alice                                               Bob
  |                                                   |
  | Choose random private: a (2 ≤ a ≤ p-2)           | Choose random private: b (2 ≤ b ≤ p-2)
  | Compute public: A = g^a mod p                    | Compute public: B = g^b mod p
  |                                                   |
  |--- Send A = g^a mod p --------------------------->|
  |<-- Send B = g^b mod p ----------------------------|
  |                                                   |
  | Shared secret: S = B^a mod p = (g^b)^a mod p     | Shared secret: S = A^b mod p = (g^a)^b mod p
  |               = g^(ab) mod p                     |               = g^(ab) mod p
  |                                                   |
  |         BOTH PARTIES ARRIVE AT THE SAME S        |
```

**Why an attacker cannot compute $S$:** The attacker sees $g$, $p$, $A = g^a \mod p$, and $B = g^b \mod p$, but to compute $S = g^{ab} \mod p$, they would need to compute $a$ from $A$ (the discrete logarithm problem) or $b$ from $B$. For a 2048-bit prime $p$, this is computationally infeasible.

**Numeric Example (small numbers for illustration):**

```
Public: p = 23, g = 5
Alice: a = 6,  A = 5^6 mod 23 = 15625 mod 23 = 8
Bob:   b = 15, B = 5^15 mod 23 = 30517578125 mod 23 = 19

Alice computes: S = 19^6 mod 23 = 47045881 mod 23 = 2
Bob computes:   S = 8^15 mod 23 = 35184372088832 mod 23 = 2

Shared secret S = 2  (both agree without ever transmitting 2)
```

**Diffie-Hellman is vulnerable to MitM:** DHKE alone provides no authentication. An attacker can intercept and substitute their own public values, establishing separate shared secrets with Alice and Bob. **Authenticated DH** (using certificates or pre-shared authentication) is required in practice — this is what TLS does.

**Ephemeral DH (DHE / ECDHE):** Using fresh random private values for each session (rather than long-term static values) provides **Perfect Forward Secrecy (PFS)**: even if the long-term private key is later compromised, past sessions cannot be decrypted because each session's symmetric key was derived from a different, ephemeral DH exchange.

***

**RSA — Rivest-Shamir-Adleman**

**RSA** (1977) is the most widely deployed asymmetric encryption and digital signature algorithm. Its security rests on the difficulty of factoring the product of two large prime numbers.

**Key Generation:**

1. Choose two large distinct prime numbers $p$ and $q$ (each at least 1024 bits; 2048 or 4096 bits recommended).
2. Compute $n = p \times q$. This is the **modulus**, included in both keys.
3. Compute Euler's totient: $\phi(n) = (p-1)(q-1)$.
4. Choose $e$ such that $1 < e < \phi(n)$ and $\gcd(e, \phi(n)) = 1$ (e is coprime to $\phi(n)$). Common choice: $e = 65537 = 2^{16}+1$ (prime, has few 1-bits, efficient exponentiation).
5. Compute $d$ such that $d \cdot e \equiv 1 \pmod{\phi(n)}$ (modular multiplicative inverse of $e$ mod $\phi(n)$, computed via Extended Euclidean Algorithm).

**Keys:**

* **Public key:** $(n, e)$ — published freely.
* **Private key:** $(n, d)$ — kept secret. ($p$, $q$, $\phi(n)$ are also secret and should be deleted after key generation.)

**Encryption and Decryption:**

\$$\text{Encryption: } c = m^e \mod n\$$ \$$\text{Decryption: } m = c^d \mod n\$$

Correctness follows from **Euler's theorem**: $m^{\phi(n)} \equiv 1 \pmod{n}$, so $c^d = m^{ed} = m^{1 + k\phi(n)} = m \cdot (m^{\phi(n)})^k \equiv m \pmod{n}$.

**Numeric Example (small numbers):**

```
p = 61, q = 53
n = 61 × 53 = 3233
φ(n) = 60 × 52 = 3120
e = 17   (gcd(17, 3120) = 1 ✓)
d = 2753 (17 × 2753 = 46801 = 15 × 3120 + 1 ≡ 1 mod 3120 ✓)

Public key: (3233, 17)
Private key: (3233, 2753)

Encrypt m = 65:
  c = 65^17 mod 3233 = 2790

Decrypt c = 2790:
  m = 2790^2753 mod 3233 = 65  ✓
```

**RSA Security:**

* Factoring $n = 3233 = 61 \times 53$ is trivial for small numbers.
* Factoring a 2048-bit $n$ is computationally infeasible with current technology (best algorithms: General Number Field Sieve, sub-exponential but enormous for 2048-bit moduli).
* Minimum recommended key size: **2048 bits** for short-term security, **3072–4096 bits** for long-term.

**RSA in practice — padding is essential:**

Raw ("textbook") RSA is deterministic and homomorphic — it must never be used directly. Structured padding schemes prevent attacks:

* **PKCS#1 v1.5**: Older padding; vulnerable to Bleichenbacher's attack (padding oracle).
* **OAEP (Optimal Asymmetric Encryption Padding)**: Used for encryption; randomised and CCA-secure.
* **PSS (Probabilistic Signature Scheme)**: Used for signatures; randomised and provably secure.

***

**Digital Signatures**

A **digital signature** provides authentication, integrity, and non-repudiation. The private key holder signs a message; anyone with the corresponding public key can verify the signature.

**Signing and Verification with RSA:**

1. **Compute hash:** $h = H(m)$ where $H$ is a cryptographic hash function (e.g., SHA-256).
2. **Sign:** $\sigma = h^d \mod n$ (sign the hash, not the raw message — hashing first makes it efficient and avoids structural attacks).
3. **Verify:** Compute $h' = \sigma^e \mod n$; accept if $h' = H(m)$.

```
Signer (Alice, has K_priv)           Verifier (Bob, has Alice's K_pub)
   |                                          |
   | m + K_priv                               |
   | -> H(m) -> sign -> σ                     |
   |                                          |
   |--- Send (m, σ) ------------------------->|
   |                                          |
   |             (m, σ) + K_pub of Alice      |
   |             -> compute H(m)              |
   |             -> verify: σ^e = H(m)?       |
   |             -> if yes: signature valid   |
```

**Why digital signatures provide non-repudiation:** Only Alice holds her private key. If Bob can verify the signature with Alice's public key, it must have been created by Alice (assuming her private key was not compromised). Alice cannot later deny signing the message.

***

**Elliptic Curve Cryptography (ECC)**

**ECC** is a modern approach to asymmetric cryptography based on the mathematics of **elliptic curves over finite fields**. An elliptic curve is defined by:

\$$y^2 = x^3 + ax + b \pmod{p}\$$

where $4a^3 + 27b^2 \not\equiv 0 \pmod{p}$ (non-singular condition).

Points on the curve form an **abelian group** under a geometric point addition operation. The **ECDLP** (Elliptic Curve Discrete Logarithm Problem) — given points $P$ and $Q = kP$, find scalar $k$ — is believed to be significantly harder than the regular DLP per bit of key.

**Why ECC matters — key size comparison for equivalent security:**

| Security Level | RSA/DH Key Size | ECC Key Size |
| -------------- | --------------- | ------------ |
| 80-bit         | 1024 bits       | 160 bits     |
| 112-bit        | 2048 bits       | 224 bits     |
| 128-bit        | 3072 bits       | 256 bits     |
| 192-bit        | 7680 bits       | 384 bits     |
| 256-bit        | 15360 bits      | 521 bits     |

ECC achieves the same security as RSA with much shorter keys → faster computation, less bandwidth, lower power consumption. Critically important for constrained devices (IoT, smartcards, mobile).

**Key ECC algorithms:**

| Algorithm                                  | Purpose                                                | Standard        |
| ------------------------------------------ | ------------------------------------------------------ | --------------- |
| **ECDH (Elliptic Curve Diffie-Hellman)**   | Key exchange                                           | RFC 6090        |
| **ECDHE**                                  | Ephemeral ECDH; provides Perfect Forward Secrecy       | Used in TLS 1.3 |
| **ECDSA (EC Digital Signature Algorithm)** | Digital signatures                                     | FIPS 186-4      |
| **Ed25519**                                | Digital signatures on Curve25519; very fast and secure | RFC 8032        |

**Common curves:**

* **P-256 (secp256r1)**: NIST curve; used in TLS, HTTPS, many systems.
* **Curve25519**: Designed by Daniel Bernstein; resistant to side-channel attacks; used in Signal, WireGuard, SSH.
* **P-384, P-521**: Higher security; used in government and high-assurance contexts.

***

**Hash Functions — Cryptographic Integrity Primitive**

Although not an encryption algorithm, **cryptographic hash functions** are fundamental to asymmetric cryptography (signatures) and many other security mechanisms.

A cryptographic hash function $H$ maps an arbitrary-length input to a fixed-length output (digest):

\$$H: {0,1}^\* \rightarrow {0,1}^n\$$

**Required properties:**

| Property                        | Definition                                                                      | Why it matters                                               |
| ------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **Pre-image resistance**        | Given $h$, infeasible to find $m$ such that $H(m) = h$                          | Prevents finding original message from hash                  |
| **Second pre-image resistance** | Given $m\_1$, infeasible to find $m\_2 \neq m\_1$ such that $H(m\_1) = H(m\_2)$ | Prevents forging a message with same hash as a given message |
| **Collision resistance**        | Infeasible to find any $m\_1 \neq m\_2$ such that $H(m\_1) = H(m\_2)$           | Prevents finding any two messages with the same hash         |
| **Avalanche effect**            | A single bit change in input causes \~50% of output bits to change              | Ensures hash is not predictably related to input             |
| **Deterministic**               | Same input always produces same output                                          | Required for verification                                    |
| **Fast to compute**             | Hash computation is efficient                                                   | Practical use                                                |

**Hash Algorithm Comparison:**

| Algorithm          | Output Size | Status     | Notes                                                                  |
| ------------------ | ----------- | ---------- | ---------------------------------------------------------------------- |
| **MD5**            | 128 bits    | Broken     | Collisions found in minutes; never use for security                    |
| **SHA-1**          | 160 bits    | Deprecated | Practical collision attacks demonstrated (SHAttered, 2017); do not use |
| **SHA-256**        | 256 bits    | Secure     | Current standard; used in TLS, DNSSEC, Bitcoin                         |
| **SHA-384**        | 384 bits    | Secure     | Truncated SHA-512; used in TLS with high-security suites               |
| **SHA-512**        | 512 bits    | Secure     | Faster than SHA-256 on 64-bit hardware                                 |
| **SHA-3 (Keccak)** | Variable    | Secure     | Different design (sponge construction); NIST standard since 2015       |
| **BLAKE3**         | Variable    | Secure     | Modern, very fast; used in many new systems                            |

**HMAC — Hash-based Message Authentication Code:**

A MAC provides both integrity and authentication (proves the message came from someone who knows the key). HMAC combines a hash function with a secret key:

\$$\text{HMAC}(K, m) = H\bigl((K \oplus \text{opad}) | H((K \oplus \text{ipad}) | m)\bigr)\$$

where `ipad` and `opad` are fixed constants. HMAC-SHA256 is widely used in TLS, JWT, HTTPS APIs.

#### 2.3 Public Key Infrastructure (PKI)

**The Problem PKI Solves**

Asymmetric cryptography enables secure communication without a pre-shared secret, but introduces a new problem: **how do you know that a public key truly belongs to the entity it claims to belong to?**

Consider: Alice wants to send a confidential message to Bob. She looks up "Bob's public key" from a directory. But how does she know this key was not substituted by an attacker (a man-in-the-middle)? Without authenticating the binding between Bob's identity and his public key, the entire system is insecure.

**PKI (Public Key Infrastructure)** is the framework of policies, roles, hardware, software, and procedures needed to create, manage, distribute, use, store, and revoke **digital certificates** — the mechanism that cryptographically binds a public key to an identity.

***

**Digital Certificates — X.509**

A **digital certificate** is a digitally signed data structure that binds a public key to an identity (a person, organisation, server hostname, or device). The dominant standard is **X.509v3** (RFC 5280).

**X.509 Certificate Contents:**

| Field                       | Description                                                                                                                                                 |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Version**                 | X.509 version (typically v3)                                                                                                                                |
| **Serial Number**           | Unique integer assigned by the CA to this certificate                                                                                                       |
| **Signature Algorithm**     | Algorithm used by the CA to sign the certificate (e.g., `sha256WithRSAEncryption`, `ecdsa-with-SHA256`)                                                     |
| **Issuer**                  | Distinguished Name (DN) of the Certificate Authority that signed this certificate                                                                           |
| **Validity Period**         | `Not Before` and `Not After` dates — the certificate is invalid outside this window                                                                         |
| **Subject**                 | Distinguished Name of the entity the certificate was issued to                                                                                              |
| **Subject Public Key Info** | The public key algorithm and the public key value                                                                                                           |
| **Extensions (v3)**         | Additional fields: Subject Alternative Names (SANs), Key Usage, Extended Key Usage, Basic Constraints (CA or end-entity), CRL Distribution Points, OCSP URL |
| **Signature**               | CA's digital signature over all of the above fields                                                                                                         |

**Distinguished Name (DN) components:**

```
CN=www.example.com       (Common Name — often the hostname)
O=Example Corporation    (Organisation)
OU=IT Department         (Organisational Unit)
L=San Francisco          (Locality)
ST=California            (State/Province)
C=US                     (Country — ISO 3166-1 alpha-2)
```

For TLS server certificates, the **Subject Alternative Name (SAN)** extension contains the actual hostname(s) the certificate is valid for. The Common Name is deprecated for hostname matching.

***

**Certificate Authority (CA) and the Chain of Trust**

A **Certificate Authority (CA)** is a trusted entity that issues digital certificates. The CA's role is to verify the identity of the certificate requester and then sign the certificate with the CA's private key. Browsers and operating systems ship with a pre-installed list of **trusted root CAs** (approximately 100–150 in major browsers). These root CAs are the anchors of trust.

**Chain of Trust (Certificate Hierarchy):**

```
Root CA (self-signed certificate, stored in OS/browser trust store)
    |
    | (Root CA signs Intermediate CA's certificate)
    v
Intermediate CA (certificate signed by Root CA)
    |
    | (Intermediate CA signs End-Entity certificate)
    v
End-Entity Certificate (e.g., www.example.com)
```

**Why intermediate CAs?** Root CA private keys are kept **offline** in highly secured facilities (Hardware Security Modules, physically air-gapped). Intermediate CAs are online and issue certificates on behalf of the root. If an intermediate CA is compromised, it can be revoked without revoking the root (which would invalidate millions of certificates).

**Certificate Chain Verification:**

When a browser connects to `https://www.example.com`:

1. The server sends its end-entity certificate and the intermediate CA certificate(s).
2. The browser verifies: Is the server's certificate signed by the intermediate CA? (Check signature with intermediate CA's public key.)
3. Is the intermediate CA's certificate signed by a trusted root CA? (Check signature with root CA's public key.)
4. Is the root CA in the browser's trust store?
5. Is each certificate within its validity period?
6. Is each certificate not revoked?
7. Does the hostname in the certificate's SAN match the hostname being connected to?

If all checks pass, the certificate is trusted.

***

**PKI Roles and Entities**

| Role                            | Description                                                                                                                   |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Root CA**                     | The ultimate trust anchor; self-signed; offline. Examples: DigiCert Root CA, GlobalSign Root CA, ISRG Root X1 (Let's Encrypt) |
| **Intermediate CA**             | Signs end-entity certificates; its certificate is signed by the root or another intermediate CA                               |
| **Registration Authority (RA)** | Handles identity verification on behalf of the CA; forwards approved requests to the CA for signing                           |
| **End Entity (Subscriber)**     | The server, person, or device that holds the end-entity certificate                                                           |
| **Relying Party**               | The client (browser, application) that validates and trusts certificates                                                      |
| **Certificate Repository**      | A directory (often LDAP or HTTP) where certificates and CRLs are published                                                    |

***

**Certificate Validation Levels**

CAs offer three levels of identity verification:

| Validation Level                 | What is Verified                                               | Certificate Contains                         | Use Case                                                       |
| -------------------------------- | -------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------- |
| **Domain Validation (DV)**       | Requester controls the domain (DNS or HTTP challenge)          | Domain name only                             | General websites, free (Let's Encrypt)                         |
| **Organisation Validation (OV)** | Domain control + organisation identity (business registration) | Domain + organisation name                   | Business websites                                              |
| **Extended Validation (EV)**     | Rigorous legal/physical verification of organisation           | Domain + organisation (with strict criteria) | Banks, e-commerce (green bar, now largely deprecated visually) |

***

**Certificate Revocation**

A certificate may need to be invalidated before its expiry — if the private key is compromised, the organisation ceases to exist, or the certificate was misissued.

**CRL — Certificate Revocation List:**

The CA periodically publishes a **CRL** — a signed list of serial numbers of revoked certificates. Relying parties download the CRL and check if a certificate's serial number appears on it.

**Problems with CRLs:**

* CRLs can grow very large.
* They are published periodically (e.g., daily), so there is a window of risk between revocation and CRL publication.
* CRL servers can become a single point of failure and a bottleneck.

**OCSP — Online Certificate Status Protocol (RFC 6960):**

Instead of downloading a full CRL, the relying party queries an **OCSP responder** with the specific certificate serial number. The responder replies with `good`, `revoked`, or `unknown`.

**Problems with OCSP:**

* Introduces latency on every TLS handshake.
* OCSP responder availability becomes a dependency.
* Privacy concern: the CA learns which certificates are being validated and by whom.

**OCSP Stapling:**

Solves OCSP's problems. The **server** periodically fetches a signed OCSP response from the CA and **staples** it to the TLS handshake. The client receives the OCSP response as part of the handshake — no extra round-trip to the OCSP responder, no privacy leak to the CA.

***

**Certificate Issuance Process**

**For a TLS server certificate:**

1. **Key Generation:** The server generates an RSA or EC key pair.
2. **CSR (Certificate Signing Request):** The server creates a CSR — a self-signed message containing the public key, the requested subject DN/SAN, and the requested key usage. The CSR is signed with the corresponding private key (proving possession).
3. **Submission:** The CSR is submitted to the CA (via web interface or ACME protocol).
4. **Validation:** The CA verifies the requester's identity and control of the domain (DV: HTTP challenge — serve a specific file at `/.well-known/acme-challenge/<token>`; or DNS challenge — create a specific TXT record).
5. **Signing:** The CA signs the public key and subject information with the CA's private key, producing the certificate.
6. **Installation:** The server installs the certificate and configures the web server.

**ACME (Automatic Certificate Management Environment, RFC 8555):** The protocol used by Let's Encrypt to automate certificate issuance and renewal. Tools like Certbot communicate with Let's Encrypt's ACME server to obtain and automatically renew certificates without human intervention.

***

**Web of Trust (PGP Alternative to PKI)**

The hierarchical CA model is not the only approach. **PGP (Pretty Good Privacy)** uses a **Web of Trust**: individuals sign each other's public keys, attesting that they have verified the owner's identity. Trust is transitive — if Alice trusts Bob, and Bob has signed Carol's key, Alice can transitively trust Carol's key.

| Aspect           | CA Hierarchy (PKI)                    | Web of Trust (PGP)                                 |
| ---------------- | ------------------------------------- | -------------------------------------------------- |
| **Trust anchor** | Root CA (centralised)                 | Distributed — multiple personal attestations       |
| **Management**   | Centralised, professional             | Decentralised, community-managed                   |
| **Scalability**  | High                                  | Low — requires key signing parties                 |
| **Failure mode** | Compromise of root CA compromises all | Isolated — only affects signers of compromised key |
| **Use case**     | TLS/HTTPS, email S/MIME, code signing | Personal email encryption (PGP/GPG)                |

***

**Certificate Transparency (CT)**

Even trusted CAs can make mistakes or be coerced into issuing fraudulent certificates (e.g., a certificate for `google.com` issued to a malicious party). **Certificate Transparency (RFC 9162)** is a mechanism to detect such misissuance.

Every publicly trusted certificate must be logged to one or more **CT logs** — append-only, cryptographically verifiable public ledgers. Browsers require a **Signed Certificate Timestamp (SCT)** in every certificate, proving the certificate was submitted to a CT log. If a CA issues a fraudulent certificate, it will appear in the CT log and can be detected by domain owners monitoring for unauthorised certificates for their domain.

Certificate Transparency has been mandatory in Chrome since 2018.

***

### 3. Secure Communication Protocols

#### 3.1 SSL (Secure Sockets Layer)

**Historical Context**

**SSL (Secure Sockets Layer)** was developed by **Netscape** in the mid-1990s to secure HTTP traffic on the early commercial Web. SSL 2.0 (1995) and SSL 3.0 (1996) were the first widely deployed versions. In 1999, the IETF standardised an improved version as **TLS 1.0** (RFC 2246). Despite the name change, "SSL" remained in common usage. Today, all SSL versions and TLS 1.0 and TLS 1.1 are deprecated and broken. The current standards are:

* **TLS 1.2** (RFC 5246, 2008) — widely deployed, secure with correct configuration.
* **TLS 1.3** (RFC 8446, 2018) — the current standard; significantly more secure and faster.

The term "SSL" in modern contexts almost always refers to TLS.

***

**What TLS Provides**

TLS is a transport-layer security protocol that sits between the application layer and TCP, providing three security services:

1. **Confidentiality**: Data is encrypted using a symmetric cipher (negotiated during handshake). A passive eavesdropper sees only ciphertext.
2. **Integrity**: Each record is protected by a MAC (Message Authentication Code) or AEAD tag. Any modification in transit is detected and the connection is aborted.
3. **Authentication**: The server presents a certificate; the client verifies it against trusted CAs. Optionally, the client also presents a certificate (mutual TLS / mTLS).

TLS does **not** hide the fact that communication is taking place, nor the IP addresses of the communicating parties (a VPN or Tor is needed for that).

***

**TLS Protocol Architecture**

TLS is composed of two layers of sub-protocols:

```
+----------------------------------------------+
|  Application Protocol (HTTP, SMTP, etc.)     |
+----------------------------------------------+
|  TLS Record Protocol                         |  <-- Carries all TLS data
|  +------------------+  +------------------+  |
|  |  TLS Handshake   |  |  TLS Alert       |  |
|  |  Protocol        |  |  Protocol        |  |
|  +------------------+  +------------------+  |
|  |  TLS Change      |  |  Application     |  |
|  |  Cipher Spec     |  |  Data Protocol   |  |
|  +------------------+  +------------------+  |
+----------------------------------------------+
|  TCP                                         |
+----------------------------------------------+
```

**TLS Record Protocol:** The foundational layer. All data — handshake messages, alert messages, application data — is transmitted as **TLS records**. Each record has:

* A content type (handshake, alert, application data, change\_cipher\_spec)
* A protocol version
* A length
* The (encrypted) payload

**TLS Handshake Protocol:** Negotiates cipher suites, authenticates the server (and optionally client), and establishes the session keys.

**TLS Alert Protocol:** Communicates error conditions. Alerts are either warnings or fatal errors. A fatal alert terminates the connection immediately.

***

**TLS 1.2 Handshake — Step by Step**

TLS 1.2 requires **2 round trips** (plus the TCP handshake) before application data can flow.

```
Client                                          Server
  |                                                |
  |--- ClientHello -------------------------------->|
  |    - TLS version supported (max = 1.2)         |
  |    - Client random (32 bytes)                  |
  |    - Session ID (for resumption)               |
  |    - Cipher suites supported (ordered list)    |
  |    - Compression methods                       |
  |    - Extensions (SNI, ALPN, supported_groups)  |
  |                                                |
  |<-- ServerHello --------------------------------|
  |    - Chosen TLS version                        |
  |    - Server random (32 bytes)                  |
  |    - Session ID                                |
  |    - Chosen cipher suite                       |
  |    - Chosen compression                        |
  |                                                |
  |<-- Certificate --------------------------------|
  |    - Server's X.509 certificate chain          |
  |                                                |
  |<-- ServerKeyExchange --------------------------| (only for DHE/ECDHE cipher suites)
  |    - DH/ECDH parameters signed by server's key |
  |                                                |
  |<-- ServerHelloDone ----------------------------| (signals end of server messages)
  |                                                |
  |--- ClientKeyExchange ------------------------->|
  |    - Pre-master secret encrypted with server's |
  |      public key (RSA), OR                      |
  |    - Client's DH/ECDH public value             |
  |                                                |
  |--- ChangeCipherSpec -------------------------->|
  |    (signals: switching to negotiated cipher)  |
  |                                                |
  |--- Finished (encrypted) ---------------------->|
  |    - Verification hash of all handshake msgs  |
  |                                                |
  |<-- ChangeCipherSpec ---------------------------|
  |<-- Finished (encrypted) ----------------------|
  |                                                |
  |<----------- Application Data (encrypted) ---->|
```

**Key derivation in TLS 1.2:**

From the `ClientHello` random ($r\_C$), `ServerHello` random ($r\_S$), and the **pre-master secret** (PMS), a **master secret** is derived:

\$$\text{master\_secret} = \text{PRF}(\text{PMS},\ \text{"master secret"},\ r\_C | r\_S)\[0..47]\$$

From the master secret, four keys are derived: client write key, server write key, client write MAC key, server write MAC key. The PRF (Pseudo-Random Function) in TLS 1.2 is HMAC-SHA256 (or HMAC-SHA384 for some cipher suites).

**Cipher Suite Notation:**

A TLS 1.2 cipher suite specifies four algorithms:

```
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
 |    |       |        |       |    |
 |    |       |        |       |    +-- PRF/MAC hash (SHA-384)
 |    |       |        |       +------- Cipher mode (GCM = AEAD)
 |    |       |        +--------------- Cipher and key size (AES-256)
 |    |       +------------------------ Authentication (RSA certificate)
 |    +-------------------------------- Key exchange (ECDHE = ephemeral EC DH)
 +--------------------------------------- Protocol (TLS)
```

***

**TLS 1.3 — The Modern Standard**

TLS 1.3 was designed with a clean-slate security review, eliminating all known weaknesses in TLS 1.2.

**Key improvements over TLS 1.2:**

| Feature                   | TLS 1.2                | TLS 1.3                                                                                  |
| ------------------------- | ---------------------- | ---------------------------------------------------------------------------------------- |
| **Handshake round trips** | 2 RTT                  | 1 RTT (0-RTT resumption possible)                                                        |
| **Key exchange**          | RSA, DHE, ECDHE        | ECDHE only (ephemeral always; PFS mandatory)                                             |
| **Cipher suites**         | \~300+ (many insecure) | 5 (all secure; AEAD only)                                                                |
| **Record encryption**     | Negotiated             | Mandatory from Finished message                                                          |
| **Handshake encryption**  | Only after Finished    | Certificate and parameters encrypted                                                     |
| **Forward secrecy**       | Optional               | Mandatory (only ephemeral key exchange)                                                  |
| **Obsoleted features**    | —                      | RSA key exchange, static DH, RC4, 3DES, CBC mode, SHA-1, MD5, compression, renegotiation |
| **Downgrade protection**  | Partial                | Built-in via random value sentinel                                                       |

**TLS 1.3 Cipher Suites (only five):**

| Cipher Suite                    | AEAD Algorithm    | Hash    |
| ------------------------------- | ----------------- | ------- |
| TLS\_AES\_128\_GCM\_SHA256      | AES-128-GCM       | SHA-256 |
| TLS\_AES\_256\_GCM\_SHA384      | AES-256-GCM       | SHA-384 |
| TLS\_CHACHA20\_POLY1305\_SHA256 | ChaCha20-Poly1305 | SHA-256 |
| TLS\_AES\_128\_CCM\_SHA256      | AES-128-CCM       | SHA-256 |
| TLS\_AES\_128\_CCM\_8\_SHA256   | AES-128-CCM-8     | SHA-256 |

**TLS 1.3 Handshake (simplified):**

```
Client                                          Server
  |                                                |
  |--- ClientHello -------------------------------->|
  |    - Supported versions (include TLS 1.3)      |
  |    - Client random                             |
  |    - Key share (ECDH public value, e.g., X25519)|
  |    - Supported cipher suites                   |
  |                                                |
  |<-- ServerHello --------------------------------|
  |    - TLS 1.3 selected                          |
  |    - Server random                             |
  |    - Server's ECDH public value                |
  |    (server now has shared secret; derives keys)|
  |                                                |
  |<-- {EncryptedExtensions} (encrypted) ----------|
  |<-- {Certificate}         (encrypted) ----------|
  |<-- {CertificateVerify}   (encrypted) ----------|
  |<-- {Finished}            (encrypted) ----------|
  |                                                |
  |--- {Finished} (encrypted) -------------------->|
  |                                                |
  |<----------- Application Data (encrypted) ---->|
```

The server's Certificate, CertificateVerify, and Finished messages are **encrypted** in TLS 1.3 — the certificate is not visible to a passive observer (unlike TLS 1.2 where the certificate was sent in plaintext). This is called **encrypted handshake** or **encrypted SNI** (when combined with Encrypted Client Hello extensions).

**0-RTT (Zero Round Trip) Session Resumption:**

TLS 1.3 allows a client that previously connected to a server to send application data in the **very first message** (0-RTT early data) using a **pre-shared key (PSK)** from the previous session. The server can process this data before the handshake completes.

**Limitation:** 0-RTT data is susceptible to **replay attacks** — an attacker can retransmit the 0-RTT data to the server. Servers must only use 0-RTT for idempotent requests (e.g., HTTP GET but not POST with side effects).

***

**Server Name Indication (SNI)**

TLS is typically established before the HTTP Host header is sent. On a server hosting multiple HTTPS virtual hosts, how does the server know which certificate to present? **SNI** (an extension in the TLS ClientHello) allows the client to specify the target hostname during the handshake, before the server has sent any certificate.

Without SNI, a server with multiple HTTPS virtual hosts would require a separate IP address per hostname. SNI is now ubiquitous — all modern clients and servers support it.

**Privacy note:** In TLS 1.2, SNI is sent in plaintext — an eavesdropper knows which hostname the client is connecting to. **Encrypted Client Hello (ECH)** is a TLS extension (in development, based on HPKE) that encrypts the entire ClientHello, including SNI.

***

**Mutual TLS (mTLS)**

In standard TLS, only the **server** presents a certificate. **Mutual TLS (mTLS)** requires the **client** to also present a certificate, authenticating itself to the server. The server verifies the client certificate against its trusted CA list.

mTLS is used in:

* Microservices architectures (service-to-service authentication within a cluster).
* API authentication (client certificates instead of passwords or API keys).
* Zero Trust networks (devices must present certificates to access resources).

***

**TLS Record Structure**

```
+---------------+-------------------+---------+-----------+
| Content Type  | Protocol Version  | Length  |  Payload  |
| (1 byte)      | (2 bytes)         | (2 bytes)| (variable)|
+---------------+-------------------+---------+-----------+
```

Content types: `20` (change\_cipher\_spec), `21` (alert), `22` (handshake), `23` (application\_data), `24` (heartbeat).

In TLS 1.3, content types in encrypted records are **hidden** inside the encrypted payload — all encrypted records appear as `application_data` (type 23) to an observer, preventing traffic analysis based on content type.

#### 3.2 Internet Security Protocols

**Overview**

TLS secures the transport layer between two applications. The Internet requires security at multiple layers, for different use cases:

| Protocol                | Layer               | Purpose                                                   |
| ----------------------- | ------------------- | --------------------------------------------------------- |
| **IPsec**               | Network (Layer 3)   | Secures IP packets; used in VPNs and site-to-site tunnels |
| **PGP / S/MIME**        | Application         | Secures email end-to-end                                  |
| **SSH**                 | Application         | Secure remote login and file transfer                     |
| **DNSSEC**              | Application (DNS)   | Authenticates DNS responses; prevents cache poisoning     |
| **IEEE 802.11i (WPA3)** | Data Link (Layer 2) | Secures wireless LAN frames                               |
| **Kerberos**            | Application         | Network authentication in enterprise environments         |

***

**IPsec — IP Security**

**IPsec** (RFC 4301) is a suite of protocols that operates at the **network layer**, securing all IP traffic between two endpoints. Unlike TLS (which operates within a single application), IPsec is transparent to applications — any application's traffic is protected without modification.

IPsec provides:

* **Confidentiality** (via encryption)
* **Integrity** and **authentication** (via cryptographic checksums)
* **Anti-replay protection** (via sequence numbers)

**IPsec operates in two modes:**

**Transport Mode:**

* Only the IP payload (transport layer and above) is protected.
* The original IP header is retained and visible.
* Used for **host-to-host** communication.

```
Original:  [IP Header | TCP Header | Data]
Transport: [IP Header | IPsec Header | Encrypted(TCP Header | Data)]
```

**Tunnel Mode:**

* The **entire original IP packet** (header + payload) is encapsulated inside a new IP packet with a new IP header.
* Used for **VPN gateways** (site-to-site VPN). The original packet's source and destination are hidden — only the VPN gateway addresses appear in the outer header.

```
Original:  [IP Header | TCP Header | Data]
Tunnel:    [New IP Header | IPsec Header | Encrypted(IP Header | TCP Header | Data)]
```

***

**IPsec Protocols — AH and ESP**

**AH — Authentication Header (Protocol 51):**

Provides **integrity and authentication** for the IP packet (including parts of the IP header), but **no confidentiality**. The AH covers the IP header (excluding mutable fields like TTL), AH header, and payload. Because it includes the IP header, AH is **incompatible with NAT** (NAT changes the IP header, breaking the AH authentication check).

**ESP — Encapsulating Security Payload (Protocol 50):**

Provides **confidentiality, integrity, and authentication** for the payload. ESP does not cover the outer IP header, making it **NAT-compatible**. ESP is the standard choice in practice — AH is rarely used.

**ESP structure:**

```
+----------+--------+----------+-----------+-----------+----------+
| IP Header| ESP Hdr| Encrypted |   ESP     | ESP Auth  | (new IP) |
|          |        | Payload   |  Trailer  |   Data    |  (tunnel)|
+----------+--------+----------+-----------+-----------+----------+
            <--- encrypted  -------->       <-- HMAC -->
```

***

**IKE — Internet Key Exchange**

IPsec requires the establishment and management of **Security Associations (SAs)** — shared state (keys, algorithms, lifetimes) that defines how traffic between two endpoints is protected. **IKE (Internet Key Exchange)** is the protocol that negotiates SAs automatically.

**IKEv2** (RFC 7296) is the current version.

**Security Association (SA):**

An SA is a one-directional logical connection defining:

* The IPsec protocol (AH or ESP)
* The encryption and authentication algorithms
* The session keys
* The SA lifetime (time or bytes)
* The **SPI (Security Parameter Index)** — a 32-bit identifier that tells the receiver which SA to use for this packet

A bidirectional IPsec connection requires **two SAs** (one in each direction).

**IKEv2 Exchange (simplified):**

```
Initiator                                        Responder
    |                                                 |
    |--- IKE_SA_INIT (DH public value, nonce) ------->|
    |<-- IKE_SA_INIT (DH public value, nonce) --------|
    |   (Both sides compute shared secret; IKE SA established)
    |                                                 |
    |--- IKE_AUTH (Identity, Certificate, AUTH) ------>|
    |    (All encrypted using IKE SA keys)            |
    |<-- IKE_AUTH (Identity, Certificate, AUTH) -------|
    |   (Child SA / IPsec SA negotiated)              |
    |                                                 |
    |<== IPsec protected traffic (AH or ESP) ========>|
```

IKEv2 uses **ECDHE or DH** for the key exchange (providing PFS with ephemeral keys), followed by mutual authentication via certificates or pre-shared keys.

***

**PGP — Pretty Good Privacy**

**PGP** is an application-layer protocol for **end-to-end encryption and digital signing of email** (and files). It was created by Phil Zimmermann in 1991. **OpenPGP** (RFC 4880) is the open standard; **GPG (GNU Privacy Guard)** is the most widely used open-source implementation.

**PGP Email Encryption — How it works:**

```
Sender Alice                                         Receiver Bob
   |                                                      |
   | 1. Generate random session key K_s                   |
   | 2. Encrypt message with K_s using AES-256:           |
   |    C_msg = AES-256(K_s, message)                     |
   | 3. Encrypt K_s with Bob's RSA public key:            |
   |    C_key = RSA_encrypt(K_pub_Bob, K_s)               |
   | 4. Sign hash of message with Alice's private key:    |
   |    σ = RSA_sign(K_priv_Alice, SHA-256(message))      |
   |                                                      |
   |--- Send: C_msg || C_key || σ  ---------------------->|
   |                                                      |
   |    1. Decrypt K_s:                                   |
   |       K_s = RSA_decrypt(K_priv_Bob, C_key)           |
   |    2. Decrypt message:                               |
   |       message = AES-256_decrypt(K_s, C_msg)          |
   |    3. Verify signature:                              |
   |       RSA_verify(K_pub_Alice, SHA-256(message), σ)   |
```

PGP uses **hybrid encryption** — symmetric encryption for the message body (fast) and asymmetric encryption only for the session key (slow but small).

**PGP Key Fingerprint:**

A short digest of the public key used for identification and verification:

```
pub   4096R/0xABCD1234 2024-01-15
uid   Alice Smith <alice@example.com>
Fingerprint = A1B2 C3D4 E5F6 7890 ABCD  EF12 3456 7890 ABCD 1234
```

***

**S/MIME — Secure/Multipurpose Internet Mail Extensions**

**S/MIME** (RFC 5751) is the alternative to PGP for email security, using **X.509 certificates** (same as TLS) rather than PGP's web of trust. S/MIME is widely supported in enterprise email clients (Microsoft Outlook, Apple Mail).

| Feature               | PGP / OpenPGP                   | S/MIME                  |
| --------------------- | ------------------------------- | ----------------------- |
| **Certificate model** | Web of trust                    | PKI (CA-issued X.509)   |
| **Key distribution**  | Key servers, manual exchange    | CA infrastructure       |
| **Corporate support** | Poor                            | Excellent               |
| **Standard body**     | IETF (OpenPGP RFC)              | IETF / PKIX             |
| **Client support**    | Requires plugin in most clients | Native in Outlook, Mail |

***

**DNSSEC — DNS Security Extensions**

Standard DNS provides no authentication — responses can be forged, enabling **DNS cache poisoning** (attacker injects false records into a resolver's cache, redirecting users to malicious sites). **DNSSEC** (RFC 4033–4035) adds **digital signatures** to DNS records.

**How DNSSEC works:**

1. Zone administrators generate a **Zone Signing Key (ZSK)** pair and a **Key Signing Key (KSK)** pair.
2. Each DNS record set (RRset) is signed with the private ZSK, producing an **RRSIG** record.
3. The public ZSK is published in a **DNSKEY** record in the zone.
4. The DNSKEY record is signed with the private KSK, producing another RRSIG.
5. The hash of the public KSK is submitted to the parent zone as a **DS (Delegation Signer)** record — establishing the chain of trust from parent to child zone.
6. The parent zone signs the DS record with its ZSK, chaining up to the root zone.

**Validating resolver operation:**

```
Resolver receives: RRset + RRSIG
   |
   | Fetch DNSKEY (public ZSK) for the zone
   | Verify: RRSIG is a valid signature over RRset using ZSK
   | Fetch DS record from parent zone
   | Verify: DS matches hash of ZSK's DNSKEY
   | Chain up to root (which is anchored in resolver's configuration)
   |
   v
If all checks pass → authenticated response (AD bit set)
```

**DNSSEC record types:**

| Record Type                | Purpose                                                                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **DNSKEY**                 | Contains the public key (ZSK or KSK) for the zone                                                                                 |
| **RRSIG**                  | Digital signature over a DNS RRset; tied to a specific DNSKEY                                                                     |
| **DS (Delegation Signer)** | Hash of a child zone's KSK DNSKEY; stored in parent zone to chain trust                                                           |
| **NSEC / NSEC3**           | Authenticated denial of existence — proves a queried name does not exist without leaking all zone names (NSEC3 uses hashed names) |

**DNSSEC limitations:**

* DNSSEC does not encrypt DNS traffic — it only authenticates it. DNS content is still visible to observers.
* **DNS-over-HTTPS (DoH, RFC 8484)** and **DNS-over-TLS (DoT, RFC 7858)** encrypt DNS queries and responses for confidentiality and resistance to tampering, but do not provide DNSSEC-style chain-of-trust authentication.

***

**Kerberos — Network Authentication**

**Kerberos** (RFC 4120) is a **symmetric key-based network authentication protocol** developed at MIT. It is the primary authentication mechanism in **Microsoft Active Directory** environments and in large enterprise networks.

**Core concept:** Kerberos avoids sending passwords over the network. Instead, it uses a **trusted third party — the Key Distribution Centre (KDC)** — to issue time-limited cryptographic tickets.

**Kerberos Components:**

| Component                         | Role                                                               |
| --------------------------------- | ------------------------------------------------------------------ |
| **Client**                        | The user/service requesting access                                 |
| **KDC (Key Distribution Centre)** | Contains two services: AS and TGS                                  |
| **AS (Authentication Server)**    | Authenticates the client's identity; issues Ticket Granting Ticket |
| **TGS (Ticket Granting Server)**  | Issues service tickets in exchange for a valid TGT                 |
| **Service Server (SS)**           | The resource the client wants to access                            |

**Kerberos Authentication Flow:**

```
Client            AS (Authentication Server)       TGS              Service Server
  |                        |                        |                     |
  |-- AS_REQ (username) -->|                        |                     |
  |                        | (lookup client's key)  |                     |
  |<-- AS_REP -------------|                        |                     |
  |   TGT (encrypted with  |                        |                     |
  |   TGS's key)           |                        |                     |
  |   Session Key K_c-tgs  |                        |                     |
  |   (encrypted with      |                        |                     |
  |   client's key)        |                        |                     |
  |                        |                        |                     |
  | [Client decrypts AS_REP using its own key]      |                     |
  |                        |                        |                     |
  |-- TGS_REQ (TGT + Authenticator, service name)->|                     |
  |                        |         [TGS verifies TGT, authenticator]   |
  |<-- TGS_REP (Service Ticket encrypted with SS key, K_c-ss) ----------|
  |                        |                        |                     |
  |-- AP_REQ (Service Ticket + Authenticator) ---------------------------->|
  |                                [SS verifies ticket and authenticator]  |
  |<-- AP_REP (optional: mutual authentication) ---------------------------|
  |                                                                        |
  |<========================= Service Data ================================>|
```

**Key mechanisms:**

* **TGT (Ticket Granting Ticket)**: After authenticating to the AS, the client receives a TGT — a ticket it can use to request service tickets without re-entering its password. TGTs have a limited lifetime (default 10 hours in Active Directory).
* **Authenticator**: A message the client constructs, containing a timestamp encrypted with the session key, proving the client is the legitimate owner of the ticket (prevents replay of stolen tickets).
* **Timestamps**: Kerberos requires client clocks to be within 5 minutes of the KDC's clock. This is why Kerberos environments use NTP for time synchronisation — clock skew beyond 5 minutes prevents authentication.

**Kerberos limitations:**

* The KDC is a **single point of failure** (mitigated by redundant KDC replicas).
* All security depends on the secrecy of the KDC's keys.
* **Pass-the-ticket** and **Golden Ticket** attacks: an attacker who compromises the KDC's Kerberos database master key can forge arbitrary tickets — a catastrophic compromise.

***

**IEEE 802.11i — Wireless LAN Security (WPA2/WPA3)**

The original IEEE 802.11 wireless standard (1997) had WEP (Wired Equivalent Privacy) for security — which was fundamentally broken by 2001 due to weak IV handling in RC4. The IEEE 802.11i amendment (2004) introduced robust wireless security, marketed as **WPA2**.

**WPA2 (IEEE 802.11i) Key Features:**

* **CCMP (Counter Mode CBC-MAC Protocol)**: AES-128 in CCM mode — provides both confidentiality (CTR mode) and integrity (CBC-MAC). Replaced the broken WEP and WPA/TKIP.
* **4-Way Handshake**: After association, the client and AP derive a **PTK (Pairwise Transient Key)** from the **PMK (Pairwise Master Key)**, both parties' MAC addresses, and fresh nonces. The PTK is used for all unicast traffic.
* **GTK (Group Temporal Key)**: Used to encrypt multicast and broadcast traffic. Distributed to all associated clients encrypted under their respective PTKs.

**WPA2 Authentication Modes:**

| Mode                             | Use Case           | How PMK is Derived                                                                                                    |
| -------------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **WPA2-Personal (PSK)**          | Home, small office | PMK derived from passphrase using PBKDF2: $\text{PMK} = \text{PBKDF2}(\text{HMAC-SHA1, passphrase, SSID, 4096, 256})$ |
| **WPA2-Enterprise (802.1X/EAP)** | Corporate networks | Client authenticates to a RADIUS server via EAP; server and client derive PMK using EAP keying material               |

**WPA3 (2018) improvements:**

| Feature                     | WPA2                                                       | WPA3                                                                                                       |
| --------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Key exchange (Personal)** | PSK (4-way handshake; offline dictionary attacks possible) | SAE (Simultaneous Authentication of Equals) — Dragonfly handshake; resistant to offline dictionary attacks |
| **Forward secrecy**         | No                                                         | Yes (SAE provides PFS)                                                                                     |
| **Enterprise security**     | 128-bit minimum                                            | 192-bit minimum (Suite B: ECDHE, ECDSA, AES-256-GCM, SHA-384)                                              |
| **Open network protection** | No encryption on open networks                             | OWE (Opportunistic Wireless Encryption) — unauthenticated but encrypted                                    |

**SAE (Simultaneous Authentication of Equals):** A password-authenticated key agreement protocol based on the Dragonfly handshake. Both sides prove knowledge of the password and derive a fresh PMK without ever transmitting the password or information that would allow an offline dictionary attack, even if all handshake messages are captured.

**Summary: Security Protocols at Each Layer**

| Layer       | Protocol           | Protects                     | Mechanism                                |
| ----------- | ------------------ | ---------------------------- | ---------------------------------------- |
| Application | PGP / S/MIME       | Email content                | Hybrid encryption + digital signature    |
| Application | SSH                | Remote access, file transfer | Asymmetric auth + symmetric encryption   |
| Application | HTTPS (HTTP + TLS) | Web traffic                  | TLS (ECDHE + AES-GCM + certificate auth) |
| Application | DNSSEC             | DNS integrity                | Digital signatures on DNS records        |
| Application | Kerberos           | Network authentication       | Symmetric key tickets via trusted KDC    |
| Transport   | TLS / DTLS         | Any TCP/UDP stream           | Handshake + AEAD symmetric encryption    |
| Network     | IPsec (AH/ESP)     | All IP traffic               | IKEv2 + AES-GCM / HMAC                   |
| Data Link   | WPA2/WPA3          | Wi-Fi frames                 | CCMP (AES) / SAE                         |
