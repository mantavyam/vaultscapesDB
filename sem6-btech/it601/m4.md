### 1. Domain Name System (DNS)

#### 1.1 Domain Name Space

**Why Names Instead of Addresses?**

Every device on the Internet is identified by a numeric IP address (e.g., `142.250.64.78`). While routers and machines work exclusively with these numbers, humans find it far easier to remember symbolic names like `www.google.com`. The **Domain Name System (DNS)** is the globally distributed mechanism that maps human-readable names to IP addresses and vice versa. It is defined in RFC 1034 and RFC 1035.

DNS is not a single server — it is a distributed, hierarchical database spread across tens of thousands of servers worldwide. No single machine holds all mappings; instead, the database is partitioned into zones, and each zone is managed by an authoritative server.

***

**Structure of the Domain Name Space**

The domain name space is organised as an **inverted tree** (root at the top, leaves at the bottom). Each node in the tree has a **label** — a string of at most 63 characters. The full name of any node is called its **Fully Qualified Domain Name (FQDN)** and is formed by concatenating all labels from the node up to the root, separated by dots.

```
                          . (root)
                          |
        +---------+-------+---------+---------+
        |         |                 |         |
       com       edu               org        net
        |         |                 |
     google     mit              wikipedia
        |         |
       www      www
```

* The **root** is an unnamed node represented by a single dot (`.`).
* **Top-Level Domains (TLDs)** are immediately below the root.
* **Second-level domains** are registered by organisations (e.g., `google` under `com`).
* **Subdomains** extend further (e.g., `www`, `mail`, `ftp`).

An FQDN always ends with a dot representing the root, though this trailing dot is usually omitted in everyday use:

```
www.google.com.   <-- FQDN (trailing dot = root)
www.google.com    <-- common notation (implied root)
```

The maximum length of a complete domain name is **255 characters**.

***

**Types of Top-Level Domains (TLDs)**

| TLD Category                   | Description                                               | Examples                                       |
| ------------------------------ | --------------------------------------------------------- | ---------------------------------------------- |
| **Generic TLDs (gTLDs)**       | Originally restricted to specific organisations; now open | `.com`, `.org`, `.net`, `.edu`, `.gov`, `.mil` |
| **Country-Code TLDs (ccTLDs)** | Two-letter codes assigned per ISO 3166-1 country standard | `.in` (India), `.uk` (UK), `.jp` (Japan)       |
| **New gTLDs**                  | Introduced post-2012; over 1,200 approved                 | `.app`, `.blog`, `.bank`, `.shop`              |
| **Infrastructure TLD**         | Reserved by IANA for technical use                        | `.arpa` (used for reverse DNS)                 |

***

**Domain Names — Rules and Conventions**

* Labels are case-insensitive: `Google.COM` is the same as `google.com`.
* Labels may contain letters, digits, and hyphens, but must not start or end with a hyphen.
* Each label is at most 63 characters.
* The full domain name is at most 255 characters including dots.

***

**Zones and Delegation**

The domain name space is divided into non-overlapping **zones**. A zone is a contiguous portion of the tree that is administered by a particular entity. When an organisation owns a domain, it is responsible for maintaining the zone file for that domain.

**Delegation** is the process by which a parent zone grants authority over a subtree to a child zone. For example, ICANN delegates `.com` to Verisign, which in turn allows organisations to register second-level domains. Once `google.com` is registered, Google itself becomes authoritative for everything under `google.com`.

```
Zone: root (.)
  Delegates: .com, .org, .net, .edu, ...

Zone: .com
  Delegates: google.com, amazon.com, ...

Zone: google.com
  Maintains: www.google.com, mail.google.com, ...
```

Each zone must have at least:

* A **primary (master) name server** — holds the original, editable copy of the zone file.
* One or more **secondary (slave) name servers** — hold read-only copies obtained from the primary via **zone transfer**. These provide redundancy and load distribution.

***

**Resource Records (RRs)**

The zone file stores **resource records**. Each RR has the format:

```
Name    TTL    Class    Type    RData
```

| Field     | Meaning                                                           |
| --------- | ----------------------------------------------------------------- |
| **Name**  | Domain name this record applies to                                |
| **TTL**   | Time-To-Live in seconds; how long resolvers may cache this record |
| **Class** | Network class; almost always `IN` (Internet)                      |
| **Type**  | Record type (A, AAAA, MX, etc.)                                   |
| **RData** | The actual data; format depends on Type                           |

**Common DNS Record Types:**

| Type      | Full Name          | Purpose                                                 | Example RData                               |
| --------- | ------------------ | ------------------------------------------------------- | ------------------------------------------- |
| **A**     | Address            | Maps hostname to IPv4 address                           | `142.250.64.78`                             |
| **AAAA**  | IPv6 Address       | Maps hostname to IPv6 address                           | `2607:f8b0:4004::200e`                      |
| **CNAME** | Canonical Name     | Alias; points one name to another                       | `www` → `webserver.google.com`              |
| **MX**    | Mail Exchange      | Identifies mail server for a domain                     | Priority + `smtp.google.com`                |
| **NS**    | Name Server        | Identifies authoritative name servers for a zone        | `ns1.google.com`                            |
| **PTR**   | Pointer            | Reverse DNS; maps IP to hostname                        | Used in `.arpa` zones                       |
| **SOA**   | Start of Authority | Contains metadata about the zone                        | Serial, refresh, retry, expire, minimum TTL |
| **TXT**   | Text               | Arbitrary text; used for SPF, DKIM, domain verification | `"v=spf1 include:..."`                      |
| **SRV**   | Service            | Locates services by protocol and domain                 | Used by SIP, XMPP                           |

**Example SOA Record:**

```
google.com.   IN   SOA   ns1.google.com.   dns-admin.google.com. (
                          2024010101   ; Serial number
                          3600         ; Refresh (1 hour)
                          900          ; Retry (15 min)
                          604800       ; Expire (1 week)
                          300 )        ; Minimum TTL (5 min)
```

* **Serial**: Version number of the zone file; secondary servers compare this to detect updates.
* **Refresh**: How often secondaries check the primary for updates.
* **Retry**: How long a secondary waits before retrying a failed refresh.
* **Expire**: If a secondary cannot contact the primary for this duration, it stops serving the zone.
* **Minimum TTL**: Default TTL for records in the zone; also the negative caching TTL (RFC 2308).

#### 1.2 DNS in the Internet

**DNS as a Distributed System**

DNS operates as a **client-server application**. The client side is called a **resolver** — a library or daemon running on every internet-connected host. When an application (e.g., a browser) needs to resolve `www.example.com`, it calls the resolver, which queries DNS servers on the application's behalf and returns an IP address.

DNS queries and responses are typically carried over **UDP port 53** for performance (short, single-packet exchanges). **TCP port 53** is used when:

* The response exceeds 512 bytes (traditional limit; raised to 4096 bytes by EDNS0).
* Zone transfers occur between primary and secondary name servers.

***

**Hierarchy of DNS Servers**

DNS servers are organised into three levels:

**1. Root Name Servers**

There are **13 logical root name server addresses** (labelled `a.root-servers.net` through `m.root-servers.net`), operated by 12 independent organisations. In reality, these 13 addresses are served by hundreds of physical machines worldwide using **anycast routing** — a query reaches the nearest physical instance automatically.

Root servers know nothing about individual domain names. They know only which servers are authoritative for each TLD.

**2. TLD Name Servers**

These are authoritative for top-level domains. For example, Verisign operates the TLD servers for `.com` and `.net`. A TLD server knows which name servers are authoritative for each second-level domain registered under that TLD.

**3. Authoritative Name Servers**

These are the servers that hold the actual DNS records for a domain. Every domain must have at least two authoritative name servers for redundancy. These servers provide the final, definitive answers to queries.

**4. Local (Recursive) Resolver**

This is not part of the DNS hierarchy per se, but is the first point of contact for clients. Also called a **recursive resolver** or **full-service resolver**. It is typically operated by an ISP, a company's IT department, or a public DNS provider (e.g., Google's `8.8.8.8`, Cloudflare's `1.1.1.1`).

***

**DNS Resolution — Step-by-Step**

There are two modes of resolution:

**Recursive Query:** The client asks a resolver to do all the work and return a complete answer. The resolver accepts full responsibility.

**Iterative Query:** The server, instead of doing the full lookup, returns a referral — a pointer to another server that might know more. The resolver must follow each referral itself.

In practice: the **client always sends a recursive query to its local resolver**. The local resolver then typically performs **iterative queries** to the DNS hierarchy.

**Example: Resolving `www.cs.mit.edu`**

```
Client                Local Resolver        Root Server       .edu TLD Server     mit.edu Auth Server
  |                        |                     |                   |                    |
  |--- recursive query --->|                     |                   |                    |
  |   "www.cs.mit.edu?"    |                     |                   |                    |
  |                        |--- iterative query->|                   |                    |
  |                        |   "www.cs.mit.edu?" |                   |                    |
  |                        |<-- referral --------|                   |                    |
  |                        |   "Ask .edu TLD at ns1.edu"            |                    |
  |                        |--- iterative query ---------------------->|                  |
  |                        |   "www.cs.mit.edu?"                    |                    |
  |                        |<-- referral -----------------------------|                   |
  |                        |   "Ask mit.edu auth at ns1.mit.edu"    |                    |
  |                        |--- iterative query ------------------------------------------->|
  |                        |   "www.cs.mit.edu?"                                         |
  |                        |<-- answer (A record: 18.9.22.69) -----------------------------|
  |<--- answer ------------|                     |                   |                    |
  |   "18.9.22.69"         |                     |                   |                    |
```

**Step-by-step breakdown:**

1. The application calls `getaddrinfo("www.cs.mit.edu")` (or similar system call).
2. The **local resolver** checks its **cache**. If the record is cached and the TTL has not expired, it returns immediately.
3. If not cached, the local resolver queries a **root name server**: "Who is authoritative for `www.cs.mit.edu`?"
4. The root server responds with a referral: "I don't know, but here are the `.edu` TLD servers."
5. The local resolver queries the **`.edu` TLD server**: "Who is authoritative for `cs.mit.edu`?"
6. The TLD server responds with a referral: "Here are the authoritative servers for `mit.edu`."
7. The local resolver queries the **`mit.edu` authoritative server**: "What is the IP address of `www.cs.mit.edu`?"
8. The authoritative server returns the **A record**: `18.9.22.69`.
9. The local resolver **caches** this result (for the duration of the TTL) and returns it to the client.

***

**DNS Caching**

Caching is fundamental to DNS performance and scalability. Without caching, every single hostname lookup would require traversing the full hierarchy from root to authoritative server — generating enormous load on root and TLD servers.

* Every DNS record carries a **TTL (Time-To-Live)** value in seconds.
* When a resolver caches a record, it starts a countdown from the TTL.
* Once TTL reaches zero, the record is considered **stale** and must be re-fetched.
* **Negative caching** (RFC 2308): If a name does not exist (NXDOMAIN response), that negative result is also cached for the SOA's minimum TTL, preventing repeated lookups for non-existent names.

**TTL trade-off:**

| Short TTL                        | Long TTL                      |
| -------------------------------- | ----------------------------- |
| Changes propagate quickly        | Changes propagate slowly      |
| More DNS queries, higher load    | Fewer DNS queries, lower load |
| Good for frequently-changing IPs | Good for stable servers       |

***

**Reverse DNS Lookup**

While forward DNS maps name → IP, **reverse DNS** maps IP → name. This is accomplished using the special domain `.in-addr.arpa` for IPv4 and `.ip6.arpa` for IPv6.

For the IP address `18.9.22.69`, the reverse lookup queries:

```
69.22.9.18.in-addr.arpa
```

The octets are reversed so that the DNS hierarchy can delegate in the same left-to-right manner (least specific to most specific). A **PTR record** at that address returns the hostname.

This is used in email spam filtering, logging, and network diagnostics.

***

**DNS Message Format**

Every DNS query and response uses the same message structure:

```
+-----------------------------+
|         Header (12 bytes)   |
+-----------------------------+
|         Question Section    |
+-----------------------------+
|         Answer Section      |
+-----------------------------+
|         Authority Section   |
+-----------------------------+
|         Additional Section  |
+-----------------------------+
```

**Header fields (key ones):**

| Field       | Size    | Meaning                                                  |
| ----------- | ------- | -------------------------------------------------------- |
| **ID**      | 16 bits | Matches a response to its query                          |
| **QR**      | 1 bit   | 0 = Query, 1 = Response                                  |
| **OPCODE**  | 4 bits  | Type of query (0 = standard)                             |
| **AA**      | 1 bit   | Authoritative Answer flag                                |
| **TC**      | 1 bit   | TrunCation flag (message was truncated)                  |
| **RD**      | 1 bit   | Recursion Desired (client requests recursive resolution) |
| **RA**      | 1 bit   | Recursion Available (server supports recursion)          |
| **RCODE**   | 4 bits  | Response code (0=OK, 3=NXDOMAIN, 2=SERVFAIL)             |
| **QDCOUNT** | 16 bits | Number of questions                                      |
| **ANCOUNT** | 16 bits | Number of answer RRs                                     |
| **NSCOUNT** | 16 bits | Number of authority RRs                                  |
| **ARCOUNT** | 16 bits | Number of additional RRs                                 |

***

**DNS Security — DNSSEC**

Standard DNS is vulnerable to **cache poisoning** (an attacker injects false records into a resolver's cache, redirecting traffic). **DNSSEC (DNS Security Extensions)** addresses this by adding **digital signatures** to DNS records.

* Each zone signs its records with a private key.
* Resolvers verify signatures using the corresponding public key, which is itself signed by the parent zone — creating a **chain of trust** from the root down.
* DNSSEC does **not** encrypt DNS traffic (it only authenticates it). DNS-over-HTTPS (DoH) and DNS-over-TLS (DoT) provide confidentiality.

### 2. Web and Browsing

#### 2.1 World Wide Web (WWW)

**What is the World Wide Web?**

The **World Wide Web (WWW)** is a distributed, hypermedia information system that operates on top of the Internet. It was invented by **Tim Berners-Lee** at CERN in 1989 and made publicly available in 1991. The Web is not the Internet itself — the Internet is the underlying network infrastructure (cables, routers, protocols), while the Web is one application built on top of it.

The Web is built on three foundational technologies:

1. **HTML (HyperText Markup Language)** — the format for encoding and presenting content.
2. **HTTP (HyperText Transfer Protocol)** — the application-layer protocol for transferring web content.
3. **URL (Uniform Resource Locator)** — the addressing scheme for identifying resources on the Web.

***

**Key Concepts**

**Hypertext and Hypermedia**

A **hypertext** document contains **links** (hyperlinks) to other documents. Clicking a link causes the browser to retrieve the linked resource. When links connect not just text but also images, audio, video, and other media, the system is called **hypermedia**. The Web is a hypermedia system.

**Web Page and Web Site**

* A **web page** is a single document, typically written in HTML, identified by a unique URL.
* A **website** is a collection of related web pages served from the same domain.
* The **home page** or **index page** is the default document returned when a domain is accessed without specifying a specific resource path.

***

**URL — Uniform Resource Locator**

A URL is the address of a resource on the Web. Its general syntax is:

```
scheme://host[:port]/path[?query][#fragment]
```

| Component    | Description                                               | Example                        |
| ------------ | --------------------------------------------------------- | ------------------------------ |
| **scheme**   | Protocol to use                                           | `https`, `http`, `ftp`         |
| **host**     | Domain name or IP of the server                           | `www.example.com`              |
| **port**     | TCP port (optional; defaults: 80 for HTTP, 443 for HTTPS) | `:8080`                        |
| **path**     | Resource path on the server                               | `/courses/networks/notes.html` |
| **query**    | Key-value pairs passed to the server                      | `?page=2&lang=en`              |
| **fragment** | In-page anchor (processed by browser, not sent to server) | `#section3`                    |

**Example:**

```
https://www.cs.mit.edu:443/courses/notes.html?topic=dns#intro
  |       |               |   |                  |        |
scheme   host            port path               query  fragment
```

The **URI (Uniform Resource Identifier)** is the broader concept that includes URLs (which locate resources) and URNs (which name resources without specifying location). In common usage, URL and URI are often used interchangeably.

***

**Evolution of the Web**

| Generation  | Name                       | Characteristics                                                          |
| ----------- | -------------------------- | ------------------------------------------------------------------------ |
| **Web 1.0** | Static Web                 | Read-only; static HTML pages; no user interaction                        |
| **Web 2.0** | Social/Dynamic Web         | User-generated content; social media; AJAX; blogs, wikis                 |
| **Web 3.0** | Semantic/Decentralised Web | Machine-readable data; AI integration; blockchain-based decentralisation |

***

**How the Web Works — End-to-End Flow**

When a user types `https://www.example.com/index.html` into a browser:

1. **DNS Resolution**: The browser resolves `www.example.com` to an IP address via the DNS system.
2. **TCP Connection**: The browser opens a TCP connection to the server's IP on port 443 (HTTPS).
3. **TLS Handshake**: A TLS session is established for encryption (for HTTPS).
4. **HTTP Request**: The browser sends an HTTP GET request for `/index.html`.
5. **HTTP Response**: The server returns the HTML file with status code `200 OK`.
6. **Parsing and Rendering**: The browser parses the HTML, discovers linked resources (CSS, JS, images), and sends additional HTTP requests for each.
7. **Page Display**: After all resources are loaded, the browser renders and displays the complete page.

#### 2.2 Web Server

**Definition**

A **web server** is software (and the machine running it) that accepts HTTP/HTTPS requests from clients and returns HTTP responses, typically containing web content (HTML pages, images, CSS, JavaScript files, or data from dynamic applications).

Prominent web server software includes:

* **Apache HTTP Server** — open-source, module-based, widely used.
* **Nginx** — event-driven, high-performance; used both as a web server and a reverse proxy.
* **Microsoft IIS (Internet Information Services)** — Windows-native.
* **LiteSpeed** — commercial; known for speed and cPanel compatibility.

***

**Core Functions of a Web Server**

1. **Listen** on a TCP port (default 80 for HTTP, 443 for HTTPS) for incoming connections.
2. **Accept** the TCP connection from the client.
3. **Parse** the incoming HTTP request (method, URL, headers, body).
4. **Locate** the requested resource — either a static file from disk or the output of a dynamic application (CGI script, PHP, Node.js, etc.).
5. **Construct** an HTTP response (status line, headers, body).
6. **Send** the response back over the TCP connection.
7. **Log** the request and response for auditing and analysis.

***

**Static vs. Dynamic Content**

| Aspect           | Static Content                       | Dynamic Content                                          |
| ---------------- | ------------------------------------ | -------------------------------------------------------- |
| **What it is**   | Pre-existing files served as-is      | Content generated at request time                        |
| **Examples**     | `.html`, `.css`, `.jpg`, `.js` files | Database-driven pages, user dashboards                   |
| **Processing**   | Direct file read from disk           | Execution of server-side code                            |
| **Performance**  | Very fast; easily cacheable          | Slower; caching requires care                            |
| **Technologies** | Pure HTML/CSS/JS                     | PHP, Python (Django/Flask), Node.js, Ruby on Rails, Java |

***

**Concurrency Models**

A busy web server must handle many simultaneous connections. The main approaches are:

* **Process-per-request (forking)**: A new OS process is created for each request. Simple but expensive in memory and process-creation overhead. Used by older CGI.
* **Thread-per-request**: A new thread handles each request. Lighter than processes but still limited by thread count. Used by older Apache (prefork + worker MPMs).
* **Event-driven / non-blocking I/O**: A single thread (or small thread pool) handles thousands of connections using an event loop. Waiting for I/O does not block other connections. Used by Nginx and Node.js. Highly efficient for I/O-bound workloads.

***

**Virtual Hosting**

A single web server can host multiple websites using **virtual hosting**:

* **Name-based virtual hosting**: The server uses the `Host` HTTP header to distinguish which site to serve. Multiple domain names share a single IP address. This is the most common form.
* **IP-based virtual hosting**: Each website has its own IP address. Requires multiple NICs or multiple IPs on one NIC.

**Example (Nginx name-based virtual hosting config):**

```nginx
server {
    listen 80;
    server_name www.siteA.com;
    root /var/www/siteA;
}

server {
    listen 80;
    server_name www.siteB.com;
    root /var/www/siteB;
}
```

***

**Reverse Proxy and Load Balancing**

In production, a web server often sits behind a **reverse proxy** (which may itself be Nginx or a dedicated load balancer). The reverse proxy:

* Distributes incoming requests across multiple backend application servers (**load balancing**).
* Terminates TLS, so backend servers handle only plain HTTP.
* Caches responses to reduce backend load.
* Provides a single entry point for security (firewall, rate-limiting, WAF).

```
Client ---> [Reverse Proxy / Load Balancer]
                     |         |         |
              [App Server 1] [App Server 2] [App Server 3]
```

***

**Web Server and HTTPS**

For HTTPS, the web server must hold a **TLS certificate** issued by a Certificate Authority (CA). During a TLS handshake:

1. The server sends its certificate to the client.
2. The client verifies the certificate chain against trusted root CAs.
3. Both parties negotiate a symmetric session key.
4. All subsequent HTTP traffic is encrypted using that session key.

**Let's Encrypt** is a free, automated CA that has made HTTPS adoption widespread.

#### 2.3 HTTP (HyperText Transfer Protocol)

**What is HTTP?**

**HTTP (HyperText Transfer Protocol)** is the application-layer protocol that governs communication between web clients (browsers) and web servers. It is a **stateless, request-response protocol** operating over TCP. "Stateless" means each request is independent — the server retains no memory of previous interactions unless state is explicitly managed (e.g., via cookies or sessions).

HTTP is defined across several RFCs:

* **HTTP/1.0** — RFC 1945 (1996)
* **HTTP/1.1** — RFC 2616 (1999), updated by RFC 7230–7235 (2014)
* **HTTP/2** — RFC 7540 (2015)
* **HTTP/3** — RFC 9114 (2022); uses QUIC instead of TCP

Default port: **80 (HTTP)** and **443 (HTTPS)**.

***

**HTTP Request Structure**

An HTTP request consists of:

```
<Method> <Request-URI> <HTTP-Version>\r\n
<Header-Field>: <Value>\r\n
...
\r\n
[Message Body]
```

**Example GET request:**

```http
GET /courses/notes.html HTTP/1.1
Host: www.cs.mit.edu
User-Agent: Mozilla/5.0
Accept: text/html,application/xhtml+xml
Accept-Language: en-US,en;q=0.9
Connection: keep-alive

```

* The blank line (`\r\n`) separates headers from the body.
* GET requests have no body.

***

**HTTP Methods (Verbs)**

| Method      | Purpose                                                              | Has Body? | Idempotent? | Safe? |
| ----------- | -------------------------------------------------------------------- | --------- | ----------- | ----- |
| **GET**     | Retrieve a resource                                                  | No        | Yes         | Yes   |
| **POST**    | Submit data; create resource                                         | Yes       | No          | No    |
| **PUT**     | Replace a resource entirely                                          | Yes       | Yes         | No    |
| **PATCH**   | Partially update a resource                                          | Yes       | No          | No    |
| **DELETE**  | Remove a resource                                                    | Optional  | Yes         | No    |
| **HEAD**    | Same as GET but response has no body; used to check headers/metadata | No        | Yes         | Yes   |
| **OPTIONS** | List supported methods for a resource                                | No        | Yes         | Yes   |
| **CONNECT** | Establish a tunnel (used for HTTPS through a proxy)                  | —         | —           | No    |
| **TRACE**   | Echo the request back; used for diagnostics                          | No        | Yes         | Yes   |

* **Safe**: Does not modify server state.
* **Idempotent**: Sending the same request multiple times has the same effect as sending it once.

***

**HTTP Response Structure**

```
<HTTP-Version> <Status-Code> <Reason-Phrase>\r\n
<Header-Field>: <Value>\r\n
...
\r\n
[Message Body]
```

**Example response:**

```http
HTTP/1.1 200 OK
Date: Mon, 23 Jun 2025 10:00:00 GMT
Server: nginx/1.24.0
Content-Type: text/html; charset=UTF-8
Content-Length: 3824
Connection: keep-alive

<!DOCTYPE html>
<html>...
```

***

**HTTP Status Codes**

Status codes are three-digit numbers grouped into five classes:

| Class   | Range   | Meaning                                          | Common Examples                                                                                  |
| ------- | ------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **1xx** | 100–199 | Informational — request received, continuing     | `100 Continue`, `101 Switching Protocols`                                                        |
| **2xx** | 200–299 | Success — request received, understood, accepted | `200 OK`, `201 Created`, `204 No Content`                                                        |
| **3xx** | 300–399 | Redirection — further action required            | `301 Moved Permanently`, `302 Found`, `304 Not Modified`                                         |
| **4xx** | 400–499 | Client Error — bad request                       | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `429 Too Many Requests` |
| **5xx** | 500–599 | Server Error — server failed                     | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`                        |

***

**Important HTTP Headers**

**Request Headers:**

| Header              | Purpose                                        | Example                                            |
| ------------------- | ---------------------------------------------- | -------------------------------------------------- |
| `Host`              | Target server hostname (mandatory in HTTP/1.1) | `Host: www.example.com`                            |
| `User-Agent`        | Client software identification                 | `User-Agent: Mozilla/5.0 ...`                      |
| `Accept`            | Media types client can handle                  | `Accept: text/html, application/json`              |
| `Accept-Encoding`   | Compression algorithms supported               | `Accept-Encoding: gzip, deflate, br`               |
| `Authorization`     | Credentials for authentication                 | `Authorization: Bearer <token>`                    |
| `Cookie`            | Cookies sent to server                         | `Cookie: session_id=abc123`                        |
| `Content-Type`      | Media type of request body                     | `Content-Type: application/json`                   |
| `Content-Length`    | Size of request body in bytes                  | `Content-Length: 256`                              |
| `If-Modified-Since` | Conditional GET — only return if changed       | `If-Modified-Since: Sat, 29 Oct 2024 19:43:31 GMT` |

**Response Headers:**

| Header                      | Purpose                                 | Example                                       |
| --------------------------- | --------------------------------------- | --------------------------------------------- |
| `Content-Type`              | Media type of response body             | `Content-Type: text/html; charset=UTF-8`      |
| `Content-Length`            | Size of response body in bytes          | `Content-Length: 3824`                        |
| `Set-Cookie`                | Instructs client to store a cookie      | `Set-Cookie: session_id=abc123; HttpOnly`     |
| `Location`                  | Redirect target URL (for 3xx responses) | `Location: https://www.example.com/new`       |
| `Cache-Control`             | Caching directives                      | `Cache-Control: max-age=3600, public`         |
| `ETag`                      | Resource version identifier for caching | `ETag: "686897696a7c876b7e"`                  |
| `Server`                    | Server software identification          | `Server: nginx/1.24.0`                        |
| `Strict-Transport-Security` | Enforces HTTPS for future requests      | `Strict-Transport-Security: max-age=31536000` |

***

**HTTP/1.0 vs HTTP/1.1 vs HTTP/2 vs HTTP/3**

| Feature                | HTTP/1.0                             | HTTP/1.1                           | HTTP/2                                   | HTTP/3                        |
| ---------------------- | ------------------------------------ | ---------------------------------- | ---------------------------------------- | ----------------------------- |
| **Connection**         | Non-persistent (new TCP per request) | Persistent (keep-alive by default) | Persistent + multiplexed                 | Multiplexed over QUIC (UDP)   |
| **Multiplexing**       | No                                   | No                                 | Yes (multiple streams on one connection) | Yes                           |
| **Header Compression** | No                                   | No                                 | Yes (HPACK)                              | Yes (QPACK)                   |
| **Server Push**        | No                                   | No                                 | Yes                                      | Yes                           |
| **HOL Blocking**       | Yes                                  | Yes (pipeline partial fix)         | Yes (TCP-level)                          | No (QUIC streams independent) |
| **Transport**          | TCP                                  | TCP                                | TCP                                      | QUIC (UDP)                    |
| **Encryption**         | Optional                             | Optional                           | Effectively mandatory                    | Mandatory                     |

**Head-of-Line (HOL) Blocking:** In HTTP/1.1, if a request stalls, all subsequent requests on that connection are blocked. HTTP/2 solves this at the HTTP level (multiple streams) but TCP itself can still cause HOL blocking. HTTP/3 uses QUIC which eliminates TCP-level HOL blocking.

***

**Persistent Connections and Pipelining**

**HTTP/1.1 Persistent Connection:**

In HTTP/1.0, a new TCP connection was opened for every request/response pair — extremely inefficient due to TCP's three-way handshake overhead. HTTP/1.1 introduced **persistent connections** (keep-alive): the TCP connection remains open after a response, allowing multiple requests to be served on the same connection.

```
HTTP/1.0:
[TCP SYN] --> [TCP SYN-ACK] --> [TCP ACK] --> GET --> Response --> [FIN]
[TCP SYN] --> [TCP SYN-ACK] --> [TCP ACK] --> GET --> Response --> [FIN]  (for next resource)

HTTP/1.1 (persistent):
[TCP SYN] --> [TCP SYN-ACK] --> [TCP ACK]
--> GET (req 1) --> Response (req 1)
--> GET (req 2) --> Response (req 2)
--> GET (req 3) --> Response (req 3)
[FIN]
```

**HTTP Pipelining:** Sending multiple requests without waiting for responses. Limited adoption due to complexity of handling out-of-order responses.

***

**Cookies and Sessions**

HTTP is stateless by design. **Cookies** are a mechanism to maintain state across requests.

1. The server sets a cookie via `Set-Cookie` header in a response.
2. The browser stores the cookie and includes it in all future requests to that domain via the `Cookie` header.
3. The server reads the cookie to identify the user or session.

**Cookie attributes:**

| Attribute             | Purpose                                             |
| --------------------- | --------------------------------------------------- |
| `Expires` / `Max-Age` | When the cookie expires (session cookie if omitted) |
| `Domain`              | Which domains receive the cookie                    |
| `Path`                | Which URL paths receive the cookie                  |
| `Secure`              | Only send over HTTPS                                |
| `HttpOnly`            | Not accessible by JavaScript (prevents XSS theft)   |
| `SameSite`            | Controls cross-site sending (Strict/Lax/None)       |

***

**HTTP Caching**

Caching reduces latency and server load by reusing previously fetched responses.

* **`Cache-Control: max-age=N`** — the response is fresh for N seconds.
* **`ETag`** — a hash/identifier for the resource version. The client sends `If-None-Match: <etag>` on a conditional request; the server returns `304 Not Modified` if unchanged.
* **`Last-Modified`** — timestamp of the resource. Client sends `If-Modified-Since`; server returns `304` if not changed.

***

**HTTPS — HTTP over TLS**

**HTTPS** is HTTP running over a **TLS (Transport Layer Security)** encrypted connection. TLS replaced the older SSL protocol. HTTPS ensures:

* **Confidentiality** — data is encrypted in transit; eavesdroppers cannot read it.
* **Integrity** — data cannot be modified in transit without detection.
* **Authentication** — the server's identity is verified via its TLS certificate.

The TLS handshake happens before any HTTP data is exchanged, adding one to two round-trip times to the initial connection establishment (mitigated by TLS session resumption and TLS 1.3 improvements).

### 3. Email Services

#### 3.1 Electronic Mail — Architecture and Components

**Overview**

**Electronic mail (email)** is one of the oldest and most widely used Internet applications. It enables asynchronous message delivery between users anywhere in the world. Unlike real-time communication (telephone, chat), email does not require both parties to be online simultaneously — the message is stored until the recipient retrieves it.

An email address has the format:

```
local-part@domain
```

For example: `alice@cs.mit.edu` — `alice` is the local part (mailbox name), `cs.mit.edu` is the domain.

***

**Core Components of an Email System**

Email involves four distinct components working together:

**1. Mail User Agent (MUA)**

Also called an **email client**. This is the software through which users compose, send, read, and manage email. Examples: Microsoft Outlook, Mozilla Thunderbird, Apple Mail, Gmail web interface.

The MUA's responsibilities:

* Provide a composition interface.
* Submit outgoing mail to the MTA.
* Retrieve incoming mail from the mail server (via POP3 or IMAP).
* Display and manage messages.

**2. Mail Transfer Agent (MTA)**

Also called a **mail server** or **SMTP server**. The MTA routes and relays email from source to destination. Examples: Postfix, Sendmail, Microsoft Exchange, Exim.

An MTA:

* Accepts email from MUAs (on port 587, submission) or from other MTAs (on port 25, SMTP relay).
* Looks up the destination domain's MX record via DNS.
* Relays the message to the destination MTA.
* Queues messages when the destination is temporarily unavailable and retries.

**3. Mail Delivery Agent (MDA)**

After the destination MTA receives a message, the MDA delivers it into the recipient's **mailbox** on the local server. Examples: Dovecot (also serves as a mail access server), Procmail. The MDA may apply filters, spam detection, and sorting rules.

**4. Mail Access Agent (MAA) / Mail Store**

The mail store holds messages in **mailboxes** until the recipient retrieves them. The access protocol (POP3 or IMAP) is what the recipient's MUA uses to access this store.

***

**Email Flow — End-to-End**

```
Sender (Alice)                                           Recipient (Bob)
alice@cs.mit.edu                                         bob@gmail.com

[MUA: Outlook]
    |
    | SMTP (submission, port 587)
    v
[Alice's MTA: smtp.mit.edu]
    |
    | DNS: MX lookup for gmail.com --> aspmx.l.google.com
    | SMTP relay (port 25)
    v
[Bob's MTA: aspmx.l.google.com]
    |
    | MDA delivers to mailbox
    v
[Bob's Mailbox on Gmail servers]
    |
    | IMAP (port 993) or POP3 (port 995)
    v
[Bob's MUA: Gmail app / browser]
```

**Step-by-step:**

1. Alice composes a message in her MUA and clicks Send.
2. The MUA connects to Alice's outgoing SMTP server (`smtp.mit.edu`, port 587) and submits the message using the **SMTP protocol**. Alice authenticates (username + password).
3. Alice's MTA accepts the message and looks up the **MX record** for `gmail.com` in DNS.
4. Alice's MTA opens an SMTP connection (port 25) to Bob's MTA (`aspmx.l.google.com`) and transfers the message.
5. Bob's MTA accepts the message and passes it to the **MDA**, which places it in Bob's mailbox.
6. Bob opens his email app, which connects to Gmail's mail server using **IMAP** or **POP3** to retrieve his messages.
7. Bob reads Alice's email.

***

**Email Message Format — RFC 5322**

An email message has two parts separated by a blank line:

**Headers:**

```
From: Alice Smith <alice@cs.mit.edu>
To: Bob Jones <bob@gmail.com>
Subject: Meeting Tomorrow
Date: Mon, 23 Jun 2025 14:30:00 +0530
Message-ID: <20250623143000.12345@cs.mit.edu>
MIME-Version: 1.0
Content-Type: text/plain; charset=UTF-8
```

**Body:**

```
Hi Bob,

Are you available for a meeting tomorrow at 10am?

Regards,
Alice
```

***

**MIME — Multipurpose Internet Mail Extensions**

The original email format (RFC 822) only supported **7-bit ASCII text**. MIME (RFC 2045–2049) extends this to support:

* Non-ASCII characters (other languages, Unicode)
* Attachments (PDF, Word documents, images, audio, video)
* Multi-part messages (e.g., a message with both plain text and HTML versions)

**Key MIME headers:**

| Header                      | Purpose                                    | Example                                                                 |
| --------------------------- | ------------------------------------------ | ----------------------------------------------------------------------- |
| `MIME-Version`              | Indicates MIME is used                     | `MIME-Version: 1.0`                                                     |
| `Content-Type`              | Media type of the body or part             | `Content-Type: multipart/mixed; boundary="---ABC123"`                   |
| `Content-Transfer-Encoding` | How the data is encoded                    | `base64` (for binary), `quoted-printable` (for text with special chars) |
| `Content-Disposition`       | Whether content is inline or an attachment | `Content-Disposition: attachment; filename="report.pdf"`                |

**Common MIME types:**

| Type          | Subtype              | Meaning                                                |
| ------------- | -------------------- | ------------------------------------------------------ |
| `text`        | `plain`              | Plain text                                             |
| `text`        | `html`               | HTML content                                           |
| `image`       | `jpeg`, `png`, `gif` | Images                                                 |
| `application` | `pdf`                | PDF document                                           |
| `application` | `octet-stream`       | Arbitrary binary data                                  |
| `multipart`   | `mixed`              | Multiple parts of different types                      |
| `multipart`   | `alternative`        | Multiple versions of same content (e.g., plain + HTML) |

**Example multipart message:**

```
Content-Type: multipart/mixed; boundary="====BOUNDARY===="

--====BOUNDARY====
Content-Type: text/plain; charset=UTF-8

Please find the report attached.

--====BOUNDARY====
Content-Type: application/pdf
Content-Transfer-Encoding: base64
Content-Disposition: attachment; filename="report.pdf"

JVBERi0xLjQKJcfs...
--====BOUNDARY====--
```

***

**Email Security**

| Mechanism                                                                  | Purpose                                                                                                                                                                              |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **SPF (Sender Policy Framework)**                                          | DNS TXT record listing IPs authorised to send email for a domain. Prevents spoofing of the envelope sender.                                                                          |
| **DKIM (DomainKeys Identified Mail)**                                      | The sending MTA signs the message with a private key; the signature is in a header. Receivers verify using the public key in DNS. Ensures message integrity and sender authenticity. |
| **DMARC (Domain-based Message Authentication, Reporting and Conformance)** | Policy that specifies what to do if SPF and/or DKIM checks fail (none / quarantine / reject). Also enables reporting.                                                                |
| **TLS for SMTP**                                                           | Encrypts the SMTP relay connection between MTAs (STARTTLS or SMTPS).                                                                                                                 |
| **S/MIME / PGP**                                                           | End-to-end encryption and signing of the email body itself.                                                                                                                          |

#### 3.2 SMTP (Simple Mail Transfer Protocol)

**What is SMTP?**

**SMTP (Simple Mail Transfer Protocol)** is the standard protocol for **sending and relaying email** across the Internet. It is defined in RFC 5321 (which obsoletes RFC 2821 and RFC 821). SMTP is a **push protocol** — the sender initiates the connection and pushes mail to the receiver.

**Ports:**

* **Port 25** — SMTP relay between MTAs (server-to-server). Generally blocked by ISPs for end-users to prevent spam.
* **Port 587** — Mail submission: MUA to MTA (requires authentication). The recommended port for client submission.
* **Port 465** — SMTPS (SMTP over TLS, implicit TLS). Legacy but still used.

***

**SMTP is a Text-Based Protocol**

SMTP uses **plain ASCII text commands and responses**. This makes it human-readable and easy to inspect. A command is a short keyword followed by arguments and terminated with CRLF (`\r\n`). Responses consist of a three-digit code and a human-readable description.

***

**SMTP Commands**

| Command     | Syntax                       | Purpose                                                                                     |
| ----------- | ---------------------------- | ------------------------------------------------------------------------------------------- |
| `HELO`      | `HELO <domain>`              | Identify the client (older; HTTP/1.0 equivalent)                                            |
| `EHLO`      | `EHLO <domain>`              | Extended HELO; client announces it supports ESMTP; server replies with supported extensions |
| `MAIL FROM` | `MAIL FROM:<sender@domain>`  | Begin a mail transaction; specify envelope sender                                           |
| `RCPT TO`   | `RCPT TO:<recipient@domain>` | Specify a recipient (repeat for multiple recipients)                                        |
| `DATA`      | `DATA`                       | Begin the message body; terminated by `<CRLF>.<CRLF>`                                       |
| `QUIT`      | `QUIT`                       | Close the connection gracefully                                                             |
| `RSET`      | `RSET`                       | Abort current mail transaction, reset state                                                 |
| `VRFY`      | `VRFY <user>`                | Verify if a mailbox exists (often disabled for privacy)                                     |
| `NOOP`      | `NOOP`                       | No operation; keeps the connection alive                                                    |
| `STARTTLS`  | `STARTTLS`                   | Upgrade the plain connection to TLS (ESMTP extension)                                       |
| `AUTH`      | `AUTH <mechanism>`           | Authenticate the client (PLAIN, LOGIN, CRAM-MD5, etc.)                                      |

***

**SMTP Response Codes**

| Code  | Meaning                                           |
| ----- | ------------------------------------------------- |
| `220` | Service ready (server greeting)                   |
| `221` | Service closing; bye                              |
| `250` | Requested action completed successfully           |
| `354` | Start mail input; end with `<CRLF>.<CRLF>`        |
| `421` | Service not available; connection closed          |
| `450` | Mailbox unavailable (try again later)             |
| `451` | Local error; request aborted                      |
| `452` | Insufficient storage                              |
| `500` | Syntax error, command unrecognised                |
| `501` | Syntax error in parameters                        |
| `503` | Bad sequence of commands                          |
| `550` | Mailbox unavailable (not found, policy rejection) |
| `551` | User not local; forwarding address given          |
| `552` | Exceeded storage allocation                       |
| `553` | Mailbox name not allowed                          |
| `554` | Transaction failed (e.g., spam policy rejection)  |

First digit semantics: **2xx = success**, **3xx = partial / continue**, **4xx = transient failure (retry)**, **5xx = permanent failure (do not retry)**.

***

**SMTP Session — Complete Example**

```
S: 220 smtp.gmail.com ESMTP ready
C: EHLO smtp.mit.edu
S: 250-smtp.gmail.com Hello smtp.mit.edu
S: 250-SIZE 35882577
S: 250-8BITMIME
S: 250-STARTTLS
S: 250-AUTH LOGIN PLAIN
S: 250 SMTPUTF8
C: STARTTLS
S: 220 2.0.0 Ready to start TLS
  ... TLS handshake occurs ...
C: EHLO smtp.mit.edu
S: 250-smtp.gmail.com Hello smtp.mit.edu
S: 250 AUTH LOGIN PLAIN
C: AUTH PLAIN AHVzZXIAcGFzc3dvcmQ=
S: 235 2.7.0 Accepted
C: MAIL FROM:<alice@cs.mit.edu>
S: 250 2.1.0 OK
C: RCPT TO:<bob@gmail.com>
S: 250 2.1.5 OK
C: DATA
S: 354 End data with <CR><LF>.<CR><LF>
C: From: Alice <alice@cs.mit.edu>
C: To: Bob <bob@gmail.com>
C: Subject: Test Message
C: Date: Mon, 23 Jun 2025 10:00:00 +0530
C: MIME-Version: 1.0
C: Content-Type: text/plain
C:
C: Hello Bob, this is a test.
C: .
S: 250 2.0.0 OK: queued as MSG12345
C: QUIT
S: 221 2.0.0 Bye
```

***

**Envelope vs. Message Headers**

A critical and commonly confused distinction:

* The **envelope** (MAIL FROM / RCPT TO commands) is used by MTAs for routing. It is not part of the email message content. Think of it as the address written on the outside of a physical envelope.
* The **message headers** (From:, To:, Subject:, etc.) are part of the email body itself and are what the user sees in their MUA.

These can differ — this is how email spoofing works, and why SPF checks the envelope sender, while DKIM authenticates the message header From.

***

**SMTP and Spam Control**

Because SMTP's original design has no authentication for the envelope sender, spam is a major problem. Mechanisms used to control it include:

* **Relay restrictions**: Modern MTAs only relay email for authenticated users or IP addresses within their network.
* **Blacklists (DNS Blackhole Lists / DNSBL)**: Real-time databases of known spam sources. An MTA can reject connections from blacklisted IPs.
* **Rate limiting**: Limit the number of messages accepted per connection/IP/hour.
* **SPF, DKIM, DMARC**: (Described in Section 3.1) authenticate the sending domain.
* **Content filtering**: Inspect message body for spam patterns (e.g., SpamAssassin).

***

**SMTP vs. HTTP (Comparison)**

| Aspect          | SMTP                                               | HTTP                    |
| --------------- | -------------------------------------------------- | ----------------------- |
| **Direction**   | Push (sender initiates)                            | Pull (client initiates) |
| **Transport**   | TCP                                                | TCP (HTTP/3: QUIC/UDP)  |
| **State**       | Commands within session; stateless across sessions | Stateless per request   |
| **Primary Use** | Email transfer                                     | Web content transfer    |
| **Persistence** | Session-based                                      | Connection keep-alive   |

#### 3.3 POP (Post Office Protocol)

**What is POP?**

**POP (Post Office Protocol)** is a protocol used by an email client (MUA) to **retrieve messages from a mail server**. The current version is **POP3**, defined in RFC 1939. POP3 operates on **TCP port 110**; POP3 over TLS (POP3S) uses **port 995**.

POP3 is a **pull protocol** and a **download-and-delete model**: messages are downloaded from the server to the client, and optionally deleted from the server. Once deleted, messages exist only on the local device.

***

**POP3 States and Commands**

A POP3 session goes through three states:

```
AUTHORIZATION state  -->  TRANSACTION state  -->  UPDATE state
(authenticate)            (retrieve messages)      (apply deletions, close)
```

**AUTHORIZATION State Commands:**

| Command | Syntax                 | Purpose                                                               |
| ------- | ---------------------- | --------------------------------------------------------------------- |
| `USER`  | `USER <username>`      | Provide the mailbox username                                          |
| `PASS`  | `PASS <password>`      | Provide the password                                                  |
| `APOP`  | `APOP <name> <digest>` | Authenticate using MD5 digest (avoids sending password in plain text) |
| `QUIT`  | `QUIT`                 | Close connection without entering TRANSACTION state                   |

**TRANSACTION State Commands:**

| Command | Syntax          | Purpose                                                    |
| ------- | --------------- | ---------------------------------------------------------- |
| `STAT`  | `STAT`          | Returns number of messages and total size                  |
| `LIST`  | `LIST [msg]`    | List message sizes; if msg given, size of that message     |
| `RETR`  | `RETR <msg>`    | Retrieve and return the full message                       |
| `DELE`  | `DELE <msg>`    | Mark a message for deletion                                |
| `NOOP`  | `NOOP`          | No operation; keep connection alive                        |
| `RSET`  | `RSET`          | Unmark all messages marked for deletion                    |
| `TOP`   | `TOP <msg> <n>` | Return headers and first n lines of body                   |
| `UIDL`  | `UIDL [msg]`    | Return unique identifier for message(s)                    |
| `QUIT`  | `QUIT`          | Enter UPDATE state; deletions committed; connection closes |

**Responses:**

* **`+OK`** — command succeeded (followed by data if applicable).
* **`-ERR`** — command failed (followed by a reason).

***

**POP3 Session Example**

```
S: +OK POP3 server ready
C: USER alice
S: +OK
C: PASS secret123
S: +OK alice's mailbox has 3 messages (18423 octets)
C: STAT
S: +OK 3 18423
C: LIST
S: +OK 3 messages (18423 octets)
S: 1 6734
S: 2 4215
S: 3 7474
S: .
C: RETR 1
S: +OK 6734 octets
S: (full message content)
S: .
C: DELE 1
S: +OK message 1 deleted
C: QUIT
S: +OK POP3 server signing off (1 message deleted)
```

***

**POP3 Characteristics and Limitations**

**Advantages:**

* Simple protocol; easy to implement.
* Works well for single-device access — messages are on your local machine, accessible offline.
* Reduces server storage requirements.

**Limitations:**

| Limitation                 | Explanation                                                                                                 |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **Single-device model**    | Messages downloaded to one device are not accessible from another (unless "leave on server" option is set). |
| **No server-side folders** | Folder organisation is local only; if you switch devices, your folder structure is lost.                    |
| **No synchronisation**     | Read/unread status, flags, deletions are not synchronised across devices.                                   |
| **Download-all model**     | POP3 downloads entire messages; cannot selectively download headers only.                                   |

Because of these limitations, POP3 has largely been replaced by IMAP for multi-device users, though it remains in use where simplicity and offline access are priorities.

***

**"Leave Messages on Server" Option**

Most MUAs offer a "leave a copy of messages on the server" option when using POP3. This prevents deletion after download, allowing multiple devices to retrieve the same messages. However, it does not provide true synchronisation — read/unread status and organisation are still not shared.

#### 3.4 IMAP (Internet Message Access Protocol)

**What is IMAP?**

**IMAP (Internet Message Access Protocol)** is a protocol for accessing and managing email messages stored **on a mail server**. The current version is **IMAP4** (revision 1), defined in RFC 3501. IMAP operates on **TCP port 143**; IMAP over TLS (IMAPS) uses **port 993**.

The fundamental philosophy of IMAP differs from POP3: messages are **stored and managed on the server**. The client views and manipulates them in place rather than downloading and deleting them. This is the **remote mailbox model**.

***

**Key Architectural Difference: POP3 vs IMAP**

```
POP3 Model:
Server [Inbox] ---(download & delete)---> Client [Local Storage]
   (server empties)                         (messages live here)

IMAP Model:
Server [Inbox / Folders / Flags] <---(sync)---> Client [Local Cache]
   (server is the master copy)                   (cache only)
```

In IMAP, the server is the authoritative store. Multiple clients (phone, laptop, web browser) all access and synchronise with the same server-side state.

***

**IMAP Capabilities**

IMAP is significantly richer than POP3. Key capabilities:

| Capability                     | Description                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Server-side folders**        | Create, rename, delete folders (called "mailboxes" in IMAP) on the server                                                             |
| **Message flags**              | Per-message flags: `\Seen` (read), `\Answered`, `\Flagged`, `\Deleted`, `\Draft`; custom flags also supported                         |
| **Partial fetch**              | Download only message headers or specific MIME parts — useful on slow connections (avoid downloading large attachments unless needed) |
| **Server-side search**         | Issue a `SEARCH` command; the server filters and returns matching message IDs                                                         |
| **Multiple concurrent access** | Multiple clients can access the same mailbox simultaneously                                                                           |
| **Synchronisation**            | New messages, flag changes, and deletions are visible to all connected clients                                                        |
| **Message sequences and UIDs** | Messages addressed by sequence number (relative) or UID (permanent, survives reconnect)                                               |

***

**IMAP Connection States**

```
Not Authenticated --> Authenticated --> Selected --> Logout
```

| State                 | Description                            | Commands Available                                                                         |
| --------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Not Authenticated** | Connection established; login required | `LOGIN`, `AUTHENTICATE`, `STARTTLS`, `LOGOUT`                                              |
| **Authenticated**     | Login successful; no mailbox selected  | `SELECT`, `EXAMINE`, `CREATE`, `DELETE`, `RENAME`, `LIST`, `SUBSCRIBE`, `STATUS`, `LOGOUT` |
| **Selected**          | A specific mailbox (folder) is open    | All above plus `FETCH`, `STORE`, `SEARCH`, `COPY`, `EXPUNGE`, `CLOSE`                      |
| **Logout**            | Session terminating                    | `LOGOUT`                                                                                   |

***

**Key IMAP Commands**

| Command                          | Purpose                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------ |
| `LOGIN user pass`                | Authenticate with username and password                                        |
| `SELECT INBOX`                   | Open a mailbox for full read/write access; server reports message count, flags |
| `EXAMINE INBOX`                  | Open a mailbox read-only                                                       |
| `LIST "" "*"`                    | List all mailboxes (folders) on the server                                     |
| `CREATE "Work"`                  | Create a new folder named "Work"                                               |
| `RENAME "Work" "Projects"`       | Rename a folder                                                                |
| `DELETE "OldFolder"`             | Delete a folder                                                                |
| `FETCH 1:5 (FLAGS BODY[HEADER])` | Fetch flags and headers of messages 1 through 5                                |
| `FETCH 3 BODY[]`                 | Fetch the complete message 3                                                   |
| `FETCH 3 BODY[TEXT]`             | Fetch only the body (not headers) of message 3                                 |
| `STORE 3 +FLAGS (\Seen)`         | Mark message 3 as read                                                         |
| `STORE 3 +FLAGS (\Deleted)`      | Mark message 3 for deletion                                                    |
| `EXPUNGE`                        | Permanently remove all messages marked `\Deleted`                              |
| `SEARCH UNSEEN`                  | Return IDs of all unread messages                                              |
| `SEARCH FROM "alice"`            | Return IDs of messages from alice                                              |
| `COPY 3 "Sent"`                  | Copy message 3 to the "Sent" folder                                            |
| `IDLE`                           | Server notifies client of new messages in real-time (push notification)        |
| `LOGOUT`                         | Close the session                                                              |

***

**IMAP Session Example**

```
S: * OK IMAP4rev1 server ready
C: A001 LOGIN alice secret123
S: A001 OK alice logged in
C: A002 LIST "" "*"
S: * LIST (\HasNoChildren) "/" INBOX
S: * LIST (\HasNoChildren) "/" Sent
S: * LIST (\HasNoChildren) "/" Trash
S: A002 OK LIST completed
C: A003 SELECT INBOX
S: * 47 EXISTS
S: * 3 RECENT
S: * OK [UNSEEN 44]
S: * FLAGS (\Answered \Flagged \Deleted \Seen \Draft)
S: A003 OK [READ-WRITE] SELECT completed
C: A004 FETCH 44:47 (FLAGS BODY[HEADER.FIELDS (FROM SUBJECT DATE)])
S: * 44 FETCH (FLAGS (\Recent) BODY[HEADER.FIELDS ...] {...})
  ... headers for messages 44-47 ...
S: A004 OK FETCH completed
C: A005 FETCH 44 BODY[]
S: * 44 FETCH (BODY[] {3512}
  ... full message content ...
  )
S: A005 OK FETCH completed
C: A006 STORE 44 +FLAGS (\Seen)
S: * 44 FETCH (FLAGS (\Recent \Seen))
S: A006 OK STORE completed
C: A007 LOGOUT
S: * BYE IMAP4rev1 server logging out
S: A007 OK LOGOUT completed
```

***

**IMAP vs. POP3 — Comprehensive Comparison**

| Feature                   | POP3                                        | IMAP                                       |
| ------------------------- | ------------------------------------------- | ------------------------------------------ |
| **Storage location**      | Local device (downloaded)                   | Server (authoritative copy)                |
| **Multi-device access**   | Poor (workarounds needed)                   | Excellent (all devices see same state)     |
| **Offline access**        | Native (messages local)                     | Requires explicit caching                  |
| **Server storage use**    | Low (messages deleted from server)          | High (all messages remain on server)       |
| **Folder support**        | Local folders only                          | Server-side folders, shared across devices |
| **Flag synchronisation**  | None                                        | Full (read/unread, starred, etc.)          |
| **Partial message fetch** | No                                          | Yes (headers only, specific MIME parts)    |
| **Server-side search**    | No                                          | Yes                                        |
| **Protocol complexity**   | Simple                                      | Complex but feature-rich                   |
| **Real-time push**        | No                                          | Yes (via IDLE command)                     |
| **Best use case**         | Single device, low bandwidth, offline-first | Multiple devices, always-connected users   |

### 4. File and Remote Access

#### 4.1 FTP (File Transfer Protocol)

**What is FTP?**

**FTP (File Transfer Protocol)** is an application-layer protocol for transferring files between a client and a server over a TCP/IP network. It is one of the oldest Internet protocols, defined in RFC 959 (1985). FTP supports both uploading (client → server) and downloading (server → client), as well as directory listing, renaming, and deletion of files.

FTP operates on **TCP** and uses **two separate connections**:

* **Control Connection** — TCP port **21** — carries commands and responses throughout the session.
* **Data Connection** — TCP port **20** (active mode) or a negotiated port (passive mode) — carries actual file data; opened per transfer and closed after.

***

**Why Two Connections?**

The separation of control and data is a deliberate design choice:

* The **control channel** stays open for the duration of the session. Commands are sent interactively.
* The **data channel** is opened on demand for each file transfer or directory listing, then immediately closed. This avoids maintaining a persistent large-bandwidth connection when no transfer is occurring.

This design is called **out-of-band control**: the control information flows on a separate channel from the actual data.

***

**FTP Modes — Active vs. Passive**

**Active Mode:**

1. Client opens a random port $N$ (> 1024) and sends `PORT N` command to server on the control connection.
2. The **server** initiates the data connection from its port 20 to the client's port $N$.

Problem: The server connects back to the client. If the client is behind a NAT or firewall, this incoming connection is often blocked.

```
Client                          Server
Random port N (listening) <---  Server port 20 (initiates data conn)
Port 21 (control) ----------->  Server port 21 (control)
```

**Passive Mode (PASV):**

1. Client sends `PASV` command on the control connection.
2. The **server** opens a random port $M$ and tells the client "connect to me on port $M$."
3. The **client** initiates the data connection to the server's port $M$.

This solves the firewall problem because the client always initiates both connections.

```
Client                          Server
(connects to M) -------------->  Server port M (data, listening)
Port 21 (control) ----------->  Server port 21 (control)
```

Modern FTP clients use passive mode by default.

***

**FTP Commands**

| Command            | Purpose                                             |
| ------------------ | --------------------------------------------------- |
| `USER <username>`  | Send username                                       |
| `PASS <password>`  | Send password                                       |
| `PWD`              | Print working directory                             |
| `CWD <dir>`        | Change working directory                            |
| `CDUP`             | Change to parent directory                          |
| `LIST [dir]`       | List directory contents (sent over data connection) |
| `NLST [dir]`       | Name list (filenames only, no details)              |
| `RETR <file>`      | Download (retrieve) a file                          |
| `STOR <file>`      | Upload (store) a file                               |
| `APPE <file>`      | Append to a file                                    |
| `DELE <file>`      | Delete a file                                       |
| `MKD <dir>`        | Make a directory                                    |
| `RMD <dir>`        | Remove a directory                                  |
| `RNFR <old>`       | Rename from (start of rename operation)             |
| `RNTO <new>`       | Rename to                                           |
| `TYPE A`           | Set transfer type to ASCII (text mode)              |
| `TYPE I`           | Set transfer type to Image/Binary                   |
| `PASV`             | Enter passive mode                                  |
| `PORT h,h,h,h,p,p` | Active mode: specify client IP and port             |
| `QUIT`             | Close control connection                            |

***

**FTP Response Codes**

| Code  | Meaning                                           |
| ----- | ------------------------------------------------- |
| `125` | Data connection already open; transfer starting   |
| `150` | File status OK; about to open data connection     |
| `200` | Command OK                                        |

| `426` | Connection closed; transfer aborted               |
| `530` | Not logged in                                     |
| `550` | File not found or access denied                   |

***

**Transfer Modes**

| Mode                               | Use                                               | Behaviour                                                                                          |
| ---------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **ASCII Mode** (`TYPE A`)          | Text files                                        | Line endings converted between OS conventions (CRLF ↔ LF); safe for text but corrupts binary files |
| **Binary / Image Mode** (`TYPE I`) | All files (binary, executables, images, archives) | Exact byte-for-byte transfer; no conversion; always use for non-text files                         |

A classic mistake is transferring a binary file in ASCII mode, which corrupts it due to line-ending conversion.

***

**Anonymous FTP**

Many public file servers support **anonymous FTP**: a user logs in with the username `anonymous` and any string as a password (by convention, their email address). This provides public read-only access to designated directories (software downloads, public datasets).

***

**FTP Security Concerns**

FTP transmits **credentials and data in plaintext**. Anyone on the network path can intercept:

* Usernames and passwords
* File contents

**Secure alternatives:**

| Protocol                              | Description                                                                                                                                                        |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **FTPS (FTP Secure)**                 | FTP over TLS (RFC 4217). Two modes: Explicit FTPS (STARTTLS on port 21) and Implicit FTPS (port 990).                                                              |
| **SFTP (SSH File Transfer Protocol)** | A completely different protocol that runs over SSH. Not FTP at all — just similarly named. Provides encryption, authentication, and file management. Uses port 22. |
| **SCP (Secure Copy Protocol)**        | Simpler file copy over SSH. Uses port 22.                                                                                                                          |

In modern deployments, SFTP has largely replaced FTP for secure file transfer.

#### 4.2 NFS (Network File System)

**What is NFS?**

**NFS (Network File System)** is a distributed file system protocol developed by Sun Microsystems in 1984 and defined in RFC 1094 (NFSv2), RFC 1813 (NFSv3), and RFC 7530 (NFSv4). NFS allows a client machine to access files over a network as if they were stored on its own local disk. The network access is transparent to applications — they use the same file system calls (`open`, `read`, `write`, `close`) regardless of whether the file is local or remote.

NFS traditionally operates over **UDP port 2049** (for performance) in older versions; **NFSv4 uses TCP port 2049** exclusively, which provides reliability.

***

**NFS Architecture**

NFS follows a **client-server model**:

* The **NFS server** exports (makes available) one or more directories from its local file system.
* The **NFS client** mounts those exported directories into its own file system hierarchy.
* Once mounted, applications on the client access remote files through the standard POSIX file system interface.

```
NFS Server                         NFS Client
/exported/data  <---[NFS over TCP/UDP]--->  /mnt/remotedata (mount point)
                                               |
                                             Application: open("/mnt/remotedata/file.txt")
                                             (looks and feels like a local file)
```

***

**How NFS Works — Key Mechanisms**

**Mounting:**

Before using an NFS share, the client must mount it. The `mount` command (or `/etc/fstab` entry) contacts the server's `mountd` daemon, verifies access, and receives a **file handle** that identifies the exported directory. Subsequent file operations use file handles.

```bash
# Client mounts server's /exported/data at local /mnt/data
mount -t nfs 192.168.1.5:/exported/data /mnt/data
```

**File Handles:**

NFS uses **opaque file handles** to identify files and directories. A file handle is a fixed-size token (32 bytes in NFSv3) that uniquely identifies a file system object on the server. Clients include the file handle in every RPC request.

File handles are **server-side references** — the client does not interpret them; it simply stores and returns them.

**RPC (Remote Procedure Call):**

NFS is built on **Sun RPC (Remote Procedure Call)**. Instead of directly manipulating the network, NFS procedures (LOOKUP, READ, WRITE, GETATTR, etc.) are called as if they were local function calls. The RPC framework serialises the arguments, sends them over the network, and deserialises the response.

***

**NFS Operations (NFSv3 core procedures)**

| Procedure | Purpose                                                |
| --------- | ------------------------------------------------------ |
| `NULL`    | No operation; used for testing                         |
| `GETATTR` | Get file attributes (size, permissions, timestamps)    |
| `SETATTR` | Set file attributes                                    |
| `LOOKUP`  | Look up a filename in a directory; returns file handle |
| `READ`    | Read data from a file                                  |
| `WRITE`   | Write data to a file                                   |
| `CREATE`  | Create a file                                          |
| `MKDIR`   | Create a directory                                     |
| `REMOVE`  | Delete a file                                          |
| `RMDIR`   | Remove a directory                                     |
| `RENAME`  | Rename a file                                          |
| `READDIR` | Read directory entries                                 |
| `FSSTAT`  | Get file system statistics                             |
| `COMMIT`  | Flush unstable writes to stable storage                |

***

**Stateless vs. Stateful NFS**

**NFSv2 and NFSv3 — Stateless:**

The server maintains **no state** about client connections or open files. Every RPC request is self-contained — it includes the file handle and all parameters needed to process it independently. If the server crashes and reboots, clients simply retry their requests; the server can resume without needing to restore any client state.

Implication: operations like file locking had to be handled by a separate auxiliary protocol (NLM — Network Lock Manager) in NFSv3.

**NFSv4 — Stateful:**

NFSv4 introduced statefulness. The server tracks open files, byte-range locks, and delegations. This enables:

* **Delegations**: The server delegates read or write authority for a file to a specific client. That client can satisfy requests locally without contacting the server, dramatically reducing network round-trips for popular files.
* **Integrated locking**: No separate lock manager needed.
* **Better semantics**: Closer to POSIX file system behaviour.
* **Compound operations**: Multiple operations bundled into a single RPC call.

***

**NFS Caching**

NFS clients aggressively cache file data and attributes locally to reduce network traffic. However, caching introduces consistency challenges:

* **Attribute cache**: The client caches file attributes (size, modification time) for a short period (typically 3–60 seconds). This means attribute reads don't hit the server every time.
* **Data cache**: Read data is cached in the client's page cache.
* **Write-back caching**: Writes may be buffered locally and flushed to the server asynchronously. If the client crashes before flushing, data is lost.
* **Cache coherence problem**: If two clients write to the same file, each might read stale cached data. NFSv4's delegation mechanism mitigates this by ensuring only one client has write authority at a time.

***

**NFS Exports and Security**

The server controls access via an **exports file** (`/etc/exports` on Linux):

```
/exported/data   192.168.1.0/24(rw,sync,no_subtree_check)
/public          *(ro,sync)
```

Options:

* `rw` / `ro` — read-write or read-only access.
* `sync` — writes are committed to stable storage before the server replies (safe but slower).
* `async` — writes acknowledged before committed (faster but risk data loss on crash).
* `no_root_squash` — allow the client's root user to act as root on the server (dangerous; rarely used).
* `root_squash` (default) — map client root to an unprivileged user (`nobody`).

**Security considerations:**

* NFSv2/v3 traditionally used only IP-based access control and UNIX UID/GID-based authorisation — both are easily spoofed.
* **NFSv4 with Kerberos (RPCSEC\_GSS)** provides strong mutual authentication and encryption, addressing most security concerns.

***

**NFS Versions Summary**

| Version | Year | Transport     | State     | Notable Features                                                  |
| ------- | ---- | ------------- | --------- | ----------------------------------------------------------------- |
| NFSv2   | 1989 | UDP (default) | Stateless | Basic file operations; 2GB file size limit                        |
| NFSv3   | 1995 | UDP or TCP    | Stateless | Large files; asynchronous writes; better error reporting          |
| NFSv4   | 2000 | TCP only      | Stateful  | Integrated locking; delegations; Kerberos security; compound RPCs |

#### 4.3 Telnet

**What is Telnet?**

**Telnet** (short for **Teletype Network**) is one of the oldest Internet application protocols, defined in RFC 854 (1983). It provides a **bidirectional interactive text-based communication channel** — most commonly used to remotely log in to and execute commands on a remote host, as if sitting at a local terminal. Telnet operates over **TCP port 23**.

Telnet creates a virtual terminal (called a **Network Virtual Terminal, NVT**) between client and server, abstracting differences in terminal types and operating systems.

***

**Network Virtual Terminal (NVT)**

The NVT is a concept that defines a canonical, lowest-common-denominator terminal with:

* A keyboard that produces 7-bit ASCII characters.
* A printer (display) that receives 7-bit ASCII.
* A half-duplex line discipline.

Both client and server translate between their local terminal formats and the NVT format, ensuring interoperability across different systems.

**NVT character set:**

* Printable characters: 7-bit ASCII (32–126).
* Control characters: CR (carriage return, 0x0D), LF (line feed, 0x0A), BEL (bell, 0x07), BS (backspace, 0x08), HT (horizontal tab, 0x09), FF (form feed, 0x0C), VT (vertical tab, 0x0B).
* A line is terminated by the NVT end-of-line sequence: `CR LF` (0x0D 0x0A).

***

**Telnet Option Negotiation**

Both sides can negotiate optional features via a set of commands embedded in the data stream. The **Interpret As Command (IAC)** byte (0xFF) signals that the following bytes are a Telnet control sequence, not user data.

**Option negotiation commands:**

| Command | Byte Value | Meaning                                    |
| ------- | ---------- | ------------------------------------------ |
| `WILL`  | 0xFB       | Sender wants to enable option              |
| `WONT`  | 0xFC       | Sender refuses to enable option            |
| `DO`    | 0xFD       | Sender requests remote side enable option  |
| `DONT`  | 0xFE       | Sender requests remote side disable option |

**Common Telnet options:**

| Option Code | Name                | Purpose                                             |
| ----------- | ------------------- | --------------------------------------------------- |
| 0           | Binary Transmission | Transmit 8-bit data instead of 7-bit                |
| 1           | Echo                | Server echoes characters back to client             |
| 3           | Suppress Go Ahead   | Enable full-duplex mode                             |
| 24          | Terminal Type       | Negotiate terminal emulation type                   |
| 31          | Window Size (NAWS)  | Client informs server of terminal window dimensions |
| 32          | Terminal Speed      | Negotiate connection speed                          |
| 34          | Linemode            | Line-by-line vs. character-by-character mode        |

**Example negotiation:**

```
IAC DO ECHO          --> Client asks server to echo characters
IAC WILL ECHO        --> Server agrees to echo
IAC DO SUPPRESS-GA   --> Client asks server to suppress Go-Ahead
IAC WILL SUPPRESS-GA --> Server agrees
```

***

**Telnet Session Flow**

```
Client                          Server (port 23)
  |                                 |
  |------- TCP SYN --------------->|
  |<------ TCP SYN-ACK ------------|
  |------- TCP ACK --------------->|
  |<------ "login: " --------------|  (server sends login prompt)
  |------- "alice\r\n" ----------->|
  |<------ "Password: " -----------|
  |------- "secret\r\n" ---------->|
  |<------ "$ " -------------------|  (shell prompt)
  |------- "ls -la\r\n" ---------->|
  |<------ (directory listing) ----|
  |------- "exit\r\n" ------------>|
  |<------ "Connection closed" ----|
```

***

**Telnet Security — The Fatal Flaw**

Telnet transmits **everything in plaintext** — including usernames, passwords, and all command output. Any attacker with the ability to intercept network traffic (a man-in-the-middle or anyone on the same network segment) can read the entire session, including credentials.

Additional security issues:

* No server authentication — a client cannot verify it is talking to the intended server (susceptible to impersonation).
* No data integrity protection — data can be modified in transit.

**Consequence:** Telnet is considered **insecure and obsolete** for any production use. It has been almost entirely replaced by **SSH** (Section 4.4). The only remaining legitimate uses of Telnet are:

* Testing connectivity to text-based services (e.g., `telnet smtp.example.com 25` to manually test an SMTP server).
* Accessing very old or embedded systems that do not support SSH.
* Network troubleshooting in controlled, isolated environments.

#### 4.4 SSH (Secure Shell)

**What is SSH?**

**SSH (Secure Shell)** is a cryptographic network protocol that provides a secure channel for remote login, command execution, file transfer, and port forwarding over an insecure network. It was designed by Tatu Ylönen in 1995 as a direct, secure replacement for Telnet, rlogin, and rsh. The current version is **SSH-2**, defined in RFC 4251–4256. SSH operates on **TCP port 22**.

SSH provides three core security guarantees:

1. **Confidentiality** — all traffic is encrypted; eavesdroppers cannot read the session.
2. **Integrity** — cryptographic MACs detect any modification of data in transit.
3. **Authentication** — both the server and the client are authenticated.

***

**SSH Architecture — Protocol Layers**

SSH is structured into three sub-protocols layered on top of TCP:

```
+-------------------------------+
|  SSH Connection Protocol      |  Multiple logical channels (shell, SFTP, port forwards)
+-------------------------------+
|  SSH Authentication Protocol  |  Verifies client identity
+-------------------------------+
|  SSH Transport Layer Protocol |  Encryption, integrity, server authentication
+-------------------------------+
|          TCP                  |
+-------------------------------+
```

**1. SSH Transport Layer Protocol (RFC 4253)**

Establishes the encrypted, integrity-protected tunnel. Handles:

* **Server authentication**: The server proves its identity using its host key (RSA, DSA, ECDSA, or Ed25519). The client verifies this against known hosts.
* **Key exchange**: Using algorithms such as Diffie-Hellman or ECDH to establish a shared session key without transmitting it.
* **Encryption**: Negotiated cipher (e.g., AES-128-CTR, AES-256-GCM, ChaCha20-Poly1305).
* **Integrity**: MAC algorithms (e.g., HMAC-SHA2-256).
* **Compression**: Optional (e.g., zlib).

**2. SSH User Authentication Protocol (RFC 4252)**

After the encrypted tunnel is established, the client authenticates to the server. Methods:

| Method                   | How it Works                                                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| **Password**             | Client sends password over the encrypted tunnel                                                                  |
| **Public Key**           | Client proves possession of a private key; server checks corresponding public key is in `~/.ssh/authorized_keys` |
| **Host-based**           | Trust is based on the client host's identity (rarely used)                                                       |
| **Keyboard-interactive** | Server sends prompts (e.g., for OTP/2FA)                                                                         |
| **GSSAPI/Kerberos**      | Enterprise single sign-on integration                                                                            |

**3. SSH Connection Protocol (RFC 4254)**

Multiplexes multiple logical **channels** over the single encrypted connection. Each channel is an independent bidirectional byte stream. Channel types include:

* **Session channel**: A remote shell, a command, or a subsystem (e.g., SFTP).
* **Direct TCP/IP channel**: Port forwarding.
* **X11 channel**: Forwarding graphical application display.

***

**SSH Host Keys and Known Hosts**

When a client connects to an SSH server for the first time:

1. The server sends its **host public key**.
2. The client checks its `~/.ssh/known_hosts` file for this server's key.
3. If not found, the client warns the user and (typically) asks for confirmation to add it.
4. Once accepted, the key is stored. On future connections, the client verifies the server's key matches what is stored — if it differs, a warning is issued (possible man-in-the-middle attack).

**Example `known_hosts` entry:**

```
192.168.1.5 ecdsa-sha2-nistp256 AAAAE2VjZHNhLXNoYTItbmlzdHAyNTYA...
```

***

**Public Key Authentication — Detailed Flow**

This is the most secure and commonly used authentication method in practice:

1. The client generates an **asymmetric key pair**: a private key (stored locally, protected by passphrase) and a public key.
2. The public key is appended to the server's `~/.ssh/authorized_keys` file for the target user account.
3. During authentication:
   * The client tells the server which public key it wants to use.
   * The server checks if that public key is in `authorized_keys`.
   * The server sends a **challenge** (random data).
   * The client signs the challenge with its private key and sends the signature.
   * The server verifies the signature using the public key. Success proves the client holds the private key.
4. No password is transmitted or required.

```
Client                          Server
  |                                 |
  |-- "I have key: PUBKEY_X" ----->|
  |<-- "Prove it: sign NONCE" ------|
  |-- signature(NONCE, PRIVKEY_X)->|
  |<-- "Authentication successful" -|
```

***

**SSH Key Algorithms**

| Algorithm   | Key Size                             | Notes                                                |
| ----------- | ------------------------------------ | ---------------------------------------------------- |
| **RSA**     | 2048, 4096 bits                      | Widely supported; older; key sizes must be large     |
| **DSA**     | 1024 bits                            | Deprecated; fixed 1024-bit key is too small          |
| **ECDSA**   | 256, 384, 521 bits (curve dependent) | Faster and smaller than RSA; use nistp256 or above   |
| **Ed25519** | 256 bits (fixed)                     | Recommended; based on Edwards-curve; fast and secure |

Ed25519 is the recommended choice for new keys as of current best practices.

***

**SSH Tunnelling and Port Forwarding**

SSH can forward arbitrary TCP connections through the encrypted tunnel — a feature called **port forwarding** or **SSH tunnelling**.

**Local Port Forwarding:**

Traffic sent to a local port is forwarded through the SSH tunnel to a remote destination.

```bash
ssh -L 8080:internal-server:80 user@jumphost
```

Any connection to `localhost:8080` on the client is tunnelled to `internal-server:80` via `jumphost`. Useful for accessing internal services behind a firewall.

**Remote Port Forwarding:**

A port on the remote server is forwarded back to the client.

```bash
ssh -R 9090:localhost:3000 user@publicserver
```

Traffic to `publicserver:9090` is forwarded to the client's `localhost:3000`. Useful for exposing a local development server publicly.

**Dynamic Port Forwarding (SOCKS proxy):**

```bash
ssh -D 1080 user@server
```

Creates a local SOCKS proxy. Applications can route any TCP traffic through the SSH tunnel — effectively a VPN.

***

**SFTP and SCP**

**SCP (Secure Copy Protocol):** A simple file copy protocol using SSH for transport.

```bash
scp localfile.txt user@server:/remote/path/
scp user@server:/remote/file.txt ./local/
```

**SFTP (SSH File Transfer Protocol):** A full-featured file management protocol over SSH. Supports directory listing, file upload/download, rename, delete, permission changes. Runs as an SSH subsystem.

```bash
sftp user@server
sftp> ls
sftp> get remotefile.txt
sftp> put localfile.txt
sftp> exit
```

Note: SFTP and FTP are entirely different protocols despite the similar name. SFTP runs exclusively over SSH.

***

**SSH vs. Telnet — Comparison**

| Feature                 | Telnet                   | SSH                                   |
| ----------------------- | ------------------------ | ------------------------------------- |
| **Encryption**          | None (plaintext)         | Full encryption (AES, ChaCha20, etc.) |
| **Authentication**      | Password in plaintext    | Password (encrypted) or public key    |
| **Server Verification** | None                     | Host key verification                 |
| **Integrity**           | None                     | HMAC                                  |
| **Port Forwarding**     | No                       | Yes                                   |
| **File Transfer**       | No (separate FTP needed) | Yes (SCP, SFTP)                       |
| **Port**                | 23                       | 22                                    |
| **Status**              | Obsolete; insecure       | Current standard                      |

### 5. Network Management and Utilities

#### 5.1 SNMP (Simple Network Management Protocol)

**What is SNMP?**

**SNMP (Simple Network Management Protocol)** is an application-layer protocol for managing and monitoring network devices (routers, switches, servers, printers, firewalls, UPS units, etc.) from a central management station. It is defined in RFC 1157 (SNMPv1), RFC 1902–1908 (SNMPv2c), and RFC 3411–3418 (SNMPv3). SNMP operates over **UDP** — queries use **port 161** and traps use **port 162**.

The word "Simple" in the name reflects the protocol's design philosophy: management information is stored in a well-defined database, and the protocol itself only needs a few basic operations to read and write it.

***

**SNMP Architecture**

An SNMP management system consists of three components:

**1. Managed Devices**

Network nodes being monitored: routers, switches, servers, etc. Each runs an **SNMP agent** — a software process that implements the SNMP protocol and maintains a local database of management information.

**2. SNMP Agents**

A software process running on each managed device. The agent:

* Collects local management data (interface statistics, CPU load, error counts, etc.).
* Stores this data in its **Management Information Base (MIB)**.
* Responds to SNMP queries from the manager.
* Sends unsolicited **traps** to the manager when significant events occur.

**3. Network Management Station (NMS) / Manager**

The central machine running management software (e.g., Nagios, Zabbix, SolarWinds, PRTG). It:

* **Polls** agents periodically by sending GET requests.
* **Sets** configuration parameters on agents using SET requests.
* **Receives traps** (alerts) from agents.
* Presents data in dashboards, graphs, and alerts.

```
Network Management Station (Manager)
          |
          |--- UDP port 161 (polling) --->   [Router Agent]   -- MIB
          |<-- UDP port 162 (traps) -----    [Switch Agent]   -- MIB
          |                                  [Server Agent]   -- MIB
```

***

**Management Information Base (MIB)**

The **MIB** is the database of management information maintained by each agent. It is organised as a tree structure (similar to DNS's domain name space), called the **Object Identifier (OID) tree** or **SMI (Structure of Management Information) tree**.

Each piece of management information (called a **managed object** or **MIB variable**) is identified by a unique **OID** — a sequence of integers separated by dots.

**OID Tree (partial):**

```
.1 (iso)
  .3 (org)
    .6 (dod)
      .1 (internet)
        .2 (mgmt)
          .1 (mib-2)
            .1 (system)
              .1 (sysDescr)      -- Description of the device
              .3 (sysUpTime)     -- Time since last reboot
              .5 (sysName)       -- Hostname
            .2 (interfaces)
              .1 (ifTable)
                .1 (ifEntry)
                  .1 (ifIndex)   -- Interface index
                  .2 (ifDescr)   -- Interface description
                  .8 (ifOperStatus) -- Operational status (up/down)
                  .10 (ifInOctets)  -- Bytes received
                  .16 (ifOutOctets) -- Bytes transmitted
```

The OID for `sysDescr` is: `1.3.6.1.2.1.1.1.0`

MIBs can be **standard** (defined by IETF for common devices, e.g., MIB-II) or **vendor-specific / enterprise** (defined by manufacturers for device-specific parameters, under `1.3.6.1.4.1.<enterprise-number>`).

***

**SNMP Operations / PDU Types**

| Operation          | Direction       | Purpose                                                                                    |
| ------------------ | --------------- | ------------------------------------------------------------------------------------------ |
| **GetRequest**     | Manager → Agent | Retrieve the value of one or more specific OIDs                                            |
| **GetNextRequest** | Manager → Agent | Retrieve the next OID in the MIB tree (used to walk/traverse the MIB)                      |
| **GetBulkRequest** | Manager → Agent | Retrieve large blocks of data efficiently (SNMPv2+)                                        |
| **SetRequest**     | Manager → Agent | Set the value of one or more OIDs on the managed device                                    |
| **GetResponse**    | Agent → Manager | Response to Get/Set requests; contains values or error codes                               |
| **Trap**           | Agent → Manager | Unsolicited notification of a significant event (link down, temperature threshold, reboot) |
| **InformRequest**  | Agent → Manager | Acknowledged trap (SNMPv2+); agent expects a confirmation response                         |

***

**SNMP Message Structure (PDU)**

All SNMP messages share a common structure:

```
+------------------+------------------+------------------+
|    Version       |   Community      |      PDU         |
+------------------+------------------+------------------+
```

* **Version**: SNMPv1 (0), SNMPv2c (1), SNMPv3 (3).
* **Community**: A plain-text string acting as a password for SNMPv1/v2c. `public` is the conventional read-only community; `private` is read-write. This is a major security weakness.
* **PDU**: The actual Protocol Data Unit containing the operation and variable bindings.

**Variable Binding (VarBind):** A pair of `{OID, value}` representing a single managed object and its value. SNMP messages can contain multiple VarBinds.

***

**SNMP Versions**

| Feature             | SNMPv1                       | SNMPv2c                      | SNMPv3                      |
| ------------------- | ---------------------------- | ---------------------------- | --------------------------- |
| **Security**        | Community string (plaintext) | Community string (plaintext) | Authentication + Encryption |
| **Authentication**  | None                         | None                         | HMAC-MD5 or HMAC-SHA        |
| **Encryption**      | None                         | None                         | DES, AES                    |
| **GetBulk**         | No                           | Yes                          | Yes                         |
| **64-bit counters** | No                           | Yes (Counter64)              | Yes                         |
| **InformRequest**   | No                           | Yes                          | Yes                         |
| **Usage**           | Legacy                       | Widely deployed              | Recommended                 |

**SNMPv3 Security Model:**

SNMPv3 introduced a **User-based Security Model (USM)** with three security levels:

| Level          | Authentication | Encryption    | Meaning                         |
| -------------- | -------------- | ------------- | ------------------------------- |
| `noAuthNoPriv` | No             | No            | No security (like v1/v2c)       |
| `authNoPriv`   | Yes (HMAC)     | No            | Authenticated but not encrypted |
| `authPriv`     | Yes (HMAC)     | Yes (AES/DES) | Fully secure                    |

***

**SNMP Trap vs. Polling**

**Polling** (periodic GET): The manager requests data from each agent at regular intervals. Simple but generates traffic proportional to the number of devices × polling frequency. Issues between polls go undetected until the next poll.

**Trap (event-driven)**: The agent proactively sends a message when something notable happens. Near-real-time event notification with minimal network overhead. However, if the trap is lost (UDP is unreliable), the manager may miss the event — addressed by InformRequest (acknowledged traps) in SNMPv2/v3.

In practice, a hybrid approach is used: polling for metrics, traps for critical events.

***

**Common SNMP Use Cases**

* Monitoring interface traffic (bytes in/out, errors, discards) on routers and switches.
* Tracking CPU, memory, and disk utilisation on servers.
* Detecting device reboots (via `sysUpTime` resetting to zero).
* Monitoring UPS battery levels and power status.
* Receiving link-down/link-up traps from network equipment.
* Automating configuration changes via SNMP Set operations.

#### 5.2 DHCP (Dynamic Host Configuration Protocol)

**What is DHCP?**

**DHCP (Dynamic Host Configuration Protocol)** is an application-layer protocol that automatically assigns IP addresses and other network configuration parameters to devices on a network. Without DHCP, every device would require manual IP configuration — an unscalable task in any network of significant size. DHCP is defined in RFC 2131 and operates over **UDP**: the server listens on **port 67**, and the client sends from **port 68**.

DHCP is the successor to **BOOTP** (Bootstrap Protocol, RFC 951), which it extends. DHCP added the concept of **leases** (temporary address assignments) and a richer set of configuration options.

***

**Information Provided by DHCP**

A DHCP server can configure a client with:

| Parameter                   | Purpose                                                 |
| --------------------------- | ------------------------------------------------------- |
| **IP Address**              | The address assigned to this client                     |
| **Subnet Mask**             | Defines the network portion of the address              |
| **Default Gateway**         | Router to use for non-local traffic                     |
| **DNS Server(s)**           | Resolvers to use for hostname lookups                   |
| **Lease Duration**          | How long the address assignment is valid                |
| **Domain Name**             | Local domain suffix for hostname resolution             |
| **NTP Server**              | Time server address                                     |
| **WINS Server**             | Windows Internet Name Service (in Windows environments) |
| **TFTP Server / Boot File** | For network boot (PXE boot)                             |

***

**DHCP Lease Concept**

A DHCP address assignment is called a **lease** — it is a temporary allocation with an expiration time. This is the fundamental difference from BOOTP (which gave permanent assignments). Leases allow the DHCP server to:

* **Reclaim** addresses from devices that have left the network (powered off, disconnected) without explicit release.
* **Efficiently manage** a pool of IP addresses across a population larger than the pool size (not all devices are online simultaneously).

**Lease lifecycle:**

* At 50% of the lease duration: the client attempts to **renew** the lease with the original DHCP server (unicast DHCPREQUEST).
* At 87.5% of the lease duration: if renewal failed, the client attempts to **rebind** with any DHCP server (broadcast DHCPREQUEST).
* At 100% (expiry): if rebind also failed, the client must stop using the IP address and restart the DORA process.

***

**DHCP Process — The DORA Handshake**

The process of obtaining an IP address consists of four messages, commonly remembered as **DORA**:

```
Client                                        DHCP Server
(0.0.0.0:68)                                  (255.255.255.255:67)
     |                                               |
     |----DHCPDISCOVER (broadcast)------------------>|
     |   "I need an IP address!"                     |
     |   Client MAC: AA:BB:CC:DD:EE:FF               |
     |                                               |
     |<---DHCPOFFER (broadcast or unicast)-----------|
     |   "I offer you 192.168.1.100"                 |
     |   Lease: 24 hours, GW: 192.168.1.1            |
     |   DNS: 8.8.8.8                                |
     |                                               |
     |----DHCPREQUEST (broadcast)-----------------> |
     |   "I accept the offer of 192.168.1.100"       |
     |   (broadcast so other servers know)           |
     |                                               |
     |<---DHCPACK (broadcast or unicast)-------------|
     |   "Confirmed. Use 192.168.1.100"              |
     |   Lease start time confirmed                  |
     |                                               |
     [Client configures interface with 192.168.1.100]
```

**Step-by-step:**

1. **DHCPDISCOVER**: The client has no IP address. It sends a broadcast (source IP `0.0.0.0`, destination `255.255.255.255`) containing its MAC address, asking for an address. Multiple DHCP servers on the network may receive this.
2. **DHCPOFFER**: Each DHCP server that receives the Discover and has available addresses responds with an Offer. The offer contains a proposed IP, subnet mask, gateway, DNS, and lease duration. The server reserves (tentatively holds) the offered IP.
3. **DHCPREQUEST**: The client selects one offer (typically the first received) and broadcasts a Request indicating which server's offer it accepts. Broadcasting this is important — all servers see it, so those whose offers were not selected know to release their tentative reservations. The Request also includes the server identifier of the chosen server.
4. **DHCPACK**: The chosen server sends an Acknowledgement confirming the lease. The client configures its network interface with the provided parameters.

**Additional messages:**

| Message       | Purpose                                                                                      |
| ------------- | -------------------------------------------------------------------------------------------- |
| `DHCPNAK`     | Server rejects a client's request (e.g., address no longer available or client moved subnet) |
| `DHCPDECLINE` | Client informs server the offered IP is already in use (detected via ARP probe)              |
| `DHCPRELEASE` | Client voluntarily releases its IP address (e.g., on shutdown)                               |
| `DHCPINFORM`  | Client already has an IP but requests additional configuration parameters                    |

***

**DHCP Packet Format**

DHCP uses a fixed-format message (inherited from BOOTP) with a variable-length options field:

| Field     | Size      | Description                                                 |
| --------- | --------- | ----------------------------------------------------------- |
| `op`      | 1 byte    | Operation: 1 = BOOTREQUEST (client), 2 = BOOTREPLY (server) |
| `htype`   | 1 byte    | Hardware address type (1 = Ethernet)                        |
| `hlen`    | 1 byte    | Hardware address length (6 for MAC)                         |
| `hops`    | 1 byte    | Number of relay agents hopped through                       |
| `xid`     | 4 bytes   | Transaction ID (random; used to match replies to requests)  |
| `secs`    | 2 bytes   | Seconds elapsed since client started process                |
| `flags`   | 2 bytes   | Broadcast flag (bit 15); other bits reserved                |
| `ciaddr`  | 4 bytes   | Client IP address (0.0.0.0 if unknown)                      |
| `yiaddr`  | 4 bytes   | "Your" (client's) IP address offered/assigned               |
| `siaddr`  | 4 bytes   | Next server IP address (for TFTP/boot)                      |
| `giaddr`  | 4 bytes   | Relay agent IP address                                      |
| `chaddr`  | 16 bytes  | Client hardware (MAC) address                               |
| `sname`   | 64 bytes  | Optional server hostname                                    |
| `file`    | 128 bytes | Boot file name                                              |
| `options` | Variable  | DHCP options (type-length-value encoding)                   |

**Key DHCP Options:**

| Option Code | Name                   | Purpose                                                      |
| ----------- | ---------------------- | ------------------------------------------------------------ |
| 1           | Subnet Mask            | Client's subnet mask                                         |
| 3           | Router                 | Default gateway(s)                                           |
| 6           | Domain Name Server     | DNS server(s)                                                |
| 15          | Domain Name            | Local domain suffix                                          |
| 42          | NTP Servers            | Network Time Protocol server(s)                              |
| 50          | Requested IP Address   | Client's preferred IP                                        |
| 51          | IP Address Lease Time  | Lease duration in seconds                                    |
| 52          | Option Overload        | Indicates options overflow into `sname` or `file` fields     |
| 53          | DHCP Message Type      | Identifies the message type (Discover, Offer, Request, etc.) |
| 54          | Server Identifier      | IP of the server sending this message                        |
| 55          | Parameter Request List | Client requests specific options                             |
| 58          | Renewal (T1) Time      | Time to attempt renewal (50% of lease)                       |
| 59          | Rebinding (T2) Time    | Time to attempt rebind (87.5% of lease)                      |
| 61          | Client Identifier      | Unique client ID (often MAC-based)                           |
| 255         | End                    | Marks end of options                                         |

***

**DHCP Relay Agent**

A DHCP server does not need to be on the same subnet as clients. A **DHCP relay agent** (also called a BOOTP relay or IP helper) runs on the router connecting the client subnet to the rest of the network. It:

1. Receives the client's broadcast DHCPDISCOVER.
2. Sets the `giaddr` (Gateway IP Address) field to its own interface IP.
3. Forwards the message as a **unicast** to the configured DHCP server on another subnet.
4. The server uses `giaddr` to determine which subnet the client is on, and selects an address from the appropriate pool.
5. The relay forwards the server's reply back to the client.

This allows a single DHCP server to serve multiple subnets.

```
[Client subnet 10.0.1.x]          [Router with relay]          [DHCP Server 10.0.0.1]
Client --> broadcast --> Relay --> unicast to 10.0.0.1
                         Relay <-- unicast reply  <-- Server
Client <-- relay forwards
```

***

**Static vs. Dynamic vs. Reserved Assignments**

| Type                       | Description                                                      | Use Case                                                                                   |
| -------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Dynamic**                | Server selects an IP from a pool for each client                 | End-user devices (laptops, phones)                                                         |
| **Static (Manual)**        | Administrator manually configures the IP directly on the device  | Not using DHCP at all                                                                      |
| **Reserved (Static DHCP)** | DHCP server always assigns the same IP to a specific MAC address | Servers, printers, network devices that need stable IPs but still use DHCP for convenience |

***

**DHCP Security Considerations**

| Threat                | Description                                                                                  | Mitigation                                                                    |
| --------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **Rogue DHCP Server** | Attacker sets up an unauthorised DHCP server to assign wrong gateway/DNS (man-in-the-middle) | DHCP Snooping (switch feature that only allows DHCP replies on trusted ports) |
| **DHCP Starvation**   | Attacker floods server with requests using spoofed MACs, exhausting the IP pool, causing DoS | Port security (limit MACs per port); DHCP Snooping rate limiting              |
| **IP Spoofing**       | Client lies about its IP                                                                     | ARP inspection combined with DHCP Snooping                                    |

#### 5.3 NTP (Network Time Protocol)

**What is NTP?**

**NTP (Network Time Protocol)** is an application-layer protocol for synchronising the clocks of computers over a packet-switched network. It is defined in RFC 5905 (NTPv4). NTP is one of the oldest Internet protocols still in active use, developed by David L. Mills in 1985. It operates over **UDP port 123**.

Accurate time synchronisation is critical for:

* Logging and audit trails (correlating events across multiple systems requires consistent timestamps).
* Security protocols (TLS certificate validity windows; Kerberos authentication tickets expire if clocks diverge by more than 5 minutes).
* Distributed databases and file systems (ordering of transactions, conflict resolution).
* Financial transactions (regulatory compliance requires accurate timestamps).
* Network troubleshooting (correlating events across devices).

***

**Time Sources and the Stratum Hierarchy**

NTP uses a hierarchical, layered structure where **stratum** refers to the distance from the ultimate reference clock.

**Stratum 0 — Reference Clocks:**

These are high-precision timekeeping devices, not directly on the network. They include:

* **GPS receivers** — synchronised to atomic clocks aboard GPS satellites.
* **Atomic clocks** (cesium/rubidium oscillators).
* **Radio time signals** (e.g., WWVB in the USA, DCF77 in Germany).
* **CDMA/PSTN timing signals**.

Stratum 0 devices are connected to Stratum 1 servers via dedicated serial connections, GPS antennas, or PPS (Pulse-Per-Second) signals.

**Stratum 1 — Primary Servers:**

Directly connected to a Stratum 0 source. These are the highest-accuracy NTP servers accessible on the network. Examples: `time.nist.gov`, `time1.google.com`. There are only a few hundred of these worldwide.

**Stratum 2 — Secondary Servers:**

Synchronised from Stratum 1 servers. These form the bulk of the public NTP infrastructure. Organisations often run their own Stratum 2 server.

**Stratum 3, 4, ... N:**

Each level synchronises from the level above. Accuracy degrades slightly at each hop. NTP supports up to **Stratum 15**; Stratum 16 means "unsynchronised" (clock not trusted).

```
[Atomic Clock / GPS] -- Stratum 0 (not networked)
        |
[Primary NTP Server] -- Stratum 1
        |
[Secondary Server]   -- Stratum 2
        |
[Corporate NTP]      -- Stratum 3
        |
[Workstations/PCs]   -- Stratum 4
```

***

**How NTP Synchronises Clocks**

NTP does not simply set the client clock to the server's time. It carefully **measures and accounts for network delay** and gradually **slews** (adjusts) the clock rather than jumping it (which would break time-sensitive applications).

**Clock offset and round-trip delay measurement:**

NTP uses four timestamps to calculate the clock offset:

| Timestamp | Description                          |
| --------- | ------------------------------------ |
| $T\_1$    | Client send time (client's clock)    |
| $T\_2$    | Server receive time (server's clock) |
| $T\_3$    | Server send time (server's clock)    |
| $T\_4$    | Client receive time (client's clock) |

\$$\text{Round-trip delay} = \delta = (T\_4 - T\_1) - (T\_3 - T\_2)\$$

\$$\text{Clock offset} = \theta = \frac{(T\_2 - T\_1) + (T\_3 - T\_4)}{2}\$$

* $\delta$ is the total time the packet spent in transit (both directions).
* $\theta$ is the estimated difference between the client's clock and the server's clock. If $\theta > 0$, the client is behind; if $\theta < 0$, the client is ahead.

NTP assumes the network delay is symmetric (equal in both directions). Asymmetric delays introduce a fundamental error that NTP cannot fully eliminate.

**Clock adjustment:**

* If the offset is small (less than 128 ms by default), NTP **slews** the clock: it runs the clock slightly faster or slower to gradually converge to the correct time without a jump. The slew rate is limited to 500 ppm (parts per million) — at maximum slew, it takes about 2,000 seconds to correct a 1-second offset.
* If the offset is large (more than 1,000 seconds by default), NTP **steps** the clock — a one-time instant correction. This is done only during startup or when the clock has drifted severely.

***

**NTP Packet Format (Key Fields)**

| Field                        | Size    | Description                                                                                                    |
| ---------------------------- | ------- | -------------------------------------------------------------------------------------------------------------- |
| LI (Leap Indicator)          | 2 bits  | Warns of impending leap second (0=no warning, 1=+1s, 2=-1s, 3=unsynchronised)                                  |
| VN (Version Number)          | 3 bits  | NTP version (4 for NTPv4)                                                                                      |
| Mode                         | 3 bits  | 1=Symmetric active, 2=Symmetric passive, 3=Client, 4=Server, 5=Broadcast, 6=Control, 7=Private                 |
| Stratum                      | 8 bits  | Server's stratum level                                                                                         |
| Poll                         | 8 bits  | Maximum polling interval (log2 seconds; e.g., 6 = 64 seconds)                                                  |
| Precision                    | 8 bits  | Precision of the server's clock (log2 seconds; e.g., -20 ≈ 1 microsecond)                                      |
| Root Delay                   | 32 bits | Total round-trip delay to the Stratum 1 reference clock                                                        |
| Root Dispersion              | 32 bits | Maximum error relative to Stratum 1 source                                                                     |
| Reference ID                 | 32 bits | For Stratum 1: 4-character ASCII identifier (e.g., "GPS ", "PPS "); for others: IP address of reference source |
| Reference Timestamp          | 64 bits | Time when the local clock was last updated                                                                     |
| Originate Timestamp ($T\_1$) | 64 bits | Time the request departed the client                                                                           |
| Receive Timestamp ($T\_2$)   | 64 bits | Time the request arrived at the server                                                                         |
| Transmit Timestamp ($T\_3$)  | 64 bits | Time the response departed the server                                                                          |

The 64-bit NTP timestamps are fixed-point numbers: the top 32 bits are seconds since 1 January 1900, and the bottom 32 bits are the fractional part. This gives a resolution of approximately $2^{-32}$ seconds (\~233 picoseconds) and covers dates until the year 2036, after which the counter rolls over (an NTP-specific epoch rollover issue, addressed in NTPv4).

***

**NTP Operating Modes**

| Mode                         | Description                                                                                                       |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Client/Server (unicast)**  | Client sends requests to a specific server; server responds. Most common.                                         |
| **Symmetric active/passive** | Peers negotiate and synchronise with each other bidirectionally. Used between Stratum 1/2 servers for redundancy. |
| **Broadcast**                | Server periodically broadcasts time to all clients on the local subnet. Efficient for large LANs; less accurate.  |
| **Multicast**                | Similar to broadcast but multicast-addressed; used in large enterprise networks.                                  |

***

**SNTP — Simplified NTP**

**SNTP (Simple Network Time Protocol)**, defined in RFC 4330, is a simplified implementation of NTP intended for devices that do not need the full accuracy of NTP (microcontrollers, embedded devices, simple workstations). SNTP uses the same packet format as NTP but does not implement the full clock filter and selection algorithms. An SNTP client simply takes the offset from a single server and adjusts its clock, without accounting for jitter or selecting the best source from multiple servers.

***

**PTP — An Alternative (IEEE 1588)**

**PTP (Precision Time Protocol)**, defined in IEEE 1588, is an alternative time synchronisation protocol designed for local area networks requiring **sub-microsecond accuracy** — far beyond NTP's typical accuracy of 1–100 milliseconds (sub-millisecond on a LAN). PTP is used in financial trading, telecom, industrial automation, and audio/video broadcasting. It requires hardware timestamping support in network switches. NTP and PTP serve different accuracy tiers and coexist in practice.

***

**NTP Security — NTPsec and NTS**

Standard NTP has no authentication for client-server communication, making it vulnerable to:

* **NTP amplification attacks**: A small forged NTP request generates a large response, used in DDoS amplification.
* **Time injection attacks**: A malicious server sends false time to desynchronise or confuse a client (affecting security protocols, log correlation, etc.).

**NTPsec** is a hardened implementation of NTP that removes legacy code and vulnerabilities.

**NTS (Network Time Security)**, defined in RFC 8915, adds TLS-based authentication and encryption to NTP, providing cryptographic assurance of time server authenticity. NTS is the recommended approach for secure time synchronisation in NTPv4.
