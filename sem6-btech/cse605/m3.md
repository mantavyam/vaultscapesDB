### 1. Understanding Requirements

#### What is a Requirement?

A software requirement is a capability needed by the user to achieve an objective. According to the **IEEE Standard 729**, a requirement is defined as:

1. A condition or capability needed by a user to solve a problem or achieve an objective.
2. A condition or capability that must be met or possessed by a system or system component to satisfy a contract, standard, specification, or other formally imposed documents.
3. A documented representation of a condition or capability, as described in (1) and (2) above.

> **Note on Project Alignment:** Establishing a common understanding of requirements is vital to prevent misunderstanding in the project outcome. It behooves developers to accurately capture, interpret, and represent the needs of business partners and customers when specifying requirements for a software product.

***

### 2. Software Requirement Analysis

#### Overview

All plan-driven life cycle models prescribe that before starting to develop software, the exact requirements of the customer must be understood and documented.

* **Cost Control:** Starting development work without properly understanding and documenting requirements increases the number of iterative changes in later life cycle phases, alarmingly pushing up development costs.
* **Downstream Utility:** A good requirements document helps form a clear understanding of various features required from the software and serves as the basis for activities carried out during later life cycle phases.

#### Timeline of Analysis and Specification

* **Start Point:** The requirements analysis and specification phase starts after the feasibility study stage is complete and the project is deemed financially viable and technically feasible.
* **End Point:** The phase ends when the requirements specification document has been developed and reviewed.
* **The Deliverable:** The output is the **Software Requirements Specification (SRS)** document, which clearly organizes and details customer requirements.
* **The Roles:** This activity is carried out by experienced members of the development team who spend time at the customer site. The engineers who gather, analyze, and document these requirements are known as **System Analysts**.

```
[Feasibility Study (Complete)] 
             │
             ▼
┌───────────────────────────┐
│   Requirements Analysis   │ <── System Analysts (Elicitation & Analysis)
└───────────────────────────┘
             │
             ▼
┌───────────────────────────┐
│  Specification Writing    │ ─── Create Software Requirements Specification (SRS)
└───────────────────────────┘
             │
             ▼
[SRS Review & Approval]
```

#### Key Phases of Requirement Analysis

1. **Elicitation:** Gathering requirements from stakeholders (users, clients) using interviews, workshops, and surveys.
2. **Problem Analysis & Negotiation:** Identifying inconsistencies, ambiguities, and conflicts in requirements to refine them.
3. **Specification:** Creating the Software Requirement Specification (SRS) document to act as a blueprint for design. This documents both functional (what the system does) and non-functional (system properties) requirements.
4. **Review:** Systematically reviewing and refining the SRS after development to improve quality and address gaps.

## Requirements Classification

### 1. Behavioral (Functional) Requirements

#### Definition

Functional requirements describe **what** the software should do. They define the functions, features, and basic facilities that the system must offer. These are direct inputs, operations, and expected outputs that must be incorporated into the final system as part of the contract.

#### Key Characteristics

* Directly visible in the final product.
* Often stated as a sequence of inputs, internal operations, and expected outputs.
* Each high-level functional requirement may involve several interactions or dialogues between the system and the external environment.
* To accurately describe functional requirements, all possible scenarios must be systematically enumerated.
* **Expressions:** Can be expressed in natural language, structured/formatted language with informal syntax, or formal specification languages with rigorous syntax.
* **Alternative Name:** Also referred to as _Functional Specifications_.

#### Examples

* **User Authentication:** The system must allow users to log in using a username and password.
* **Search Functionality:** The software should enable users to search for products by name or category.
* **Report Generation:** The system should be able to generate sales reports for a specified date range.
* **Hospital Management System Example:** A doctor must be able to retrieve the medical records of their patients.

***

### 2. Non-Behavioral (Non-Functional) Requirements

#### Definition

Non-functional requirements (NFRs) describe **how** the software performs a task rather than what it does. They act as quality constraints, performance criteria, and operational limits that the system must satisfy.

#### Key Focus Areas

* Portability
* Security
* Maintainability
* Reliability
* Scalability
* Performance
* Reusability
* Flexibility

#### Examples

* **Performance:** The system should process 1,000 transactions per second.
* **Usability:** The software should be easy to use and feature a user-friendly interface.
* **Reliability:** The system must maintain 99.9% uptime.
* **Security:** Data must be encrypted during transmission and storage.

#### Common Categories of Non-Functional Requirements

* **Interface Constraints:** Requirements defining how the system interacts with users, other systems, or hardware.
* **Performance Constraints:** Response times, security levels, storage space capacities, etc.
* **Operating Constraints:** Limits imposed by the operational environment or target platform.
* **Life Cycle Constraints:** Long-term requirements such as maintainability, portability, and upgrade paths.
* **Economic Constraints:** Budgetary or resource limits affecting the development or deployment.

***

### 3. Domain Requirements

#### Definition

Domain requirements are characteristic of the particular industry, environment, or category of projects in which the software operates. They are derived directly from the domain model rather than specific user requests, and they can be either functional or non-functional in nature.

#### Key Characteristics

* They introduce industry-specific terminology, operational rules, and compliance standards.
* **Continuous Process:** Domain requirements engineering is a continuous process of proactively defining requirements for foreseeable applications within a software product line.

#### Examples

* **Healthcare:** The software must comply with HIPAA regulations for handling patient data safely.
* **Finance:** The system should adhere to GAAP standards for financial reporting.
* **E-Commerce:** The software should support various payment gateways like PayPal, Stripe, and credit cards.
* **Academic Records System:** An academic application maintaining school/college records must inherently allow access to the list of active faculty and student rosters for each grade level.

## Software Prototyping

#### Definition

Software prototyping is the process of implementing a simplified, preliminary version of the presumed software requirements. This is done to learn more about the actual requirements or to evaluate alternative designs that satisfy the requirements.

#### Why Prototyping is Needed

* To assess the exact set of requirements that will make a product successful in the marketplace.
* To test technical feasibility without incurring the cost of building the entire system.
* To keep end-users actively involved in the system design phase.

#### Key Benefits

* **Clarity on Gaps:** Helps developers identify and clarify missing requirements by showing users a visual draft of what they requested.
* **Risk Reduction:** Mitigates financial loss by enabling manufacturers and clients to determine project feasibility early, rather than building the complete system and finding it unviable.
* **Early Working Systems:** Provides a tangible, working system model ahead of scheduled deployment.
* **Stakeholder Engagement:** Actively involves the user in refining system design, leading to higher satisfaction.

## Software Design Quality: Coupling and Cohesion

Coupling and cohesion are two key metrics used to evaluate the quality of a software system's design. Both dictate the maintainability, scalability, and overall reliability of the codebase.

```
┌───────────────────────────────────────┐
│        High-Quality Software          │
│  ┌─────────────────────────────────┐  │
│  │      High Internal Cohesion     │  │  (Elements inside a module work together)
│  └─────────────────────────────────┘  │
│  ┌─────────────────────────────────┐  │
│  │      Low Inter-Module Coupling  │  │  (Modules are independent of each other)
│  └─────────────────────────────────┘  │
└───────────────────────────────────────┘
```

* **Poor Design (High Coupling, Low Cohesion):** Makes a system fragile, difficult to modify, and hard to unit-test.
* **Good Design (Low Coupling, High Cohesion):** Makes a system modular, easy to maintain, and simple to improve over time.

***

### 1. Cohesion

Cohesion refers to the degree to which elements inside a single module work together to fulfill a single, well-defined purpose.

* **High Cohesion:** Internal elements are closely related and tightly focused on one purpose.
* **Low Cohesion:** Internal elements are loosely related and serve multiple unrelated purposes.

#### Types of Cohesion (Ordered from Highest/Strongest to Lowest/Weakest)

| Cohesion Type                | Description                                                                                                                                                   | Strength & Maintainability     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| **Functional Cohesion**      | Elements work together to perform one single, clear function.                                                                                                 | **Highest** (Strongest Design) |
| **Sequential Cohesion**      | Elements are organized such that the output of one step serves as the direct input to the next step (data flow sequence).                                     | High                           |
| **Communicational Cohesion** | Elements operate on the same shared input data or contribute to the same output data (e.g., a module that updates a database record and prints it).           | Medium-High                    |
| **Procedural Cohesion**      | Elements are grouped because they must follow a specific sequence of steps, though the steps themselves might not share data.                                 | Medium-Low                     |
| **Layer Cohesion**           | Grouped by architectural layers, packaging modules that provide similar functional services (e.g., UI layer vs. Data Access layer).                           | Medium-Low                     |
| **Temporal Cohesion**        | Elements are grouped solely because they are executed at the same time in the execution cycle (e.g., an initialization module or a shutdown cleanup routine). | **Lowest** (Weakest Design)    |

***

### 2. Coupling

Coupling refers to the degree of interdependence between separate software modules.

* **High Coupling:** Modules are highly dependent on one another; changes in one module propagate changes across others.
* **Low Coupling:** Modules are independent; changes in one module have little to no impact on others.

#### Types of Coupling (Ordered from Weakest/Best to Strongest/Worst)

| Coupling Type         | Description                                                                                                                                        | Coupling Strength & Risk     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| **Data Coupling**     | Modules communicate solely by passing necessary elementary data (e.g., an integer, character, or boolean) as parameters.                           | **Weakest** (Best Design)    |
| **Stamp Coupling**    | Modules pass a complete composite data structure (e.g., an object, record, or struct), but the receiving module only uses a portion of its fields. | Weak                         |
| **External Coupling** | Modules depend on external tools, protocols, files, or hardware devices. Changes to external formats force changes in the code.                    | Medium                       |
| **Control Coupling**  | One module passes control information (such as a flag or code) to another, directly dictating its internal execution logic.                        | Medium-Strong                |
| **Common Coupling**   | Multiple modules read and write to the same shared global data space or global variables, making data-flow tracing difficult.                      | Strong                       |
| **Content Coupling**  | One module directly accesses, modifies, or branches into the internal code or private data of another module.                                      | **Strongest** (Worst Design) |

## Software Engineering Design Methodologies

The Software Design Process is the phase where developers plan how to turn structured requirements into a working system, serving as a structural blueprint. Rather than moving straight to writing code, developers decompose complex requirements into smaller pieces, establish system architecture, and define how components integrate.

The two main methodologies are:

1. **Function-Oriented Design (FOD)**
2. **Object-Oriented Design (OOD)**

***

### 1. Function-Oriented Design (FOD)

Function-Oriented Design decomposes a system into smaller, interacting modules based on the actions or functions they perform. It uses a **top-down approach** to break down high-level system requirements into nested sub-functions.

#### Key Characteristics

* **Functional Decomposition:** Breaking complex tasks into smaller, manageable functional modules (represented by action verbs).
* **Transformation View:** Treats the system as a transformation function that processes inputs to generate outputs.
* **Data Sharing:** Modules interact by passing parameters or accessing global memory space.
* **Primary Tools:** Relies on Data Flow Diagrams (DFDs), Structure Charts, and Data Dictionaries to map the architecture.
* **Best Use Cases:** Highly suitable for systems with stable, well-defined requirements where process flow is more critical than complex, changing data structures.

#### Trade-offs

* **Advantages:** Simple and easy to understand; directly translates functional requirements into a modular structure; highly effective for smaller, process-centric projects.
* **Limitations:** Lower reusability compared to object-oriented design; higher risk of coupling if modules share too much data; harder to maintain when requirements change significantly.

***

### 2. Data Flow Diagrams (DFD)

A Data Flow Diagram is a graphical tool used to represent how data moves through a system. It tracks data inputs, outputs, data stores, and the processes that transform the data. DFDs are widely used in structured analysis due to their simplicity and clarity for both technical and non-technical stakeholders.

#### Levels of DFD

DFDs are organized into hierarchical levels to manage complexity. Higher levels provide more details:

* **Level 0 DFD (Context Diagram):** Represents the entire system as a single process, showing its interaction with external entities. It highlights major inputs and outputs without any internal details.
* **Level 1 DFD:** Breaks the Level 0 process into major subprocesses, exposing internal data flows and data stores.
* **Level 2 DFD and Beyond:** Further decomposes Level 1 subprocesses into detailed functional areas. This is used for complex systems requiring deeper analysis.

#### Rules of DFD

Data flow transitions must follow strict architectural rules:

```
┌─────────────────────────────────┬─────────────────────────────────┐
│     Permitted Data Flows        │      Prohibited Data Flows      │
├─────────────────────────────────┼─────────────────────────────────┤
│ External Entity ──► Process     │ External Entity ─✖─ Ext. Entity │
│ Process ──► External Entity     │ External Entity ─✖─ Data Store  │
│ Process ──► Data Store          │ Data Store ─✖─ External Entity  │
│ Data Store ──► Process          │ Data Store ─✖─ Data Store       │
│ Process ──► Process             │                                 │
└─────────────────────────────────┴─────────────────────────────────┘
```

#### Case Study: Railway Reservation System DFD Levels

**Level 0 (Context Diagram)**

The entire reservation system is treated as a single process interacting with:

* Passenger (External Entity)
* Payment System (External Entity)
* Database (Data Store)

**Level 1 DFD**

The single system process is broken down into major internal subprocesses:

* Search Train
* Book Ticket
* Cancel Ticket
* Process Payment

**Level 2 DFD**

Further decomposes a Level 1 subprocess. For example, **Book Ticket** is broken down into: $$\text{Book Ticket} \longrightarrow \text{Verify Availability} \longrightarrow \text{Calculate Fare} \longrightarrow \text{Confirm Booking}$$

### 3. Structure Charts

A Structure Chart is a top-down, hierarchical diagram used to visualize the architectural design of a system. It decomposes a program into smaller modules and shows their control relationships, interactions, and data/control signals passed between them.

```
                  ┌─────────────────┐
                  │   Main Module   │
                  └────────┬────────┘
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
    ┌─────────────────┐         ┌─────────────────┐
    │  Read Input     │         │ Process Record  │
    └─────────────────┘         └─────────────────┘
      ( )                 ( )     ( )           (●)
       │                   ▲       │             ▲
       └───────Data────────┘       └────Data─────┴────Control (Flag)
```

#### Key Components of Structure Charts

* **Modules (Boxes):** Represent subroutines, functions, or processes.
* **Connections (Lines):** Show which modules call others, indicating control hierarchy.
* **Data Couple (Arrow with empty circle $\circ$):** Indicates data fields passed between modules.
* **Control/Flag Couple (Arrow with filled circle $\bullet$):** Indicates control signals (such as true/false flags) passed between modules.
* **Loops & Decisions:** Specialized symbols that indicate iterative execution or conditional branching.

***

### 4. Object-Oriented Design (OOD)

Object-Oriented Analysis and Design (OOAD) models a system as a set of interacting real-world objects. It focuses on identifying objects, defining their attributes and behaviors, and managing their interactions.

* **Core Principle:** Real-world items are mapped directly to software objects that encapsulate data (attributes) and operations (methods).
* **Design Patterns:** OOAD leverages established design patterns to help developers build efficient and maintainable systems.
* **UML Diagrams:** Unified Modeling Language diagrams (e.g., class diagrams, sequence diagrams) are used to visualize components and interactions.
* **Use Cases:** Uses formal use cases to clarify stakeholder needs and build a system that meets requirements.

> **Example (Library Management System):** Real-world objects like `Book`, `Member`, and `Librarian` are identified. Each has unique attributes and behaviors (e.g., a `Book` has an ISBN and a `borrow()` method), and they interact to coordinate library services.

#### The OOD Process Flow

```
┌───────────────────────┐
│  Requirement Analysis │ ─── Define the system's functional requirements
└──────────┬────────────┘
           │
           ▼
┌───────────────────────┐
│     System Design     │ ─── Create high-level architecture; identify objects
└──────────┬────────────┘
           │
           ▼
┌───────────────────────┐
│     Modeling (UML)    │ ─── Visualize classes, interfaces, and interactions
└──────────┬────────────┘
           │
           ▼
┌───────────────────────┐
│    Implementation     │ ─── Write code in an OOP language (C++, Java, Python)
└──────────┬────────────┘
           │
           ▼
┌───────────────────────┐
│        Testing        │ ─── Verify correct object interaction and requirements
└───────────────────────┘
```

## User Interface (UI) Design

UI Design is the process of creating user-facing interfaces, focusing on making interactions intuitive, accessible, and user-centric.

#### Core Principles

* **User-Centered:** Designing with a clear understanding of user needs, tasks, and context.
* **Consistency:** Using uniform UI elements (colors, icons, and typography) to reduce learning curves.
* **Feedback:** Providing clear, immediate, and visible responses to user actions.
* **Simplicity & Flexibility:** Creating clean, intuitive layouts that support customization for both novice and power users.

## Structured Programming Paradigms & Information Hiding

Structured programming paradigms dictate how software systems are decomposed and built. This section covers the Top-Down and Bottom-Up paradigms, as well as the principle of Information Hiding.

***

### 1. Bottom-Up Structured Programming (Composition Approach)

* **The Process:** Starts by building small, fundamental modules, testing them thoroughly, and then combining them into larger subsystems until the complete system is formed.
* **Characteristics:** This approach is commonly used in Object-Oriented Programming (OOP) languages (such as C++, Java, and Python).
* **Advantages:** Promotes high code reusability; simplifies individual component testing; minimizes redundant code.
* **Drawbacks:** It can be difficult to visualize the overall integrated system until late in the development cycle.

***

### 2. Top-Down Structured Programming (Decomposition Approach)

* **The Process:** Starts with a high-level overview of the program, then progressively decomposes it into smaller, functional modules or sub-programs.
* **Characteristics:** Primarily used in classic structured programming languages (such as C, COBOL, and Fortran).
* **Advantages:** Well-suited for large systems where high-level architecture must be locked in early; simplifies identifying structural design errors.
* **Drawbacks:** Subprograms are difficult to test in isolation because they depend on lower-level modules that may not yet be built; higher possibility of redundant information across modules.

***

### 3. Comparison Matrix

| S. No. | Top-Down Approach (Decomposition)                                        | Bottom-Up Approach (Composition)                                              |
| ------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| **1.** | Focuses on breaking a large problem down into smaller, manageable parts. | Solves smaller sub-problems first and integrates them into a complete system. |
| **2.** | Primarily used in Structured Programming languages (COBOL, Fortran, C).  | Primarily used in Object-Oriented Programming languages (C++, C#, Python).    |
| **3.** | Each part is programmed separately, which can lead to code redundancy.   | Redundancy is minimized by using data encapsulation and data hiding.          |
| **4.** | Modules require less communication during early development.             | Modules must communicate closely to integrate successfully.                   |
| **5.** | Well-suited for debugging and module documentation.                      | Primarily used and prioritized in integration testing.                        |

### 4. Information Hiding

#### Concept

Information Hiding is a design principle where modules hide their inner workings (implementation details) and only expose essential functions through a strictly defined interface.

#### Purpose

* Minimizes complexity by reducing dependencies between modules.
* Ensures that changes inside one module have little to no impact on other modules.

#### Application

This principle is foundational to software engineering and is applied in both functional decomposition (structured programming) and encapsulation (object-oriented programming).
