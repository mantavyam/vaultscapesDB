## **Module II: Software Metrics & Project Planning**

### **Software Measurement**

* Software measurement is the quantitative process of determining the size, complexity, quality, or cost of software products and processes to support data-driven decision-making.
* Governed by ISO standards, it involves collecting metrics on projects to improve productivity, estimate resources, and manage development, using both direct (e.g., lines of code) and indirect (e.g., maintainability) methods.
* Software metrics provide quantitative, reproducible measurements for project planning, cost estimation, and quality control, covering size (LOC, tokens, function points), design, data structures, and information flow.
* Key estimation models include COCOMO and Putnam, while effective risk management minimizes project delays and defects.

#### **Types of Metrics:**

* **Product Metrics:** Measure characteristics of the software itself (e.g., size, complexity, functionality, quality).
* **Process Metrics:** Measure characteristics of the development process (e.g., defect removal efficiency, development speed).
* **Project Metrics:** Measure resources and project status (e.g., cost, effort, schedule).

#### **Methods:**

* **Direct Measures:** Countable, such as lines of code, execution speed, and cost.
* **Indirect Measures:** Evaluative, such as complexity, functionality, and maintainability.

#### **Examples:**

* **Size:** Lines of Code (LOC), Function Points (FP).
* **Complexity:** Cyclomatic complexity (logic flow), Halstead complexity (operators/operands).

#### **Why Measure Software?**

* **Control:** Monitoring if a project is on time and within budget.
* **Improvement:** Identifying bottlenecks to enhance productivity and quality.
* **Prediction:** Estimating effort, cost, and defect rates for future projects.

***

### **Software Size Metrics**

These quantify the volume of software to estimate effort.

* **LOC (Lines of Code):** Simple, language-dependent measure of source instructions, excluding comments/blank lines.
* **Token Count:** Treats programs as a series of tokens (operators/operands) to measure software science complexity.
* **Function Count (Function Points - FP):** Measures functionality from a user's perspective, independent of programming language. It counts Inputs, Outputs, Inquiries, Files, and Interfaces, adjusted by complexity factors.

### **Lines of Code (LOC)**

* Lines of Code (LOC) is a size-oriented software metric that counts the total lines in source code to estimate project size, cost, and developer productivity.
* It generally excludes comments and blank lines, focusing on executable and non-executable statements.
* While easy to use, it is language-dependent and can encourage poor code quality (bloat).

* 10,000 LOC $$\rightarrow$$ 13,50

#### **Lines of Code (LOC) Metrics Categories:**

LOC measures the physical or logical size of a program, often used for productivity, cost, and maintenance estimation.

* **Physical Lines (LOC):** Counts every line in the source file, including comments and blank lines.
* **Logical Lines of Code (LLOC/NCLOC):** Counts the number of executable statements or declarations, often language-dependent.
* **Common Units:** Often measured in KLOC (Thousands of Lines of Code).

LOC typically fall into three categories for cost estimation: Three-Point Estimation, Productivity/Cost Calculations, and Conversion from Function Points.

#### **1. PERT: Three-Point Estimation**

The Program Evaluation and Review Technique (PERT) uses three values to account for uncertainty. Instead of a single "guess," you look at the best, worst, and most likely scenarios.

**The Variables:**

* **Optimistic (a or O):** Everything goes perfectly.
* **Most Likely (m or M):** The standard expectation.
* **Pessimistic (b or P):** Everything goes wrong (risks materialize).

**The Formulas:** PERT uses a weighted average (Beta distribution) to give more weight to the "Most Likely" scenario:

$$E = \frac{a + 4m + b}{6}$$

To understand the risk or "spread," we calculate the Standard Deviation ($$\sigma$$):

$$\sigma = \frac{b - a}{6}$$

**Numerical Example:** Imagine you are estimating the time to develop a login module:

* Optimistic (a): 10 days
* Most Likely (m): 15 days
* Pessimistic (b): 26 days
* **Calculated Estimate (E):** $$E = \frac{10 + (4 \times 15) + 26}{6} = \frac{96}{6} = 16$$ days.

***

#### **2. Productivity & Cost Metrics (LOC)**

Software projects often use Lines of Code (LOC) or Source Lines of Code (SLOC) to measure output.

* **Productivity:** How much "work" is produced per unit of effort.

$$Productivity = \frac{LOC}{Person-Months}$$

* **Cost per Line:** How much each line of code costs the company.

$$Cost\ per\ LOC = \frac{Total\ Project\ Cost}{Total\ LOC}$$

**Numerical Example: Effort and Total Cost** The Scenario:

* Estimated Size: 20,000 LOC
* Team Productivity: 500 LOC / Person-Month
* Labor Rate: $8,000 per month (per person)

**Steps:**

1. **Total Effort:** $$\text{Effort} = \frac{20{,}000}{500} = 40$$ Person-Months.
2. **Total Cost:** $$\text{Total Cost} = 40 \times 8{,}000 = \$320{,}000$$.
3. **Cost per Line:** $$\frac{\$320{,}000}{20{,}000} = \$16$$ per line.

**Summary Table:**

| Metric        | Formula                      | Unit          |
| ------------- | ---------------------------- | ------------- |
| PERT Estimate | $$(a+4m+b)/6$$               | Days / Weeks  |
| Effort        | Size/Productivity            | Person-Months |
| Project Cost  | Effort $$\times$$ Labor Rate | Currency ($)  |

***

#### **Disadvantages of LOC:**

* **Language Dependency:** Different languages require varying line counts to achieve the same functionality.
* **Quality Issues:** High LOC can promote inefficient "code bloat" rather than concise, maintainable code.
* **Refactoring:** Code optimization often reduces LOC, which can inaccurately imply lower productivity.

## **Token Count (Halstead Metrics)**

* Token count in software engineering is a size-oriented metric measuring code volume by counting individual lexical units—operators and operands—rather than lines of code (LOC).
* Halstead's Software metrics are a set of measures proposed by Maurice Halstead to evaluate the complexity of a software program.
* These metrics are based on the number of distinct operators and operands in the program and are used to estimate the effort required to develop and maintain the program.

#### **Key Aspects of Token Count Metric:**

* **Tokens:** Smallest functional units in code.
* **Operands:** variables, constants, labels.
* **Operators:** arithmetic symbols, keywords like if/for, delimiters.
* **Formula Components:** \* $$n_1$$**:** Number of unique operators (eg, +, if, float, ()).
* $$n_2$$**:** Number of unique operands (e.g, x, temp, 100).
* $$N_1$$**:** Total occurrences of operators.
* $$N_2$$**:** Total occurrences of operands.

#### **Measurements Derived:**

* **Vocabulary (n):** $$n_1 + n_2$$
* **Program Length (N):** $$N_1 + N_2$$
* **Volume (V):** $$N \times \log_2(n)$$
* **Estimated Length (**$$\hat{N}$$**):** $$\hat{N} = n_1 \log_2 n_1 + n_2 \log_2 n_2$$
* **Estimated Program Level / Difficulty:**
* $$\hat{L} = \frac{2n_2}{n_1 N_2}$$
* $$\hat{D} = \frac{1}{\hat{L}} = \frac{n_1 N_2}{2n_2}$$
* **Effort (E):** $$E = V / \hat{L} = V \times \hat{D}$$
* **Time (T):** $$T = E / \beta$$ (where $$\beta$$ is normally set to 18).

#### **Numerical Example (Token Count Calculation):**

**Problem:** Calculate Vocabulary and Token Count for:

```cpp
int main() {
 int a, b, sum;
 a = 10;
 b = 20;
 sum = a + b;
}
```

**Step 1: Identify Operators (**$$n_1$$ **and** $$N_1$$**)**

| Operator   | Occurrences                              |
| ---------- | ---------------------------------------- |
| int        | 2                                        |
| main       | 1                                        |
| ()         | 1                                        |
| {}         | 1                                        |
| ,          | 2                                        |
| ;          | 4                                        |
| =          | 3                                        |
| +          | 1                                        |
| **Totals** | $$n_1 = 8$$ **(Distinct)**; $$N_1 = 15$$ |

**Step 2: Identify Operands (**$$n_2$$ **and** $$N_2$$**)**

| Operand    | Occurrences                              |
| ---------- | ---------------------------------------- |
| a          | 3                                        |
| b          | 3                                        |
| sum        | 2                                        |
| 10         | 1                                        |
| 20         | 1                                        |
| **Totals** | $$n_2 = 5$$ **(Distinct)**; $$N_2 = 10$$ |

**Step 3: Final Results**

* **Vocabulary (n):** $$8 + 5 = 13$$
* **Total Token Count (N):** $$15 + 10 = 25$$
* **Volume (V):** $$25 \times \log_2(13) = 25 \times 3.7004 = 92.51$$ bits.
* **Estimated Length (**$$\hat{N}$$**):** Assuming a split of $$n_1=6, n_2=7 \rightarrow (6 \times 2.585) + (7 \times 2.807) \approx 35.16$$.

## Function Count & Functional Metrics

The term "function count size metric" refers primarily to the Function Point (FP) metric, a standardized unit of measurement used to quantify the amount of business functionality a software system provides from a user's perspective.

#### **Key Concepts:**

* **Function Point (FP):** Measures the size based on functions/transactions provided to the user.
* **User-Oriented:** Focused on what the user requests and receives, independent of programming language.
* **Purpose:** Used to estimate effort, cost, and duration at an early stage, even before coding begins.

#### **The Five Components of FP Analysis:**

Categorized into five information domain characteristics, weighted by complexity (simple, average, or complex):

1. **External Inputs (EI):** Unique data/control info input from external sources entering application boundary.
2. **External Outputs (EO):** Unique data/control info outputs sent from application to external sources (reports, messages).
3. **External Inquiries (EQ):** Interactive queries retrieving data from internal logical files without changing data.
4. **Internal Logical Files (ILF):** Logically related group of data maintained within boundary (e.g., database table).
5. **External Interface Files (EIF):** Logically related group of data referenced by the application but maintained by another application.

#### **Standard Weighting Table: UFP**

| Measurement Parameter               | Low | Average | High |
| ----------------------------------- | --- | ------- | ---- |
| Number of external inputs (EI)      | 3   | 4       | 6    |
| Number of external outputs (EO)     | 4   | 5       | 7    |
| Number of external inquiries (EQ)   | 3   | 4       | 6    |
| Number of internal files (ILF)      | 7   | 10      | 15   |
| Number of External Interfaces (EIF) | 5   | 7       | 10   |

**Final FP Formula:**

$$FP = Unadjusted\ Function\ Points\ (UFP) \times Value\ Adjustment\ Factor\ (VAF)$$

* **VAF Calculation:** $$0.65 + (0.01 \times \sum F_i)$$
* $$\sum F_i$$ is the sum of 14 GSCs (General System Characteristics), ranging from 0 to 70.

#### **FP Numerical Example:**

Small Library Management System:

* External Inputs: 2 (Simple) $$\rightarrow 2 \times 3 = 6$$
* External Outputs: 1 (Average) $$\rightarrow 1 \times 5 = 5$$
* External Inquiries: 2 (Simple) $$\rightarrow 2 \times 3 = 6$$
* Internal Logical Files: 1 (High complexity) $$\rightarrow 1 \times 15 = 15$$
* External Interface Files: 0 $$\rightarrow 0 \times 7 = 0$$
* $$\sum F_i$$: 35.
* **Total UFP:** $$6 + 5 + 6 + 15 + 0 = 32$$.
* **VAF:** $$0.65 + (0.01 \times 35) = 1.0$$.
* **Final FP:** $$32 \times 1.0 = 32$$.
* **Effort estimation:** If productivity is 5 hours/FP, total effort = $$32 \times 5 = 160$$ hours.

#### **Standard Conversion Ratios (FP to LOC):**

| Language | Average LOC/FP |
| -------- | -------------- |
| C        | 128            |
| C++      | 64             |
| Java     | 53             |
| Python   | 40             |
| SQL      | 12             |

**Example:** If software has 15.4 FP in C++: $$15.4 \times 64 = 985.6$$ LOC.

***

**Example:** Given the following values, compute function point when all complexity adjustment factor (CAF) and weighting factors are Simple.

* User Input = 50
* User Output = 40
* User Inquiries = 35
* User Files = 6
* External Interface = 4

Using the standard weighting factors for **Simple** complexity:

***

**Step 1: Unadjusted Function Points (UFP)**

UFP is calculated by multiplying each count by its Simple weight and summing them up:

$$
UFP = (50 \times 3) + (40 \times 4) + (35 \times 3) + (6 \times 7) + (4 \times 5)
$$

$$
UFP = 150 + 160 + 105 + 42 + 20 = \mathbf{477}
$$

***

**Step 2: Complexity Adjustment Factor (CAF)**

Since all 14 CAF factors are rated as **Simple** (scale = 1, i.e., "Incidental"), the formula is:

$$
CAF = 0.65 + (0.01 \times \Sigma F_i) = 0.65 + (0.01 \times 14 \times 1)
$$

$$
CAF = 0.65 + 0.14 = \mathbf{0.79}
$$

***

**Step 3: Final Function Point (FP)**

$$
FP = UFP \times CAF = 477 \times 0.79 = \mathbf{376.83}
$$

### **Computing 3D Function Points:**

**3D Function Point** is an extended function point metric developed by **Boeing** that measures software functionality across three distinct dimensions — Data, Functional, and Control — to better handle real-time and control-intensive systems.

### The Three Dimensions

#### Data Dimension

This dimension is evaluated exactly like traditional Function Points (FP), counting inputs, outputs, inquiries, external interfaces, and internal files with complexity weights.

#### Functional Dimension

This dimension captures **Feature-Transformations** — the number of internal processing steps required to transform input data into output data. A "transformation" is viewed as a series of processing steps constrained by a set of semantic statements.

#### Control Dimension

This dimension captures **Feature-Transitions** — the total number of transitions between states in a system. Each state represents an externally observable mode of behavior, making this dimension especially useful for real-time systems.

***

### Formula

The 3D Function Point index is computed as:

$$
\text{Index} = I + O + Q + F + E + T + R
$$

Where:

* **I** = Inputs
* **O** = Outputs
* **Q** = Inquiries
* **F** = Internal data structures (files)
* **E** = External files
* **T** = Transformations (functional dimension)
* **R** = Transitions (control dimension)

Each value is a **complexity-weighted count** calculated as:

$$
\text{Complexity Weighted Value} = N_{il}W_{il} + N_{ia}W_{ia} + N_{ih}W_{ih}
$$

Where $$N$$ represents the number of occurrences at low, average, and high complexity, and $$W$$ represents the corresponding weights.

***

### Why 3D Function Points?

Boeing introduced this method to solve **two key limitations** of the original Albrecht Function Point approach:

* The traditional FP method focuses mostly on data-oriented applications and **underestimates real-time or control-heavy systems**.
* It does not account for internal processing complexity (transformations) or state-based behavior (transitions).

> **Note:** Function Points, Feature Points, and 3D Function Points all measure "functionality delivered by software" — they yield the same value when only the data dimension is considered.

## **Design and Data Metrics**

### **Design Metrics:**

Measure complexity and structure of system architecture.

* **Structural Coupling:** Analyzes module interaction via static analysis.
* **Information Flow Metrics:** Measure connections and transfer between components.
* **Cyclomatic Complexity (V(G)):** Number of linearly independent paths.

### **Data Structure Metrics:**

* **Amount of Data:** Quantified by number of variables (VARS), unique operands ($$n_2$$), and total occurrences of variables ($$N_2$$).
* **Usage of Data:** Average number of live variables within a procedure.
* **Sharing of Data:** Assesses data coupling (higher sharing = higher complexity).
* **Program Weakness:** Relates to lack of cohesion in modules.

### **Information Flow Metrics (Henry and Kafura):**

* **FAN-IN:** Number of components that call or pass info to a specific component.
* **FAN-OUT:** Number of components called by a specific component.
* **Information Flow Index (IF(A)):** Derived from fan-in and fan-out.
* High fan-in/fan-out indicate weak cohesion and excessive coupling.

## **Cost Estimation Models**

Mathematical algorithms used to predict effort, duration, and cost.

### **1. Static Single Variable Model:**

Equation depends on one predictor (usually size):

$$C = aL^b$$

* C = cost/effort (person-months).
* L = size (LOC).
* a, b = constants from historical data.
* **SEL Model Equations:**
* $$E = 1.4L^{0.93}$$
* $$DOC = 30.4L^{0.90}$$
* $$D = 4.6L^{0.26}$$

### **2. Static Multivariable Model:**

Depends on several variables for development environment.

* **Equations:**
* $$E = 5.2L^{0.91}$$
* $$D = 4.1L^{0.36}$$

***

### **COCOMO (Constructive Cost Model)**

Developed by Barry Boehm in 1981. It is a regression-based model using KLOC.

#### **Six Phases of COCOMO:**

1. **Planning and requirements:** Defining scope, objectives, and constraints.
2. **System design:** High-level architecture and overall structure.
3. **Detailed design:** Specifications for modules, algorithms, and interfaces.
4. **Module code and test:** Writing source code and coding functionalities.
5. **Integration and test:** Combining modules and ensuring they work together.
6. **Cost Constructive model:** Using the actual estimation formulas.

#### **Types of Projects in COCOMO:**

1. **Organic:** Small team, well-understood problem, nominal experience.
2. **Semi-detached:** Intermediate team size and knowledge. (e.g., Compilers).
3. **Embedded:** Highest complexity, large team, strict requirements. (e.g., Flight control).

#### **Comparison Table:**

| Aspects         | Organic            | Semidetached         | Embedded        |
| --------------- | ------------------ | -------------------- | --------------- |
| Project Size    | 2 to 50 KLOC       | 50-300 KLOC          | 300+ KLOC       |
| Complexity      | Low                | Medium               | High            |
| Team Experience | Highly experienced | Mixed Staff          | Experts         |
| Environment     | Flexible           | Somewhat flexible    | Highly rigorous |
| Example         | Simple payroll     | New interface system | Flight control  |

#### **Basic COCOMO Formulas:**

* **Effort (E):** $$a_b(KLOC)^{b_b}$$ Person-Months.
* **Development Time (D):** $$c_b(E)^{d_b}$$ Months.
* **Average Staff Size (SS):** $$E / D$$ Persons.
* **Productivity (P):** $$KLOC / E$$ KLOC/PM.

**Coefficients Table 4(a):**

| Software Project | $$a_b$$ | $$b_b$$ | $$c_b$$ | $$d_b$$ |
| ---------------- | ------- | ------- | ------- | ------- |
| Organic          | 2.4     | 1.05    | 2.5     | 0.38    |
| Semidetached     | 3.0     | 1.12    | 2.5     | 0.35    |
| Embedded         | 3.6     | 1.20    | 2.5     | 0.32    |

**Numerical Solution for 400 KLOC:**

* **Organic:** $$E = 2.4(400)^{1.05} = 1295.31$$ PM; $$D = 2.5(1295.31)^{0.38} = 38.07$$ PM.
* **Semidetached:** $$E = 3.0(400)^{1.12} = 2462.79$$ PM; $$D = 2.5(2462.79)^{0.35} = 38.45$$ PM.
* **Embedded:** $$E = 3.6(400)^{1.20} = 4772.81$$ PM; $$D = 2.5(4772.8)^{0.32} = 38$$ PM.

### **Putnam Resource Allocation Model**

Created by Lawrence H. Putnam in the late 1970s. Useful for large, intricate projects.

#### **Key Concepts:**

* **Trade-off:** Between time available and resources (effort) needed.
* **Rayleigh Curve:** Illustrates effort distribution. Effort peaks and then decreases as the project approaches final stages. The X-axis is time, Y-axis is effort.

#### **SLIM Model (Software Life Cycle Model):**

Uses the **Putnam-Norden-Rayleigh (PNR)** equation:

$$S = Ck^{1/3}t^{4/3}$$

* S = software size.
* C = technology factor.
* k = effort coefficient.
* t = time to complete.

**Example of Schedule Compression:**

* $$t_1 = 12$$ months $$\rightarrow$$ Effort $$E_1 \approx 22.63$$.
* $$t_2 = 8$$ months $$\rightarrow$$ Effort $$E_2 \approx 11.31$$ (assuming change in coefficients).
* Principle: Compressing the schedule results in significantly higher costs/effort.

## **Risk Management**

The proactive process of identifying, analyzing, prioritizing, and mitigating potential threats to ensure project success.

#### **The Risk Management Process:**

1. **Risk Identification:** Uncovering risks. $\rightarrow$ **List of Potential Risks**.
2. **Risk Analysis:** Evaluating probability/impact. $\rightarrow$ **Prioritised Risk List**.
3. **Risk Planning:** Avoidance/Contingency plans. $\rightarrow$ **Risk Avoidance and Contingency Plans**.
4. **Risk Monitoring:** Tracking risks. $\rightarrow$ **Risk Assessment**.

#### **Common Types of Software Risks:**

* **Project Risks:** Budget overruns, schedule delays, resource shortages.
* **Technical Risks:** Unproven technology, complex code, poor performance.
* **Business Risks:** BUILDING the wrong product, losing management support.
* **Requirements Risks.**
